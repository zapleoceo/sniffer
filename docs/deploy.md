# Развёртывание

SnifferBot живёт на том же Hetzner-сервере, что Вера, Степан и AIbroker,
отдельным compose-проектом. Контракт изоляции — [spec-v2.md, раздел
1](spec-v2.md#1-изоляция-от-веры--контракт).

> [architecture.md, раздел 8](architecture.md#8-что-используем) всё ещё
> описывает план с Oracle Cloud Always Free. Он отменён: хост — Hetzner
> (spec-v2, таблица в разделе 0). Этот файл описывает то, что есть.

## 1. Где что живёт

| | |
|---|---|
| Домен | `lbot.zapleo.com` — указывает на этот сервер |
| Сервер | **отдельная машина под проект** — IP, SSH-алиас и порт проставить при заказе |
| Каталог | `/var/www/sniffer` |
| Репозиторий | `https://github.com/zapleoceo/sniffer`, ветка `master` |
| Compose-проект | `sniffer` (сеть `sniffer_default`, том `sniffer_sniffer_pgdata`) |
| Контейнеры | `sniffer-postgres`, `-collector`, `-worker`, `-bot`, `-notifier` |
| БД | `docker exec sniffer-postgres psql -U sniffer -d sniffer`, хост-порт `127.0.0.1:5433` |

**Домен пока ничего не обслуживает.** Бот работает long polling, ни один
процесс SnifferBot не слушает порт. `lbot.zapleo.com` зарезервирован под
будущий вебхук или лендинг; открывать под него 80/443 сейчас не нужно, и
healthcheck деплоя по HTTP поэтому не ходит — он смотрит на состояние
контейнеров.

## 2. Требования к машине

SnifferBot едет на **собственный сервер**. Изоляция от Веры физическая: её
машина (`195.201.31.49`) остаётся нетронутой, потому что на её IP завязаны
клиентские конфиги WireGuard и ссылки MTProxy на чужих устройствах — при смене
адреса они умирают молча. Переезд Веры отменён именно по этой причине.

Минимум под полный стек:

| Ресурс | Минимум | Комфортно | Почему |
|---|---|---|---|
| RAM | 4 ГБ | **8 ГБ** | пять контейнеров живут в 400–600 МБ, но на P2 приезжают SearXNG и Firecrawl, а Firecrawl тянет headless Chrome |
| Диск | 25 ГБ | **40 ГБ** | образы ~4 ГБ, база растёт от `raw_messages`, build-cache переполняется незаметно |
| CPU | 2 vCPU | 2 vCPU | нагрузка I/O-bound, считать нечего |

Опыт соседней машины, из-за которого эти цифры не взяты с потолка: 3.8 ГБ RAM,
занятых на 2 ГБ, и 2.9 ГБ в свопе из 4 — состояние, при котором любой новый
жадный процесс отбирает память у соседей, а OOM-killer выбирает жертву по всей
машине, а не по compose-проекту.

Отсюда три правила, которые нельзя нарушать молча:

1. **Стек держим компактным.** Пять контейнеров: Postgres и четыре тонких
   Python-процесса. Каждый с потолком памяти (`mem_limit` в
   `docker-compose.yml`), суммарный потолок ~1.5 ГБ при реальном потреблении
   400–600 МБ. Потолок — страховка от утечки, а не резервирование.
2. **SearXNG и Firecrawl сюда не ставятся.** Они описаны в
   [spec-v2, раздел 4](spec-v2.md#4-источники--проверенный-статус) как
   веб-источник этапа P2, но SearXNG — это ещё 300–500 МБ, а Firecrawl тянет
   headless-браузер, то есть гигабайт с лишним и пики при каждом рендере. На
   этой машине их нет и не будет. Веб-источник — отдельное решение: вторая
   машина, внешний сервис или перенос P2. Добавлять их в этот
   `docker-compose.yml` нельзя.
3. **Сборка — самое тяжёлое, что здесь происходит.** `docker compose build`
   без аргументов собрал бы четыре сервиса параллельно; на ~1 ГБ свободной
   памяти это OOM. Поэтому `infra/deploy.sh` собирает ровно один сервис —
   образ у всех четырёх общий (`sniffer:local`).

Если станет теснее, следующий шаг — **собирать образ в GitHub Actions и тянуть
готовый из GHCR**. Тогда с сервера уходит и пик памяти на сборке, и build-cache
с диска. Пока не сделано: требует настройки пакетов и токена, отдельная задача.

## 3. Первичная установка — один раз, руками

Всё, что ниже, делается один раз. Дальше сервер трогают только через
конвейер: **ручных правок в `/var/www/sniffer` нет, состояние сервера
определяется репозиторием.**

### 3.1 Deploy-ключ

На своей машине:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/sniffer_deploy -C "github-actions sniffer" -N ""
```

Публичную часть — на сервер, приватную — в GitHub Secrets (раздел 4).

```bash
ssh -p <порт> root@<ip> \
  "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys" < ~/.ssh/sniffer_deploy.pub
```

### 3.2 Ключ для `git fetch` с сервера

Отдельный от предыдущего: тем ходит GitHub на сервер, этим — сервер на GitHub.
Read-only deploy key в настройках репозитория (Settings → Deploy keys), **без
парольной фразы**: деплой запускается неинтерактивно, и ключ с паролем просто
подвесит `git fetch` до таймаута.

На сервере:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/sniffer_repo -C "sniffer server pull" -N ""
cat >> ~/.ssh/config <<'EOF'
Host github.com
  IdentityFile ~/.ssh/sniffer_repo
  IdentitiesOnly yes
EOF
```

Публичную часть `~/.ssh/sniffer_repo.pub` — в Settings → Deploy keys, галку
«Allow write access» **не** ставить. Затем один раз вручную:

```bash
ssh -T git@github.com     # принять ключ хоста, иначе первый деплой встанет
```

Без этих трёх шагов деплой падает на `git fetch` с `Permission denied
(publickey)`, и по логу это выглядит как проблема с деплой-ключом GitHub
Actions, хотя дело в другом ключе.

### 3.3 Каталог и код

```bash
mkdir -p /var/www && cd /var/www
git clone git@github.com:zapleoceo/sniffer.git sniffer
cd sniffer && cp .env.example .env
```

Заполнить `.env` — чеклист в [spec-v2, раздел
9](spec-v2.md#9-что-нужно-завести). Обязательный минимум: `BOT_TOKEN`,
`TG_API_ID`, `TG_API_HASH`, `TG_PHONE`, `BROKER_PROJECT_KEY`.

Два поля важно не пропустить:

- `DATABASE_URL=postgresql+asyncpg://sniffer:<пароль>@postgres:5432/sniffer` —
  внутри compose-сети база доступна по имени сервиса, а не по `localhost:5433`.
  5433 — это только для доступа с хоста.
- `POSTGRES_PASSWORD=<длинный случайный>` — если не задать, compose подставит
  дефолт `sniffer`. Порт слушает только loopback, но пароль-заглушка на
  машине, где живут ещё три проекта, — это долг, а не решение.

### 3.4 Первый старт

```bash
docker compose up -d postgres
docker compose logs -f postgres     # дождаться "database system is ready"
```

Схема (`infra/sql/001_init.sql`) применяется автоматически и **только при
создании тома**. На уже созданной базе файл не выполнится — это важно помнить
при изменениях схемы (раздел 7).

### 3.5 Авторизация юзербота

Telethon при первом запуске просит код из SMS — интерактивно, поэтому руками:

```bash
docker compose run --rm collector python -m sniffer.collector auth
```

Полученную `StringSession` вписать в `.env` как `TG_SESSION`. Строкой, а не
файлом: файловая сессия не переживает пересоздание контейнера.

### 3.6 Полный запуск

```bash
docker compose up -d
docker compose ps
```

Дальше — только конвейер.

## 4. GitHub Secrets

Settings → Secrets and variables → Actions → **New repository secret**.
Значения секретов после сохранения не показываются — только перезаписываются.

| Секрет | Обязателен | Что кладём |
|---|---|---|
| `SSH_PRIVATE_KEY` | да | Содержимое `~/.ssh/sniffer_deploy` **целиком**, вместе со строками `-----BEGIN…` и `-----END…` и переводом строки в конце |
| `SSH_HOST` | да | IP нового сервера |
| `SSH_USER` | да | `root` |
| `SSH_PORT` | **на этой машине да** | порт SSH нового сервера, если он не 22 |
| `SSH_KNOWN_HOSTS` | желательно | Вывод `ssh-keyscan -p <порт> <ip>`. Без него ключ хоста принимается без проверки, и в лог падает `::warning::` |
| `DEPLOY_PATH` | нет | Только если каталог не `/var/www/sniffer` |

Проверить ключ до первого деплоя:

```bash
ssh -i ~/.ssh/sniffer_deploy -p <порт> root@<ip> 'echo ok && docker compose version'
```

**Про `root`.** Деплой ходит под root, потому что так уже устроен доступ к
этой машине. Правильнее — отдельный пользователь `deploy` в группе `docker` и
владелец `/var/www/sniffer`: тогда утёкший ключ даёт максимум управление
контейнерами, а не машиной. Не сделано; когда будет — меняется только секрет
`SSH_USER` и владелец каталога.

## 5. Как идёт деплой

Пуш в любую ветку → `quality`. Merge в `master` → `docs-gate` + `quality` →
`deploy`. Файлы: `.github/workflows/quality.yml`,
`.github/workflows/deploy.yml`, `infra/deploy.sh`.

```
push master
   ├── docs-gate   менялся src/sniffer/{sources,verifier,pipeline}/ — значит
   │               в диффе обязан быть и docs/*.md, иначе сборка красная
   ├── quality     ruff check · ruff format --check · mypy · pytest
   │               плюс проверка, что в дифф не попали .env, *.session, ключи
   └── deploy      только если оба зелёные
```

`deploy` копирует `infra/deploy.sh` из деплоящегося коммита в `/tmp` на
сервере и запускает его там. Именно из коммита, а не с диска сервера: иначе
правка самого скрипта применялась бы со следующего деплоя, а не с этого.

Что делает `infra/deploy.sh`:

1. Берёт замок `/var/lock/sniffer-deploy.lock`. Два деплоя одновременно
   перетёрли бы друг другу рабочее дерево.
2. Проверяет окружение: каталог, `.git`, `.env`, docker, compose v2.
3. **Проверяет диск.** Выше 80% — сначала чистит висячие образы и build-cache
   старше недели. Выше **85%** — деплой отменяется до сборки, код выхода 20.
4. `git fetch` + `git reset --hard` на коммит из workflow. Локальные правки на
   сервере перечисляются в логе и отбрасываются.
5. Собирает образ **только если** в диффе есть `src/`, `Dockerfile`,
   `pyproject.toml` или `uv.lock`. Правка доков или compose пересборки не
   требует.
6. `docker compose up -d --remove-orphans`.
7. Здоровье: ждёт 20 секунд и проверяет, что все пять контейнеров `running`,
   счётчик рестартов не вырос (то есть ничего не падает по кругу), а
   healthcheck Postgres не `unhealthy`. Иначе код выхода 40.
8. Уборка: висячие образы и build-cache старше недели. Тома не трогаются
   никогда.
9. Печатает `docker compose ps`, `free -m`, `df -h` и последние 30 строк логов.

Коды выхода скрипта: `10` окружение не готово, `15` замок занят (workflow
повторит до трёх раз), `20` нет места, `40` контейнеры не в порядке.

## 6. Ручной деплой и диагностика

```bash
ssh <алиас-сервера>
cd /var/www/sniffer

bash infra/deploy.sh --check          # только проверки, ничего не меняет
bash infra/deploy.sh                  # обычный деплой на origin/master
bash infra/deploy.sh --force-build    # пересобрать образ принудительно
bash infra/deploy.sh /var/www/sniffer <sha>   # на конкретный коммит
```

Через `bash`, а не `./`: файл коммитился с Windows, где git не хранит бит
исполнения, и на сервере он может приехать без `+x`. Чтобы это починить один
раз навсегда — `git update-index --chmod=+x infra/deploy.sh` в репозитории.
Workflow это не касается: он запускает скрипт через `bash`.

Логи и состояние:

```bash
docker compose logs -f --tail 100 bot
docker compose logs --since 30m worker
docker compose ps
docker stats --no-stream $(docker compose ps -q)
```

## 7. Откат

**Штатный путь — `git revert` и обычный пуш.**

```bash
git revert <sha> && git push
```

Тот же конвейер прогонит quality и раскатает откат. Так состояние сервера
остаётся равным состоянию репозитория.

**Срочный путь**, когда ждать CI нельзя:

```bash
ssh <алиас-сервера> '/var/www/sniffer/infra/deploy.sh /var/www/sniffer <предыдущий-sha>'
```

После этого всё равно сделать `git revert` в `master` — иначе следующий же
деплой вернёт поломку, и это будет выглядеть как «само сломалось».

**Чего откат кода не чинит: схему БД.** `001_init.sql` выполняется только на
пустом томе. Любое изменение схемы применяется руками через `psql`, и откат
кода его не отменяет — обратную миграцию надо писать отдельно. Пока
миграционного механизма в проекте нет; когда появится, это место придётся
переписать.

## 8. Диск заполнен

Симптом: деплой упал с кодом 20 и сообщением про занятость выше 85%.

```bash
df -h /
docker system df
du -xh --max-depth=1 /var/lib/docker | sort -h | tail
```

Чистить по возрастанию агрессивности:

```bash
docker builder prune -f --filter until=24h      # кэш сборки, обычно он и виноват
docker image prune -f                           # висячие образы
docker image prune -a -f --filter until=336h    # образы старше 14 дней
docker container prune -f                       # остановленные контейнеры
journalctl --vacuum-size=200M                   # системные логи
```

Чего **не делать никогда**:

- `docker volume prune` — снесёт тома Веры и Степана вместе с базами.
- `docker compose down -v` — то же самое, но точечно и на проде. 20 июня 2026
  этой командой уже стёрли рабочий том Степана.
- `docker system prune -a` без разбора — выкинет образы, которыми пользуются
  соседние стеки, и следующая их сборка займёт диск заново.

Порог 85% можно временно поднять переменной `DISK_LIMIT_PCT`, но это ровно то
решение, из-за которого сборка потом падает на середине и оставляет битые
слои. Сначала освободить место.

## 9. Память кончилась

Признаки: контейнер перезапускается сам, `docker compose ps` показывает
растущий счётчик рестартов, деплой падает с кодом 40.

```bash
docker inspect -f '{{.Name}} OOMKilled={{.State.OOMKilled}} restarts={{.RestartCount}}' \
  $(docker compose ps -q)
dmesg -T | grep -i -E 'oom|killed process' | tail -20
free -m
```

Потолки задаются в `docker-compose.yml` и переопределяются из `.env`:

```
SNIFFER_MEM_POSTGRES=384m
SNIFFER_MEM_COLLECTOR=320m
SNIFFER_MEM_WORKER=384m
SNIFFER_MEM_BOT=256m
SNIFFER_MEM_NOTIFIER=192m
```

Потолок ограничивает RAM, но не своп: docker по умолчанию разрешает
контейнеру ещё столько же свопа сверх лимита. Если свопа свободно
около 1.1 ГБ, поэтому потолки защищают от утечки, но не от медленного
переползания в своп. Если это станет проблемой — добавить каждому сервису
`memswap_limit`, равный `mem_limit`: тогда контейнер будет убит в своём
cgroup, а не утащит машину в тряску. Это осознанный размен «наш процесс падает
чаще» на «соседние стеки живы», и делать его надо явно, а не по умолчанию.

Порядок урезания, если памяти на машине не хватает: сначала `worker` (он
пиковый, а не постоянный), затем `notifier`, затем `collector`. `postgres` не
резать ниже 256 МБ — начнёт мести по диску вместо кэша. Если и это не
помогает, вопрос уже не в потолках: значит, на машине слишком много стеков, и
решение — вынести SnifferBot на отдельную машину, а не отжимать по десять
мегабайт.

## 10. Бэкап

```
0 4 * * * cd /var/www/sniffer && docker compose exec -T postgres pg_dump -U sniffer sniffer | gzip > /var/backups/sniffer-$(date +\%F).sql.gz && find /var/backups -name 'sniffer-*.sql.gz' -mtime +7 -delete
```

Ротация на семь дней обязательна: на диске 10 ГБ свободного, и бэкапы без
удаления старых сами приведут к отказу деплоя по разделу 8.

**Бэкап, который ни разу не восстанавливали, — это не бэкап.** Раз в месяц
поднять дамп в отдельный контейнер и убедиться, что он читается.

## 11. Что осталось незакрытым

- Пароль Postgres по умолчанию `sniffer`, если не задать `POSTGRES_PASSWORD`.
- Деплой ходит под `root`; отдельного пользователя `deploy` нет.
- Падение деплоя никуда не уведомляет — узнать можно только по вкладке
  Actions. У Веры для этого есть job, который пишет владельцу в Telegram.
- Механизма миграций нет: схема меняется руками через `psql`.
- Сборка идёт на сервере. Перенос в GitHub Actions + GHCR снял бы с машины и
  пик памяти, и build-cache.
