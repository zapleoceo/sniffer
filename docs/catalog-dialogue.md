# Каталог в клиентском диалоге

`CATALOG_MODE` выбирает путь поиска; по умолчанию `legacy`, существующий поиск
и запись live-находок не меняются. `catalog` читает новый каталог через
`agent_app.main.search_request`, без запасного live-поиска при ошибке.
Карточки рисует `bot.cards` из записей приложения, не из текста модели.
Статус из сервиса показывается перед карточками или вместо обычного «ничего
не нашлось»: отсутствие данных не объявляется отсутствием подходящих товаров.

`pilot` включает новый путь только для `CATALOG_PILOT_USER_IDS=[7,12]`.
Это внутренние `users.id` базы, **не Telegram ID**. Пустой список не включает
никого. Неверный режим отклоняется настройками при запуске. В `shadow` клиент
получает только legacy-результат; новый поиск выполняется с
`allow_collection=False`, ограничен пятью секундами и не создаёт заданий.
Сравнение пишет только количества в лог, не тексты и персональные данные.
Теневой замер может добавить до пяти секунд к выдаче; исключение не меняет
ответ legacy, отмена запроса корректно прерывает выполнение.

Граница получает `user_id`, корень запроса и версию из загруженного `Dialogue`.
Не из текста пользователя, аргументов модели или callback без проверки владельца.
Сервис повторно проверяет владельца/версию в базе перед выдачей или постановкой
сбора. Локально несовпадающий владелец отклоняется до вызова любого искателя.

Существующая search-first воронка и `/requests` сохраняются. Если категория
понятна, «нужен скутер» сразу запускает поиск: город берётся из запроса или из
`DEFAULT_CITY`, а бюджет клиент добавляет после первой выдачи. До поиска бот
задаёт не более одного блокирующего вопроса — только о неизвестной категории.
Лишнего вопроса об автомате нет: скутер уже означает автоматическую коробку.

Подтверждение перед поиском называет цель, распознанную из намерения клиента:
покупателю ищутся подходящие предложения, арендатору — варианты аренды,
продавцу — покупатели, владельцу жилья — арендаторы. Поэтому «продам» и «сдам»
не выглядят как поиск товара для самого клиента.
В той же строке повторяются названные критерии: коробка и направление объёма
двигателя для мотобайка, число комнат и предпочтение по мебели для жилья.
Мебель остаётся мягким сигналом ранжирования, а не обязательным отсевом.
Подтверждение даёт исправить неверный разбор сразу, не добавляя анкету перед
первой выдачей.

Выбор старого запроса сохраняет его отдельный корень и историю; новые критерии
создают новую версию именно выбранного запроса. Кнопки повторного поиска,
редактирования и мониторинга остаются прежними. Настройки меняют маршрут ответа,
но сами по себе не переключают владельца публикации/уведомлений: это отдельный
контролируемый этап развёртывания.

Проверка: `tests/test_catalog_dialogue.py` — режимы, идентичность/версия,
нулевые вызовы при чужом владельце, shadow без записи и без подмены карточек,
ошибка/отмена, отсутствие live-fallback и симуляция скутера без вопроса о бюджете.
`tests/test_bot_dialog.py` проверяет существующую воронку, несколько запросов,
выбор/редактирование, кнопки, журнал и подписки. Все модели и сеть подменены.

Отдельный прогон `python -m sniffer.simulation --catalog --replies` проводит
фиксированных RU/EN/VI-клиентов через настоящий путь
`Conversation → CatalogFinder → CatalogSearch`. Поисковая подделка не получает
готовый паспорт: она принимает только серверные `user_id`, корень и версию,
повторно находит ровно эту запись в `MemoryStore`, строит production
`collection_scope`, выбирает противоположную сторону сделки и запускает
`rank_items`. Legacy finder в таком прогоне аварийный, поэтому незаметный
fallback не может сделать отчёт ложно зелёным. В сценариях есть покупка,
аренда, продажа, сдача, транспорт, жильё, уточнение цены, смена темы и один
действительно необходимый вопрос о неизвестной категории. Обычный запуск без
`--catalog` по-прежнему использует прежний набор и прежний вердикт.

Живой PostgreSQL-контур проверяет отдельный smoke
`tests/test_catalog_postgres_smoke.py`: настоящий `PassportStore` сохраняет
запрос, опубликованное через реальные репозитории наблюдение читается цепочкой
`Conversation → CatalogFinder → search_request → ReadAgent/MCP → MainGateway`,
после чего `render_cards` строит ответ только из проверенной записи. На внешних
границах подменены AIbroker, курс USD/VND и фабрика тестовых сессий/настройки;
детерминированный parser заменяет модельный intake, а scoped test-wrapper
публикует фикстуры перед вызовом настоящего `search_request`. Рядом сохраняется
точно подходящее, но неопубликованное наблюдение и несколько опубликованных
противоречий: ни одно не имеет права попасть в MCP-результат/карточку. Без
`TEST_DATABASE_URL` тест явно пропускается; в CI он работает с pgvector
PostgreSQL, как остальные DB-тесты.
