# Универсальный поиск: единый контур данных

Состояние на 02.09.2026: разовый поиск, накопленный PostgreSQL-каталог и
подписки используют одну модель карточки. Документ фиксирует реализованный
контракт и его проверку; предполагаемые будущие части названы отдельно.

## Контур

```text
Telegram history → raw_messages → gate/extract → listings ┐
                                                           ├→ archive source → общий rank/verifier → бот
Chotot/Telegram live → общий rank/verifier → listings cache┘

listings → matcher → notifications + outbox → notifier → Telegram Bot API
```

`listings.source + listings.external_id` — идентичность находки независимо от
того, пришла она из live-поиска или собственного архива. Повторный поиск не
создаёт вторую карточку. Telegram-архив дополнительно связан с
`raw_messages.id`; live-карточка может не иметь `raw_message_id`.

Находка без даты не кэшируется. Подставить время текущего запроса означало бы
выдать старое объявление за свежее при следующем поиске.

## Семантика сделки

Паспорт описывает сторону клиента, карточка — автора объявления:

| Клиент | Искомое объявление |
|---|---|
| `buy` | `sell` |
| `rent` | `rent_out` |
| `sell` | `wanted` |
| `rent_out` | `wanted` |

Преобразование единое (`domain.passport.counterpart_deal_type`) и используется
архивным поиском и подписками. Прямое сравнение `buy == sell` запрещено: оно
оставляло реальную подписку навсегда пустой.

## Идемпотентность и конкурентность

- collector вставляет сырьё через `ON CONFLICT (chat_tg_id, msg_id) DO NOTHING`;
- raw-сообщение берётся worker через `FOR UPDATE SKIP LOCKED` по одной строке;
- проверка кросспоста сериализуется транзакционным advisory lock по
  нормализованному `text_hash`;
- live-карточка вставляется через `ON CONFLICT (source, external_id) DO NOTHING`;
- подписки блокируются `FOR UPDATE SKIP LOCKED`, поэтому два matcher не могут
  одновременно занять один дневной лимит;
- `notifications(subscription_id, listing_id)` остаётся дедупом;
- outbox берётся notifier через `FOR UPDATE SKIP LOCKED`.

Доставка Bot API имеет семантику **at least once**. Падение после успешного
HTTP-вызова и до commit может дать повтор: Bot API не принимает наш
идемпотентный ключ. Обещать exactly once здесь нельзя.

## Курсор подписки

`since_listing_id` — неизменяемая точка начала подписки.
`scan_listing_id` — последняя реально рассмотренная карточка. Он движется и по
неподходящим результатам. Без второго курсора matcher постоянно перечитывал
первые 100 строк и никогда не доходил до новых.

Суточный слот занимает `notifications.created_at` при постановке в очередь.
`notifications.sent_at` появляется только после успешной доставки. Неудачная
доставка не позволяет параллельному matcher превысить лимит, но в аналитике не
считается отправленной.

## Digest и тихие часы

- `mode=instant`: отправка сразу, кроме тихих часов;
- `mode=digest`: ближайшие 18:00 Asia/Ho_Chi_Minh;
- интервал `quiet_from → quiet_to` переносит сообщение на конец интервала;
- ночной интервал, например 22:00–08:00, корректно проходит через полночь.

## Диалог и достижимый минимум вопросов

Абсолютный потолок до первой выдачи — один вопрос. Если категория уже названа
или однозначно следует из модели, вопросов нет. Если искать ещё нечем, вопрос
выбирает поле с максимальной полезностью; после ответа бот ищет, а не начинает
анкету заново.

Симулятор запускается командой:

```bash
uv run python -m sniffer.simulation
```

Релевантность теперь обычный обязательный тест, не `xfail`.

## Что ещё не реализовано

`search_tsv` и `embedding` остаются резервом схемы: текущий архивный поиск
использует структурные поля и общую детерминированную проверку текста. До
замера на достаточно большом каталоге включать полнотекстовый или векторный
порог нельзя — неизмеренный порог уменьшает полноту незаметно.

Полное LLM-извлечение продавца, grounding каждого атрибута и проверка живости
архивных карточек остаются следующей ступенью. Минимальный worker уже извлекает
явно написанные модель, марку, коробку и объём детерминированным разбором.
