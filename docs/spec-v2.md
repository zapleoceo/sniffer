# SnifferBot — спецификация v2

> Дополняет [architecture.md](architecture.md). Фиксирует три требования,
> которых в v1 не было: **поиск не ограничен источниками**, **обязательный
> проверяльщик**, **публичный бот с монетизацией**.

## 0. Что меняется против v1

| Требование | Было в v1 | Стало в v2 |
|---|---|---|
| Источники | курируемый список 20–30 чатов, Telethon | агент-планировщик + реестр адаптеров: Telegram, Chotot, веб, опционально FB |
| Границы поиска | заданы списком чатов | заданы **только паспортом запроса**; чем искать — решает агент |
| Проверка выдачи | нет | **verifier** — отдельная ступень и отдельный процесс |
| Аудитория | не определена | публичный бот, задел под монетизацию и антиспам |
| Юзербот | номер не выбран | **отдельный номер**, личный аккаунт не используется |
| Хост | Oracle Free | Hetzner `195.201.31.49` — **общая машина** с Верой и Степаном, изоляция логическая |

## 1. Изоляция от Веры — контракт

Пересечение ровно одно — **машина**. На всех остальных слоях пересечений нет, и
это проверяемое требование, а не намерение.

Физической изоляции больше нет: выделенный сервер `135.181.87.140` удалён
2026-08-31, SnifferBot переехал к Вере и Степану. Держится изоляция теперь на
именах compose-проекта и на потолках памяти (`mem_limit`) — OOM-killer выбирает
жертву по всей машине, а не по проекту, поэтому потолок на каждом контейнере
обязателен.

| Слой | Вера | SnifferBot |
|---|---|---|
| **Сервер** | Hetzner `195.201.31.49` | **та же машина** (4 vCPU / 7.6 ГБ / 75 ГБ) |
| Репозиторий | `zapleoceo/muai` | `zapleoceo/sniffer` |
| Каталог на сервере | `/var/www/vera3` | `/var/www/sniffer` |
| Compose-проект | `vera3` | `sniffer` |
| Postgres | контейнер `vera3-postgres`, БД `vera` | контейнер `sniffer-postgres`, БД `sniffer` |
| Порт БД на хосте | **5433** | **5434**, только `127.0.0.1` |
| Docker-сеть | `vera3_default` | `sniffer_default` |
| Telegram-аккаунт | личный Димы | **отдельный номер** |
| LLM | AIbroker, ключ проекта `vera` | AIbroker, **свой project-key со своим дневным cap** |

Изоляция **логическая**: машина одна. Переезд Веры отменён — на её IP завязаны
клиентские конфиги WireGuard и ссылки MTProxy, которые живут на чужих
устройствах и молча умрут при смене адреса, — а выделенный сервер SnifferBot
удалён 2026-08-31, поэтому приехал он.

AIbroker физически сосед, но обращение к нему идёт через `aib.zapleo.com`. Она безопасна при условии отдельного project-key: бот
физически не может выесть квоту Веры, потому что cap стоит на ключе.
Требование симметричное — Вера так же не может выесть квоту бота.

## 2. Агент поиска — как снимается ограничение по источникам

Формулировка требования: *система ограничена только запросом, что искать, но не
тем, чем искать*. Значит список источников не может быть зашит в код воронки.

### 2.1 Структура

```
формулировка клиента
      │
      ▼
┌─────────────────┐   намерение, категория, город, бюджет, бренд
│  intake         │   один LLM-вызов, при любом отказе — разбор по правилам
└────────┬────────┘
         ▼
паспорт запроса
      │
      ▼
┌─────────────────┐   решает: какие источники, какие запросы, на каком языке
│  search planner │   один LLM-вызов, план по strict json_schema
└────────┬────────┘
         │  план = список задач {source, query, params}
         ▼
┌──────────────────────────────────────────────────────────┐
│  реестр адаптеров — таблица sources в БД, не константы   │
│                                                          │
│  telegram_groups    messages.search по известным чатам   │
│  telegram_discover  вне этой таблицы: пишет в реестр      │
│                     чатов, а не отдаёт карточки (4.5)     │
│  chotot             gateway.chotot.com, публичный JSON   │
│  web                SearXNG (ссылки) + Firecrawl (текст) │
│  facebook           выключен по умолчанию, см. 6.3       │
└────────┬─────────────────────────────────────────────────┘
         │  сырые находки
         ▼
   воронка v1: гейт → prefilter → structured → listings
         │
         ▼
   ┌───────────┐
   │ verifier  │  раздел 3
   └───────────┘
```

Добавить источник — это строка в таблице `sources` плюс класс адаптера с одним
методом `search(query, params) -> list[RawItem]`. Планировщик видит доступные
источники из БД и сам решает, какие уместны для этого паспорта. Ни воронка, ни
бот про конкретные источники не знают.

### 2.2 Что решает планировщик

На входе паспорт, на выходе план по строгой схеме:

```json
{
  "tasks": [
    {"source": "telegram_groups", "query": "инжектор", "lang": "ru", "priority": 1},
    {"source": "telegram_groups", "query": "блюкарт", "lang": "ru", "priority": 1},
    {"source": "chotot", "query": "xe ga", "params": {"cg": 2020}, "priority": 1},
    {"source": "web", "query": "Honda Lead cu Nha Trang", "lang": "vi", "priority": 2}
  ],
  "reasoning": "категория motorbike, город nha_trang; вьетнамский сегмент в TG отсутствует, локальный рынок берём с Chotot"
}
```

Планировщик обязан **расширять запрос синонимами, жаргоном и переводами**, а не
брать слова клиента буквально. Обоснование — раздел 7, наблюдение про «инжектор».

#### Словарь рынка — данные, а не ветвление

Слова живут в `search/market_terms.py`, доступ к ним и профили источников — в
`search/vocabulary.py`. Знание одно, потребителей два: промпт отдаёт его модели
как отправную точку, фолбэк строит из него готовый план. Продублировать его в
обоих местах — значит однажды поправить только одно.

Слои не взаимозаменяемы:

| Слой | Что это | Пример |
|---|---|---|
| `CATEGORY_TERMS` | как называют предмет | `скутер`, `tay ga`, `scooter` |
| `MOTORBIKE_MODELS` | модель → марка, тип кузова, написания (отдельный файл `motorbike_models.py`) | `lead` → honda, `tay ga`, «lead», «лид» |
| `INTENT_TERMS` | глагол сделки, вывернутый по намерению | клиент покупает → `продам`, `bán` |
| `ATTRIBUTE_TERMS` | как значение атрибута звучит на языке рынка — **для прозы** | `transmission=automatic` → `автомат`, `вариатор`, `tay ga` |
| `BOARD_ATTRIBUTE_TERMS` | измеренное подмножество того же, безопасное как `q` у структурной доски | **пусто целиком** — замер не прошло ни одно слово свойства (4.1.1) |
| `BOARD_SAFE_QUERIES` | гейт на ЛЮБОЙ `q` к источнику, ищущему полями, включая присланный моделью | пусто; неизмеренный текст модели к доске не уезжает |
| `JARGON` | чем продавец хвастается и что покупатель проверяет | `инжектор`, `блюкарт`, `на ходу`, `cà vẹt`, `xe zin` |

`JARGON` — отдельный слой, а не приставка к предмету: смысл его в том, что
предмет продавец вообще **не назвал**. Поэтому «инжектор» уходит отдельным
запросом.

`BOARD_ATTRIBUTE_TERMS` — тоже отдельный слой, и он не «дубль на всякий случай».
«Слово для чата» и «слово, безопасное как `q` у структурной доски» — разные
вещи, и по самому слову этого не видно: доска складывает `q` со своими фильтрами
через **И**, поэтому слово о свойстве не уточняет фильтр, а **гасит его в ноль**.
Замер: `motorbiketype=3` даёт 12 объявлений, он же с `q='côn tay'` — ноль
(4.1.1). Клиент, попросивший механику, увидел бы пустоту и прочёл её как «на
рынке нет». Поэтому в `q` доски попадает только то, что стоит в этой таблице, а
попасть в неё можно лишь с числом замера.

Слова документов лежат в одной таблице `PAPERS_WORDS` и оттуда попадают и в
`ATTRIBUTE_TERMS.papers`, и в `JARGON`: знание одно — «блюкарт» это и значение
атрибута, и то, чем продавец хвастается, — а две копии однажды разъедутся.

Тот же словарь читает и бесплатный гейт воронки. `vocabulary.category_hints(text)`
отвечает, какие категории названы в тексте — словом (`CATEGORY_TERMS`), маркой
(`MOTORBIKE_BRANDS`) или моделью (`motorbike_models`), — и гейт
(`pipeline/gate.py`) получает эту функцию внедрением от воркера, своей копии
списка марок и моделей не держит. А держал: тот список разошёлся с этими
таблицами — `sym`, `kymco`, `lead`, `attila` здесь есть, а у гейта их не было, и
лот, названный одной моделью, отсеивался как «без категории» ещё до базы. Это тот
же класс дефекта, что отделение модели от марки чинило в поиске, только на входе
воронки; знание одно, разъезжаться нечему.

**Профиль источника** (`SOURCE_PROFILES`) — три факта, каждый выведен из
провала, а не из вкуса:

| Поле | Что решает |
|---|---|
| `langs` | на чём пишут продавцы именно здесь |
| `free_text` | объявление написано прозой (тогда жаргон работает) или собрано из полей (тогда нет) |
| `city_in_query` | вклеивать ли город в текст запроса |

Ни планировщик, ни фолбэк не знают слова `chotot`: они спрашивают у профиля.
Незнакомый источник получает `DEFAULT_PROFILE` — все языки рынка, жаргон и
город: без записи в таблице новый адаптер работает вслепую, но работает.

**Правила пополнения.** Словарь — это измеряемая вещь, и отличать замер от
догадки в нём обязательно, иначе через полгода он станет догадкой целиком.

1. Новый город, категория, синоним, жаргонное слово — строка в таблице
   `market_terms.py`. Ни одного `if` по названию города, категории или
   источника нигде появиться не должно.
2. Новый источник — строка в `SOURCE_PROFILES`. Правка планировщика, фолбэка
   или промпта под конкретный источник означает, что абстракция протекла.
3. У каждого слова помечено, чем оно подтверждено: **замер** (живой запрос,
   число в комментарии), **текст объявлений** (слово встречено в реальной
   выдаче) или **полевые заметки** (проверено человеком, кодом не измерено).
   Слово без пометки добавлять нельзя.
4. Слово, дающее ноль на своём источнике, из словаря **убирается**, а не
   остаётся «на всякий случай»: оно тратит задачу из бюджета плана (12 задач,
   2.3) и создаёт вид работающего поиска. Так ушло `xe ga` — см. 4.1.1.
5. Слово, дающее всю выдачу целиком (`xe máy`, `chính chủ` на Chotot),
   фильтром не является и предметом считаться не должно.
6. **Правила 4 и 5 относятся ко всем слоям, а не только к `CATEGORY_TERMS`.**
   Слово атрибута — такое же слово: `côn tay` (`transmission=manual`) даёт ноль,
   `cà vẹt` (`papers=blue_card`) даёт ноль, `chính chủ` (`condition=good`) даёт
   всю выдачу. Поэтому в `q` структурной доски они не идут, а в чат идут — там
   это единственный инструмент. Разница выражена таблицей
   (`BOARD_ATTRIBUTE_TERMS`), а не комментарием: комментарий не проверяется
   тестом, таблица проверяется.
7. Атрибут, для которого у источника ЕСТЬ структурное поле, едет полем и
   словом не дублируется. Замер: `q='tay ga'` и `motorbiketype=1` дают одни и те
   же 41 объявление, `q='honda'` и `motorbikebrand=1` — одни и те же 26. Поле
   не зависит от написания, которое прислал клиент, и не гаснет о чужое слово.
8. Атрибут, для которого поля НЕТ (`papers`), в текст не превращается, если его
   слово не прошло замер: лучше отдать полную выдачу и отсечь ранжированием,
   чем показать пустоту. `q` при этом остаётся пустым — это законная задача, а
   не сломанная. У `condition` поле ЕСТЬ (`condition_ad`: 58 б/у и 1 новое из
   59), поэтому им распоряжается правило 7, а не это.
9. **Число слова обязано быть своим.** Слово, чьё число совпадает с числом его
   же измеренной части, не фильтр — оно не добавляет к этой части ничего. Так
   отбраковано `xe mới`: 8 из 59, то есть не ноль и не вся выдача, прежним
   правилам 4 и 5 оно удовлетворяло, — а это оказалось число слова `xe` (те же
   восемь id), «mới» отдельно даёт все 59, и все восемь помечены б/у при
   запросе НОВОГО. Проверять «значит ли слово то, что написано» по одному числу
   нельзя; сверять число фразы с числом её части — можно, и это проверяет код
   (`is_board_safe`), а не памятка.
10. **`q` от модели проходит тот же гейт, что наш словарь.** У источника с
    `free_text=False` присланный моделью текст выбрасывается, если его нет в
    `BOARD_SAFE_QUERIES` (сейчас пусто) — а задача остаётся: фильтры отбирают,
    клиент получает выдачу вместо пустоты. Иначе весь замер защищал бы только
    фолбэк, то есть путь, который работает реже всего.
11. **Имя модели — не исключение из правил 7 и 10.** Оно выглядит исключением:
    «Honda Lead» это настоящий текст объявления, а не слово о свойстве. Но поля
    модели у структурной доски НЕТ (`motorbiketype`, `motorbikecapacity`,
    `motorbikebrand` — и всё, 4.1.1), поэтому имя в `q` не заменяет
    отсутствующий фильтр, а гасит те, что есть. Источнику со свободным текстом
    модель уходит первым запросом — там продавец называет байк именно так, — а
    выдача доски отбирается по модели уже у нас (2.7). Промпт планировщика
    называл модель исключением и тем самым спорил с кодом, который её всё равно
    выбрасывал: расхождение снято в пользу замера.

#### Атрибуты паспорта доезжают до источника фильтром, а не словом

Свойство предмета сильнее любого синонима: замер по Нячангу — общий запрос по
категории даёт 71% настоящих скутеров-автоматов, `motorbiketype=1` даёт 100%
(4.1.1). Поэтому `transmission=automatic` обязан становиться **фильтром**.

Разделение ответственности при этом сохраняется полностью:

```
паспорт ──► context_params() ──► нейтральные факты в params:
                                 attributes {transmission: automatic}
                                 budget {max, currency}
                                        │
                                        ▼
                          адаптер переводит в СВОИ имена полей:
                          chotot: transmission=automatic → motorbiketype=1
                                  engine_cc=125          → motorbikecapacity=3
                                  year_min=2018          → regdate=2018
                                  brand=Vespa            → motorbikebrand=3
```

Планировщик про поле `motorbiketype` не знает и знать не должен — иначе каждый
новый источник правил бы планировщик. Адаптер берёт понятное и **молча
игнорирует остальное**, поэтому едут все заполненные атрибуты, а не только те,
что кто-то умеет отбирать.

Следствие, ради которого это и сделано: фильтр ставится **детерминированно, без
участия модели**. Модель может ошибиться, упасть или быть недоступной — коробка
передач всё равно превратится в `motorbiketype`.

Бюджет уходит в фильтр цены только когда он **уже в донгах**. Курс USD→VND
намеренно не захардкожен: протухший курс превращает верный фильтр в неверный
молча. До появления источника курса валютный бюджет отсекается ранжированием.

**Это не редкий случай, а обычный, и потому это задача P1, а не «когда-нибудь».**
Клиент почти всегда называет бюджет в долларах («до 400»), а Chotot принимает
только донги — значит ценовой фильтр доски пуст не иногда, а в большинстве
запросов, и вся отсечка по цене падает на ранжирование уже полученной выдачи.
Замер показывает, сколько при этом теряется точности: `motorbiketype=1` даёт 41
объявление, он же с `price=0-25000000` — 30. Нужен источник курса с кэшем на
сутки и явной пометкой в карточке, по какому курсу считали.

Три детали реализации, которые заметны снаружи:

- **`params` в ответе модели приезжают парами строк** `[{key, value}]` и
  разворачиваются в объект при разборе. Strict `json_schema` не допускает
  объект со свободными ключами — провайдеры такое отклоняют.
- **`enum` источников собирается из реестра**, а не пишется в промпт руками.
  Модель физически не может назвать источник, под который нет адаптера.
- **Язык выбирается по источнику, а не по языку клиента.** Русский запрос к
  вьетнамской доске вернёт ноль. Город в текст запроса подставляется только для
  источников, ищущих по всему интернету: в чате Нячанга слово «Нячанг» в
  объявлениях не пишут, и в поисковой строке оно только режет выдачу.
- **Жаргон уходит только источникам со свободным текстом.** Замер по Chotot:
  «скутер» 0, «инжектор» 0, «блюкарт» 0 объявлений. Структурная доска собирает
  объявление из полей, жаргона там нет ни в одном, и такая задача просто
  пропадает из бюджета плана впустую.
- **У структурной доски `q` пуст, и это правильный запрос.** Отбор делают поля;
  текст туда пропускает только `BOARD_SAFE_QUERIES`, где сейчас пусто, — и гейт
  стоит на обоих путях, нашем и модельном (2.2, правило 10). Глагол сделки
  приставкой к слову — приём прозы: замер — «nguyên zin» 59, «bán nguyên zin» 0;
  «xe mới» 8, «bán xe mới» 0.

### 2.3 Бюджет поиска

Свобода источников не означает свободу расходов.

| Параметр | Лимит |
|---|---|
| задач в плане | 12 |
| чатов на один `messages.search` | 10, иначе FloodWait |
| запросов к SearXNG | 5 |
| запросов к Chotot | 5 |
| страниц через Firecrawl | 10 |
| общий таймаут плана | 90 с |
| LLM на запрос | 1 планировщик + 1 на пачку извлечения + 1 на карточку в верификаторе |

Что не уложилось в таймаут — отдаётся частично: пять карточек за минуту
полезнее двадцати за десять.

### 2.4 Фолбэк планировщика

Недоступность брокера не должна означать мёртвого бота. При `BrokerError`,
исчерпанном дневном cap, таймауте или невалидном ответе строится
детерминированный план из словаря рынка: предмет на каждом языке источника плюс
глагол сделки, вывернутый по намерению (клиент покупает — ищем «продам», «bán»,
«for sale»).

Фолбэк проходит **ту же нормализацию**, что и ответ модели. Иначе он тихо
разъедется с боевым путём и сломается ровно тогда, когда остаётся единственным
рабочим. «Та же» означает конкретный список, а не пожелание:

- тот же словарь рынка и те же профили источников (2.2) — язык по источнику,
  жаргон только свободному тексту, город только «всему интернету»;
- тот же `context_params()`, поэтому атрибуты паспорта превращаются в
  структурные фильтры источника и в фолбэке — без участия модели;
- тот же запрет на слово в `q` структурной доски: слова предмета и атрибутов
  фолбэк берёт из `BOARD_ATTRIBUTE_TERMS`, то есть из замера, и сейчас оставляет
  `q` пустым всегда — замер не прошло ни одно слово свойства. Это не оптимизация, а корректность: `q` складывается с фильтром
  через И, и `motorbiketype=3` + `q='côn tay'` даёт ноль вместо 12 (4.1.1);
- тот же `SearchPlan.from_tasks()`: дедуп, обрезка **по приоритету** и потолок
  задач. Обрезка по приоритету, а не по порядку перечисления, — чтобы главный
  запрос каждого источника выжил, иначе источник выпадает из плана целиком.

Проверяется это тестом, который сравнивает **результат `build_params()`** для
задачи фолбэка и для задачи из плана модели по одному и тому же паспорту, и
делает это по КАЖДОМУ значению атрибутов мотобайка из `docs/passport.md`.
Сравнения одних `params` не хватало: расходился именно `q`, а его в `params`
нет — так дефект и прожил ровно до первого клиента с механикой.

Флаг `is_fallback` — поле плана, а не пометка в тексте: доля фолбэков это
операционная метрика, по ней видно, что брокер лежит.

### 2.5 Разбор формулировки клиента

Паспорт собирается из свободного текста тем же правилом, что и план: один вызов
LLM, а при любом отказе — детерминированный разбор регулярками (намерение,
категория, город, бюджет, бренд). Когда ключа брокера нет вовсе, модель не
вызывается: ждать таймаут на каждом сообщении клиента дороже, чем сразу
ответить по правилам.

Ответ модели не заменяет разбор целиком, а **дополняет** его: поле, которое
модель оставила пустой строкой, берётся из правил. Иначе «до 400 долларов»
терялось бы всякий раз, когда провайдер поленился заполнить бюджет.

Две вещи, которые правила знают про этот рынок:

- **«Ищу» и «нужна» намерением не считаются.** Они говорят, что клиент ищет, но
  не говорят, покупает он или снимает. Различает их категория: квартиру в
  Нячанге снимают, скутер берут себе.
- **Миллионы без валюты — это донги.** Рынок двухвалютный, и «до 10 млн»
  однозначно, а «до 400» — доллары. Порог: сто тысяч.

Разбор по правилам — не запасной путь, а базовый: он отвечает за секунды и без
единого вызова модели.

### 2.6 Исполнение плана

План исполняет отдельный слой, знающий об источниках ровно два имени — из плана
и из реестра. Бюджет из 2.3 применяется здесь: не больше пяти запросов на один
источник, 90 секунд на весь план.

- Запросы к одному источнику идут **последовательно**: параллелить обращения к
  одному хосту значит выглядеть как атака там, где мы и так гости.
- Источник, пометивший себя `degraded`, из плана выбывает сразу — остальные
  доигрывают.
- Адаптер, нарушивший контракт и бросивший исключение, теряет только свою
  выдачу; ошибка попадает в лог, клиент получает результаты остальных.
- Не уложившиеся в бюджет задачи снимаются, собранное отдаётся частично.
- Дедуп по `(source, external_id)`, порядок — по свежести: лот без метки
  времени уходит в конец, непроверяемая свежесть свежестью не считается.

### 2.7 Что доходит до клиента — отбор перед показом

Живой отказ 02.09.2026: на «нужен скутер, не мотоцикл, honda lead» бот отдал
Honda Airblade трижды и лот 59-дневной давности. Дефекта было два, и второй
дороже: живой поиск (`search/relevance.py`) только **сортировал**. «Ниже» не
значит «не показан» — показываем мы первые пять, и когда лучшего нет, первыми
пятью оказывается мусор.

**Модель отбирается на нашей стороне, и иначе нельзя.** Структурного поля модели
у Chotot не существует: есть `motorbiketype`, `motorbikecapacity` и
`motorbikebrand` (4.1.1), и марки мало — `motorbikebrand=1` отдаёт все 26 Хонд
Нячанга, среди них Airblade, Vision и Wave. Именем модели в `q` это не
решается: `q` складывается с фильтрами через И и гасит их в ноль (2.2, правило
11). Значит фильтр клиентский — по заголовку и тексту лота, тем же знанием о
написаниях, которым модель узнаётся в запросе клиента.

**Отсев многоступенчатый, и ступени отменяются по-разному.**

| Ступень | Что отсекает | Отменяется, если пусто? |
|---|---|---|
| чужая категория | клиент просил скутер, лот называет себя комнатой | **нет** |
| чужая модель | клиент назвал Lead, лот называет другую известную модель | **нет** |
| чужая марка | клиент назвал Yamaha, лот называет Honda (или её модель) | **нет** |
| чужая коробка | клиент просил автомат, лот пишет «côn tay»/«механика» | **нет** |
| объём вне диапазона | «250 минимум» — лот с cc<250; «до 250» — лот с cc>250 | **нет** |
| чужое число комнат | клиент просил 2 спальни, лот называет студию или 3 спальни | **нет** |
| оффер аренды покупателю | клиент с intent=BUY, лот — прокат («Аренда байков», «/сутки») | **нет** |
| дороже потолка | цена явно выше бюджета (неизвестная цена остаётся) | **нет** |
| совсем старое | лоту больше 28 дней (`LIVE_MAX_AGE_DAYS`) | **да** |

Перед отсевом кросспосты схлопываются (`_dedup`). Один лот приходит в несколько
чатов и переопубликуется с новыми эмодзи, пробелами и переставленными или
задублированными фразами (замер 02.09.2026: «Honda Air Blade 2012» и «SYM
ATTILAVTS 124» по два раза). Точный хэш такое не ловит, поэтому отпечаток — это
множество **содержательных слов** текста плюс `(source, external_id)`: полный
набор минус крошечный закрытый список декоративных приставок (`_SERVICE_WORDS` —
категория предмета «скутер/байк/мотоцикл» и глагол продажи «продам/срочно»; эмодзи
убирает нормализация). Так ловится и **ближний дубль**, где кросспост отличается
ЛИШЬ приставкой: «Скутер SYM ATTILAVTS 124» против «SYM ATTILAVTS 124» — один лот,
а до этой правки — две карточки, которые владелец и видел дублем. Два же разных
лота не схлопываются: год, цена в тексте, пробег, другая модель — содержательные
токены, они в отпечатке и держат лоты порознь, потому что схлопнуться могут только
тексты, различающиеся ОДНИМИ декоративными словами. Отпечаток по тексту, а не
«заголовок + текст»: кросспостят в группах Telegram, где заголовка у поста нет
вовсе (`telegram_mapping`), так что для источника дедупа это прежнее поведение. Из
равных остаётся свежайший — после сортировки он стоит первым.

Марка и коробка — жёсткие факты запроса, а не пожелания для сортировки, и это
стоило починки дважды. Сперва их не было в отсеве вовсе, и на «ямаха» приходил
Honda. Потом ступень добавили, но она молчала: марку лота искали словарём фраз
(`ATTRIBUTE_TERMS`), где слов марки нет вовсе — там свойства (коробка, документы,
состояние), — и марка в тексте лота не находилась никогда (realcheck 03.09.2026,
Honda и Kymco на запрос «ямаха»). Теперь марку и коробку лота читают те же
детекторы, что читают запрос клиента (`detect_brand` / `detect_transmission`), и
марка выводится ещё и из модели: «Exciter» отсеётся на запрос honda, не написав
«yamaha» словом. Дисциплина общая: **неизвестное — не противоречие**, лот без
марки/коробки остаётся; отсекается только явно названное чужое.

Отсюда требование к словарю марок (`MOTORBIKE_BRANDS`): он обязан покрывать
марки, которые РЕАЛЬНО есть на рынке. Неполный список читается как «неизвестная
марка» и молча пропускает чужое — Kymco (147 объявлений в базе) проходил на
«ямаха», пока его там не было. Порог включения — присутствие на рынке, а не
популярность: пять Daelim — это пять чужих карточек на запрос о другом.

**Документы — сигнал ранжирования, а не отсев, и это осознанно.** «блюкарт»,
«с блюкартом», «документы есть» разбираются в `papers=blue_card`
(`intake_rules.detect_papers`, слова из `PAPERS_WORDS`) и поднимают балл лота,
где документы названы, — весь ручной поиск байка держался на блюкарте («без
доков не надо»), а разбор его раньше не читал вовсе. Но в таблицу отсева выше
документы НЕ входят: продавец без блюкарта об этом обычно молчит, «нет
документов» в объявлении почти не пишут, и жёсткий фильтр по документам оставил
бы клиента с пустой выдачей вместо той, где документные лоты просто выше. Кому
нужно строго «только с документами» — это `deal_breaker`, отдельный механизм.

Асимметрия не случайна. Чужая модель — не «похуже», а не тот предмет, то есть
брак выдачи (3.2): пять Airblade на запрос Lead клиент читает как «бот меня не
услышал», а пустой ответ прямо советует, что делать («попробуйте иначе: без
марки, с другим бюджетом»). Возраст — догадка о живости, а не факт о предмете:
лот старше порога всё-таки бывает жив, и карточка честно скажет «объявлению N
дней, могло быть продано» (3.3). Поэтому пустая выдача хуже слабой ровно здесь и
не хуже там.

Для конкретно названной модели теперь требуется положительное подтверждение:
безымянный скутер не доказывает, что это Lead. Неизвестность остаётся допустима
для необязательных свойств, но не подменяет идентичность предмета.

**Категория отбирается на нашей стороне по той же причине, только сильнее.** У
доски категория хотя бы есть (`cg=2020`), у телеграм-чата структурного поля нет
вовсе: поиск там идёт словами, а «продам», «Нячанг», «срочно» стоят в объявлении
о чём угодно. Модельный фильтр такой лот не видит — комната модели не называет,
— и в пятёрку она проходит по свежести. Замер симуляции 02.09.2026 до отсева: из
92 показанных карточек 38 мимо запроса (41%), и почти все — комната
(`room-shared-kitchen`) и велосипед (`giant-escape-3`) в выдаче СКУТЕРОВ. После
отсева — 16 из 80 (20%), и ни одной чужой категории среди них.

Категория лота читается тем же разбором, которым читается запрос клиента
(`search/intake_rules.category_of`), и с тем же выводом из модели. Второй парсер
здесь однажды разошёлся бы с первым, и «комната» значила бы разное с двух сторон
одного поиска. Вывод из модели тут не украшение: «Honda Lead 110 2008» слова
«скутер» не содержит — только имя модели, — и без вывода такой лот проходил в
выдачу студий как «неизвестная категория» (realcheck 03.09.2026). Lead бывает
только у мотобайка, и запрос о жилье его теперь отсекает. Защита та же, что на
стороне запроса: категорию сперва ищут словом, и до модели доходят, лишь когда
слова нет, — иначе «Vision Tower» в адресе квартиры сделал бы её Хондой.

Ступень не отменяется при пустом результате, и это не копия правила о модели, а
тот же вывод из тех же двух фактов. Чужая категория — факт о предмете, прочитанный
из его собственных слов, а не догадка. Показать комнату вместо скутера, когда
скутеров не нашлось, значит вернуть ровно ту жалобу, ради которой отсев и появился.
Подстраховка у ступени внутренняя, а не рядом: лот, чью категорию прочитать НЕ
удалось, чужим не считается — «не смогли прочитать» это не «не подходит». Именно
поэтому отмена не нужна: случай, в котором она спасала бы, ступень и так
пропускает. Плата за это записана честно — лот, который не называет ни категории,
ни знакомой модели, проходит оба фильтра. Прежним примером был `honda-cb200x`, но
после внесения мотоциклетных семейств (03.09.2026) «CB200X» узнаётся как модель
`cb`, и его категория теперь читается из имени — зазор сузился на все лоты,
чью модель пополнившаяся таблица стала узнавать. Свойство остаётся: лот с
ДЕЙСТВИТЕЛЬНО незнакомой моделью и без слова категории пройдёт, — просто в текущем
каталоге такого больше нет.

**Явные противоречия свойств отсекаются.** Другая названная марка, коробка,
объём вне допуска и цена выше явного потолка больше не компенсируются
свежестью. Отсутствующее свойство остаётся неизвестностью; карточка без цены не
считается дорогой. Контрольный прогон после изменения: 28 сценариев, 86
карточек, 0 мимо запроса.

**Объём лота читается из текста, а если там его нет — из МОДЕЛИ.** Направление
несёт запрос (`engine_cc_dir`): «от 250» отсекает лот с cc<250, «до 250» — с
cc>250. Объём самого лота берёт `engine_size.listing_cc_values` — и явное «155cc»,
и голое «nvx 125». Но R15 и Air Blade своё число в тексте часто не пишут, а модель
его знает: когда числа в тексте нет ВОВСЕ, объём подставляется у названной модели
(`relevance._wrong_engine` через `vocabulary.model_engine_cc`), и R15 (155) на «250
минимум» отсеивается, хотя cc в его тексте нет. Живой отказ владельца 02.09.2026:
тот запрос показывал 142 карточки там, где честных 0–2 — в Нячанге мотоциклов
250cc+ почти нет. Дисциплина двойная и прежняя: текст лота ГЛАВНЕЕ модели (явный
«Air Blade 160» — объём того экземпляра, он бьёт справочные 110), а неизвестность
— не противоречие (ни числа в тексте, ни знакомой модели — лот остаётся; электро
объёма не даёт вовсе). Объём модели справочный и огрублённый (одно частое число на
ряд вариантов), поэтому он расставляет лот по КЛАССУ, а не спорит о ±10 см³
([passport.md](passport.md#марка-и-модель--разные-поля)).

**Прокат — не покупка, и покупателю он не идёт.** Клиент с intent=BUY хочет
купить, а «🏍 Аренда мотоциклов», «‼️АРЕНДА БАЙКОВ (сутки/месяц)‼️» — оффер
аренды, сторона автора. Замер 02.09.2026: прокат лез в топ почти любого
покупательского запроса. Отсекается по **явному** предложению аренды, а не по
слову «аренда» где попало: ценник за период («/сутки», «/мес», «сутки/месяц»)
однозначен где угодно, а рамочное слово («аренда», «прокат», «cho thuê», «for
rent» — из `market_terms.RENTAL_STEMS`, где «cho thuê»/«for rent» переиспользованы
из `INTENT_TERMS`) считается прокатом только в заголовке и не под продажей или
отрицанием. Иначе «продам, не для аренды» отсеклось бы как прокат. Отсев только у
покупателя: клиенту с intent=RENT прокат — ровно то, что нужно.

**Объём — диапазон, а не точка.** «250 кубиков минимум», «от 250», «не меньше
250», «250+» несут нижнюю границу: лот с cc<250 противоречит. «до 250», «не
больше 250» — верхнюю. Без слова — точка с полосой допуска ±25%. Направление
несёт паспорт (`engine_cc_dir`, см. passport.md). Живой отказ 02.09.2026: «нужен
мотоцикл 250 кубиков минимум» выдавал 124–125cc скутеры, потому что направление
терялось и разбор считал полосу вокруг 250. Объём ЛОТА при этом читается и голым
числом («nvx 125», «SYM ATTILA 124», «155 abs»), а не только когда рядом стоит
«cc» — но осторожно: число в диапазоне 50–1500, НЕ год (19xx/20xx), НЕ цена
(рядом с млн/к/тр/₫/$/000.000) и НЕ пробег (км). Сомнительное число не читается
вовсе — неизвестный объём не отсекается (`неизвестное ≠ несовпадение`), а точно
прочитанный чужой — отсекается.

**Число комнат отсекается так же, как объём — жёсткий факт, не пожелание.** «2
спальни» против студии — разное жильё, и лот, назвавший ЧУЖОЕ число комнат,
выбрасывается: студия и трёшка на запрос двушки — не «почти», а другой сегмент,
дороже и больше. Совпадение точное. Дисциплина прежняя и та же, что у объёма:
**неизвестное ≠ несовпадение** — лот, число комнат не назвавший, остаётся
(половина объявлений его не пишет, и отсев за молчание опустошил бы выдачу).
Число комнат лота читает `search/rooms.py` тем же знанием, что и запрос клиента.
Тонкость — из замера снимка жилья Нячанга (200 лотов): у агентских объявлений в
подвале стоит меню видов жилья («КВАРТИРЫ И СТУДИИ», 17 лотов из 200), и слово
«студии» там — навигация, а не описание ЭТОГО лота. Поэтому число, ПРИЖАТОЕ к
слову («2 спальни»), главнее разговорного имени, и разговорное читается только
когда прижатого числа нет вовсе: 75 лотов замера с чистой «2 спальни», 35 с «3
спальни», и лишь 2 с конфликтом. Та же дисциплина, что у объёма двигателя: явное
число экземпляра бьёт справочную догадку. **Мебель и вид на море — мягкие
сигналы**, как документы: не отсекают, а поднимают балл лота, где названы
(`_attribute_fit`).

**Порог показа — дата, а не балл, и это главное отличие от подписки.** У
подписки порог балльный (`matching.MATCH_MIN_SCORE = 0.55`), и он там уместен:
у карточки в базе `posted_at` обязателен. В живом поиске он необязателен, а
`freshness` отдаёт ноль ОДИНАКОВО лоту без даты и лоту двухмесячному — балльный
порог отсекал бы не старое, а **неизвестное**, то есть законную карточку с
пометкой «дата публикации неизвестна» (3.3). Поэтому здесь считается возраст, и
только у тех лотов, у кого он вообще известен.

Само число — 28 дней — своё, а не производное от порога живости в 14: там
решается, когда предупредить, здесь — с какого возраста показывать лот вместо
более свежего значит врать. Жёсткость допустима ровно потому, что подстрахована
отменой ступени.

## 3. Verifier — проверяльщик

Обязательное требование. Ставится между извлечением и выдачей, работает
отдельным процессом, чтобы перезапускаться и версионироваться независимо.

Проверяет три разные вещи, и смешивать их в один вызов нельзя.

### 3.1 Grounding — карточка соответствует исходному тексту

Самый дешёвый и самый важный слой. Модель при извлечении дописывает то, чего в
объявлении нет: «блюкарт есть», когда написано «документы в порядке».

Правило: каждое непустое поле карточки подтверждается подстрокой исходного
сообщения либо явным правилом маппинга.

```
поле карточки → цитата из raw_text → иначе поле обнуляется,
                                     причина not_grounded в лог
```

Для чисел (цена, год, пробег, объём) проверка без LLM — регуляркой по исходному
тексту. Для смысловых полей один дешёвый вызов на пачку.

Провал проверки **не выбрасывает карточку, а опустошает поле**: «год
неизвестен» честнее выдуманного года.

### 3.2 Соответствие паспорту

Цена ошибки несимметрична: показать карбюратор тому, кто просил инжектор, — это
не низкий score, а брак выдачи. Поэтому deal-breaker'ы проверяются отдельно от
ранжирования.

```
must_have отсутствует       → карточка понижается
deal_breaker присутствует   → карточка выбрасывается, причина в лог
поле не определено          → карточка помечается unverified, показывается
                              ниже проверенных и с явной пометкой
```

### 3.3 Живость лота

Главная боль ручного поиска: объявление висит с мая, вещь продана в июне.
Объявления не снимают почти никогда.

| Сигнал | Действие |
|---|---|
| возраст > 14 дней | `stale`, показываем с пометкой «объявление от <дата>, могло быть продано» |
| в треде ответ автора: продано / sold / đã bán | `sold`, скрываем |
| тот же текст переопубликован позже | актуальна последняя публикация, старые схлопываются |
| цена в повторах падает | пишем `price_history`, показываем клиенту динамику |
| сообщение удалено автором | `gone` при следующей проверке |

Живость перепроверяется по расписанию для всех карточек, попавших хоть в одну
выдачу: дешёвый `get_messages` по id, без LLM.

**Что из этого работает на P0.** Первая строка таблицы: возраст считается по
дате публикации источника, и карточка старше 14 дней уходит клиенту с пометкой
«объявлению N дней, могло быть продано». Лот без даты не выбрасывается, но
честно помечен «дата публикации неизвестна» — это тот же `unknown` из 3.4, а не
молчаливое повышение доверия. Проверка чистая, без сети и без модели: это
просто дата. Остальные сигналы требуют ингеста и приходят вместе с ним на P1.

### 3.4 Схема хранения

```sql
listing_verifications (
  listing_id    bigint references listings(id),
  kind          text,   -- grounding | passport_match | liveness
  verdict       text,   -- pass | fail | unknown
  details       jsonb,  -- поле, причина, цитата
  checked_at    timestamptz,
  verifier_ver  text    -- версия правил, чтобы переигрывать на истории
)
```

Карточка без пройденного grounding в выдачу не попадает никогда. Карточка с
`liveness = unknown` попадает, но с пометкой.

Многозначная форма — через запятую: `motorbiketype=1,3` даёт 53 из 59, а

**Заполненность полей решает, годится ли фильтр.** `motorbiketype` заполнен у
**всех** 59 и разбивает выдачу без остатка (41 + 5 + 12 + 1 = 59) — поэтому
это жёсткий фильтр. `motorbikecapacity` заполнен у **35 из 59**: фильтр по
нему выбрасывает не только неподходящие байки, но и все, где продавец объём не
указал (41 → 24 в паре с типом). Поэтому объём применяется только когда
клиент спросил про него сам.

**Текстовый `q` — не текстовый поиск, и на него нельзя опираться.** Это смесь
поиска по `subject`/`body` с фасетным словарём, и ведёт она себя
непредсказуемо:

| `q` | Выдача из 59 |
|---|---|
| `tay ga` | 41 — **ровно те же объявления**, что `motorbiketype=1` (пересечение 41, разницы ноль) |
| `xe số` | 5 — снова совпадает с `motorbiketype=2` |
| `xe ga` | **0** |
| `xe máy`, `xe máy cũ`, `cũ`, `nguyên zin`, `chính chủ` | 59 — то есть не фильтруют ничего |
| `xe` | 8 |
| `honda` | 26 — ровно столько же, сколько `motorbikebrand=1` |
| `xe mới` | 8 — **чужое число**: те же восемь id, что `q='xe'`, и все помечены б/у |
| `mới` | 59 — само слово «новый» не фильтрует ничего |
| `xe cũ`, `cà vẹt`, `cavet`, `giấy tờ đầy đủ`, `bán tự động`, `côn tay`, `xe côn tay` | **0** |

рынке нет», поэтому такая ошибка живёт долго и незаметно; на неё есть тест.
Второй: отбор по свойствам делают `params`, а не слова.

**`q` складывается с фильтрами через И — поэтому слово гасит верный фильтр.**
Это отдельный замер (31.08.2026), и он дороже предыдущего: там слово давало
неточную выдачу, здесь — пустую. Проверялось полным путём код → сеть: паспорт →
фолбэк-план → `build_params()` → gateway.

| `motorbiketype=2`, без `q` | **5** | лапка (Wave, Sirius) |
| `motorbiketype=2` + `q='bán tự động'` | **0** | слово из текста объявлений, но не фасета |
| `motorbiketype=2` + `q='xe số'` | 5 | совпало со значением фильтра, поэтому не погасило |

| `motorbikebrand=3` (Piaggio/Vespa) | 1 | во всём Нячанге одна Vespa, и она автомат |
| `motorbikebrand=3` + `motorbiketype=3` | **0** | **честный ноль**: механической Vespa на рынке нет |

путях, нашем и модельном. Разница между «словом для чата» и «словом, безопасным для доски»
выражена таблицей, а не комментарием (2.2, правила 6–8).

| `condition=good` | `q='nguyên zin'` | 59 | без `q` | 59 |
| `condition=worn` | `q='xe cũ'` | **0** | без `q` | **59** |
| `condition=new` | `q='xe mới'` | 8 (все б/у) | `condition_ad=2` | **1** (единственное «Mới») |
| `transmission=manual` + `papers=blue_card` | `q='côn tay'` + фильтр | **0** | `motorbiketype=3` | **12** |
| `brand=Vespa` + `transmission=manual` | `q='Vespa'` + фильтры | 0 | два поля, без `q` | 0 (честный: такой Vespa нет) |

Ни одного ложного нуля не осталось. Нули в таблице подтверждены раздельно:
`motorbikebrand=3` даёт 1 объявление, и оно `motorbiketype=1`.

**Отдельно про нули от `condition_ad`.** «новый + 125cc» и «новый + автомат»
дают ноль, и это нули НАСТОЯЩЕГО поля, а не пустота от лишнего слова: во всём
Нячанге одно объявление помечено «Mới», и это Honda 67 с механикой и без
указанного объёма. Раньше на этих запросах уходило `q='xe mới'` и приходило 8 и
2 объявления — все б/у, то есть ответ был не «мало», а неверный. Честный ноль
доски лучше восьми чужих карточек, а настоящее предложение новых байков живёт
не на этой доске: `condition_ad` передаёт слова продавца, а сегмент новых у
дилеров и в чатах. По той же причине `condition=good` и `condition=worn` полем
НЕ отбираются — градаций внутри б/у у поля нет, и «good» через `condition_ad=1`
выбросил бы объявление, помеченное новым.

### 4.2 Почему SearXNG, а не поисковый API

Brave убрал бесплатный тариф для новых пользователей в феврале 2026: вместо
5000 запросов в месяц теперь 5 долларов кредитов, примерно тысяча запросов.
SearXNG self-hosted даёт неограниченные запросы к 70+ движкам за стоимость
своего контейнера и без ключей. При требовании «только бесплатное» это
единственный вариант, который не упрётся в квоту на третьем клиенте.

### 4.3 Зачем Firecrawl рядом с SearXNG

SearXNG возвращает ссылки и сниппеты, но не содержимое. Объявление живёт на
странице, и её надо прочитать. Firecrawl превращает произвольную страницу в
чистый текст или структуру, разворачивается свой инстанс. Без него веб-адаптер
умеет только «нашёл ссылку», что для выдачи бесполезно.

### 4.4 Telegram-группы — что стоило дорого узнать

Снято при написании адаптера 31 августа 2026 и подтверждено живым прогоном в
тот же день: юзербот, состоящий в `@gamezone_vietnam`, ответил на запросы
«продам» и «аренда» (2 и 5 находок). Это не общие соображения, а места, где
Telethon ведёт себя не так, как ожидаешь по названию метода.

**Про ссылки известно ровно столько, сколько измерено.** Двухсегментная форма
проверена: `curl` по `t.me/<username>/<msg>?embed=1` отдаёт в теле страницы
точный текст сообщения. **Трёхсегментная (форум) — не подтверждена**: тот же
запрос к `t.me/<username>/<topic>/<msg>?embed=1` возвращает 200 и оболочку
виджета без сообщения, тогда как то же сообщение без номера темы отдаётся
нормально. Из этого **не следует**, что ссылка не работает у человека в
клиенте — виджет предпросмотра может просто не поддерживать пути с темой.
Следует лишь то, что доказательства у нас нет, а бо́льшая часть живых находок
приходит именно в форумной форме. Проверять надо в настоящем клиенте, и до тех
пор форма остаётся как есть: менять её без доказательства, что она плохая, —
это менять работающее на предположение.

| Деталь | Что происходит на самом деле | Что из этого следует |
|---|---|---|
| `flood_sleep_threshold` | по умолчанию **60**: клиент сам спит на FloodWait до минуты **внутри вызова** и повторяет запрос, не сказав наружу ни слова | ставим **0**, иначе ни пауза, ни `degraded`, ни бюджет из 2.3 никогда не сработают — минуту съедят молча, а план ждёт 90 с |
| `t.me/c/<id>/<msg>` | открывается **только у участников** чата и требует id **без** служебного `-100`: `-1001902334455` → `1902334455` | публичной группе даём `t.me/<username>/<msg>` — она открывается у кого угодно, в том числе у клиента, который в группе не состоит; форма `/c/` запасная |
| адресация чата | по `username` сущность разрешается с холодной сессии, по голому id — **только если чат уже в кэше сессии**, а наполняется кэш `get_dialogs`, который стабильно отваливается по таймауту (раздел 7) | в реестре чатов `username` — не украшение; `tg_id` хранится в размеченной форме (`-100…`), потому что голое положительное число Telethon примет за id пользователя |
| `limit` в `get_messages` | больше 100 разбивается на несколько RPC подряд | потолок 100 на чат: незаметное умножение числа запросов — это и есть FloodWait |
| пустая строка в `search` | возвращает всю группу подряд | пустой запрос до Telegram не доходит: это выкачивание чата мимо воронки, а не поиск |
| автор поста | группа не отдаёт username автора (раздел 7) | `seller_name` остаётся пустым, контакт ищется в тексте, иначе у клиента остаётся ссылка на пост |
| цена в тексте | в группе нет отдельного поля цены; в реальных постах она пишется как «Цена 22 мил», «3 млн донгов», `15.500.000 VND`, `3.7tr` | берём только число после явной метки цены и нормализуем в VND. Год, объём `125cc` и пробег не становятся ценой; неизвестная цена честно остаётся неизвестной и получает меньший балл при ранжировании |
| форумные супергруппы | сообщение лежит в теме, и ссылка без её номера ведёт в никуда; тему видно в `reply_to`: `forum_topic` поднят, а сама тема — `reply_to_top_id`, либо `reply_to_msg_id`, если ответ идёт прямо на корень темы. **В живой выдаче доминирует вторая форма** (`reply_to_top_id = null`), первая приходит только у ответов на чужое сообщение внутри темы | ссылка становится трёхсегментной: `t.me/c/<id>/<topic>/<msg>` и `t.me/<username>/<topic>/<msg>`. Барахолок с темами много, и без этого их выдача была бы нерабочей. В фикстуре обе формы: сначала в ней был только редкий вариант, то есть тестами был закрыт как раз тот случай, которого в выдаче почти не бывает |
| альбом (медиагруппа) | пять фото с одной подписью приезжают **пятью сообщениями** с разными `id` и общим `grouped_id` | дедуп по `(source, external_id)` их не ловит — id разные. Схлопываем по `(чат, grouped_id)` на весь план, иначе клиент видит одно объявление пять раз |
| отозванная сессия | `UnauthorizedError` / `AuthKeyError` на КАЖДОМ чате: это состояние аккаунта, а не чата | распознаём на первой же ошибке, помечаем `degraded` и прекращаем обход. Девять одинаковых отказов подряд сессию не воскресят, а Telegram запомнит |

**Реестр чатов — не новый метод, а обёртка над готовым.** В слое `db` уже есть
`ChatRepository.list_active(limit)`: отдаёт активные чаты, **меньший
`search_rank` — раньше** (по умолчанию 100, то есть новый чат встаёт за
курируемыми). Источнику этого мало ровно в трёх местах, и все три закрывает
`sources/chat_directory.py`, не трогая репозиторий:

| Расхождение | Как закрыто |
|---|---|
| репозиторий не владеет сессией — её открывает вызывающий | обёртка держит `session_scope` и отдаёт репозиторию открытую сессию |
| фильтра по городу нет: `list_active` отдаёт активные чаты **всех** городов | город отрезается в обёртке, на стороне Python — чатов десятки, это дешевле, чем разъезжаться с веткой слоя `db` |
| фильтр применяется ПОСЛЕ выборки, а обход ограничен десятью чатами | из базы берём с пятикратным запасом: иначе десять чатов Нячанга превратились бы в два, остальное заняли бы чужие города |

**Сборка — одна строка, и она значением по умолчанию, а не примером в
документации.** Строку держит функция `new_directory()` в
`sources/chat_directory.py`, и её результат адаптер берёт себе сам, когда его
создают без аргументов:

```python
def new_directory() -> ChatDirectory:
    from sniffer.db import ChatRepository, session_scope

    return RepositoryChatDirectory(session_scope, ChatRepository)
```

Так сделано после того, как эта строка один раз осталась только в spec-v2 и в
тестах. Боевой путь создаёт источник через `get_source("telegram_groups")` — без
аргументов, — и адаптер получал заглушку `EmptyChatDirectory`: главный источник
продукта искал по пустому списку, писал в лог `telegram.no_chat_directory` и
возвращал ноль находок. Снаружи это выглядело как «все результаты с сайта, ни
одного из групп», а причину искали в исправном адаптере. Отсюда правило:
**значение по умолчанию — боевое; заглушка подставляется руками**. Заодно это
единственный модуль, где слой источников знает про слой `db`, —
`sources/chat_directory.py`. Кроме `new_directory()` он теперь содержит
операции общего каталога; адаптеры получают протоколы и SQL не видят. Импорты
внутри функций сохраняют модуль импортируемым там, где базы нет.

Проверяется проводка `tests/test_source_wiring.py`: боевой `run_plan` с задачей
`telegram_groups` доходит до чата, которого нет ни в одной строке кода, и
приносит с него находку. Тест на обёртку эту дыру пропустил — он проверял, что
`RepositoryChatDirectory` умеет отдавать чаты, а не что кто-нибудь его создаёт.

О тесноте запаса обёртка сообщает (`telegram.city_overfetch_tight`) только
когда сошлись **оба** признака: чатов нужного города меньше бюджета И база
отдала ровно столько строк, сколько просили, — то есть за обрезкой действительно
остались записи. Одного «города мало» недостаточно: на живой базе это давало
тревогу при 4 чатах из 44 при потолке 50, где ничего не отрезано и спасать
нечего.

SQL-фильтр по городу в самом репозитории — задача на потом, когда чатов станет
много; до тех пор запас в пять раз честнее преждевременной оптимизации.

Адаптер всё равно сортирует и обрезает список сам: реализация, забывшая про
`limit`, не должна превращаться во FloodWait. Запись с **положительным**
`tg_id` отвергается с ошибкой в логе, а не «пробуется»: положительный id — это
пользователь, и запрос ушёл бы в личную переписку молча.

Поведение при FloodWait: пауза `seconds × 2^(число флудов − 1)`, то есть 1×, 2×,
4× от названного Telegram минимума. Первый флуд ждёт ровно столько, сколько
попросили: названный минимум мы уважаем, а удваивать его сразу значит платить
за повтор, которого ещё не было.

Попыток на чат две, и **после второго флуда пауза не отсыпается**: попыток
после неё не остаётся, чат всё равно бросается — выждать значит отдать время,
которое не получат остальные девять чатов. Сам флуд при этом считается: лимит у
Telegram на аккаунт, а не на чат, и следующему чату эта немилость достанется
целиком (первая пауза 1×, дальше 2× и 4× независимо от того, на каком чате
флуд случился).

Если пауза не помещается в остаток бюджета — источник помечает себя `degraded`
и выбывает из плана (2.6), остальные доигрывают. Этот вывод делается и на
последней попытке, где ждать всё равно не станем: «Telegram просит больше, чем
у источника осталось» — это про состояние аккаунта, и следующий запрос его
только усугубит.

**Бюджет — на источник, а не на задачу.** План вправе поставить до пяти задач
на один источник (2.3), поэтому 40 с отсчитываются от первой задачи
`telegram_groups` и делятся на все его задачи. Иначе две задачи по 40 с съели
бы 80 с из 90 с плана и остальные источники не успели бы вовсе. Исчерпанный
бюджет — не поломка: источник остаётся в плане и просто перестаёт ходить в
Telegram.

### 4.5 `telegram_discover` — как набирается список чатов

**Статус:** очередь и её запуск в коллекторе готовы; первое вступление после
деплоя проверяется живым аккаунтом. Ручного вступления больше нет — владелец
отменил его 31.08.2026, — поэтому это единственный путь, каким проект набирает
чаты.

Источник особенный: он не отдаёт карточки. Его продукт — строки в реестре
`chats`, а читает их обычный `telegram_groups`. Поэтому он не наследует
`Source` и не стоит в реестре адаптеров: `search()`, который вернул бы
`RawItem`, у него нет и быть не может.

Классов два, и делятся они по ритму работы, а не по размеру файла.
`ChatDiscovery` (`telegram_discover.py`) собирает и отбирает — идёт вместе с
потоком сообщений, стоит одного `resolve_username`. `ChatJoiner`
(`telegram_discover_joiner.py`) разбирает очередь — срабатывает три раза в
сутки и стоит аккаунта, если ошибиться. В Telegram от первого уходит только
чтение.

Четыре шага, каждый со своим ограничением.

**1. Сбор кандидатов.** Ссылки вынимаются из сообщений, которые и так проходят
через воронку, — отдельного обхода чатов ради разведки нет. Формы: `t.me/<имя>`,
`t.me/<имя>/<пост>`, `t.me/joinchat/<хэш>`, `t.me/+<хэш>`, `@имя` в тексте и
**`url` у сущности сообщения** (`MessageEntityTextUrl`), где адрес спрятан за
подписью. Последняя форма самая частая: разбор одного лишь текста пропустил бы
половину находок. Плюс `contacts.Search` по словарю (`search_dialogs` не годится,
см. 7).

**2. Отсев без вступления — по обеим формам ссылки.** Публичную группу
описывает `resolve_username`, закрытую — `messages.checkChatInvite`; оба отдают
тип, название и описание, ничего не отправляя. Отбрасываются канал (нет
объявлений от людей), гигагруппа (та же пустота: пишут только администраторы),
бот, пользователь, чужой город, то, где города не видно вовсе, и — только у
приглашений — группа «только по заявке» и та, в которой мы уже состоим. Уже
известное и однажды отклонённое не разбирается повторно. Города — данные, а не
код: второй город это строка в `CITY_MARKERS`.

Проверка `screen()` **одна на оба пути**, и это не экономия строк. Правило
«канал, бот, пользователь и чужой город не наши» в двух редакциях разъедется, а
цена расхождения здесь несимметрична: **выйти из чата нельзя**. Закрытый список
CLAUDE.md знает два действия, и `LeaveChannel` в него не входит, поэтому
ошибочное вступление не откатывается ничем — оно навсегда занимает место под
потолком и стоит одного из трёх суточных слотов. Единственное место, где ошибку
ещё можно не совершить, — до вступления.

У непройденного приглашения `tg_id` нулевой: до вступления Telegram id закрытого
чата не отдаёт. Поэтому сверка кандидата с реестром по id делается только когда
id известен, а по хэшу — по самому хэшу (`key`), который регистрозависим.

Ранее кандидат с хэшем ставился в очередь без единой проверки: комментарий
обещал «решение принимают ворота вступления», а таких ворот не существовало —
город в реестре записывался безусловно, то есть запись **лгала**, и фильтр по
городу на чтении ей верил. Отсюда правило: у приглашения поблажки нет.

**3. Очередь вступлений.** Лимиты взяты из CLAUDE.md дословно: не больше **3
вступлений в сутки**, пауза **не меньше часа** и вразнобой, `FloodWaitError`
останавливает вступления **до конца суток, но не меньше чем на 12 часов** (это
предупреждение, а не задержка на названные секунды), потолок **50 чатов**.

Пол в полсуток приписан после замера: «до конца суток» само по себе оказалось
лазейкой. Флуд в 23:59 давал `blocked_until` = полночь, то есть **шестьдесят
секунд**, а дальше работала только часовая пауза — два новых вступления в
течение трёх часов после предупреждения. Буква правила соблюдалась, защитный
смысл исчезал; тест брал полдень и этот край не покрывал.

**Расхождение, названное явно.** CLAUDE.md говорит «при достижении — только
замена, не рост». Реализована половина: рост останавливается, замены нет.
Заменить чат значит из какого-то выйти, а `LeaveChannel` — это **третье
действие**, которого в закрытом списке владельца нет; появиться оно может только
его решением. Поэтому на потолке разведка перестаёт вступать и пишет
`discover.chat_cap_reached`, а не вытесняет кого-нибудь молча. Половина правила,
которая исполнена, — безопасная: 50 чатов при обходе десяти за запрос (2.3) не
жмут, а до потолка ещё двенадцать дней стартового набора.

Счётчик живёт в таблице `chat_join_events`, а не в памяти: процесс
перезапускается деплоем и падением, а лимит Telegram — нет. Слот занимается
**одной транзакцией вместе с проверкой** (`claim_slot`): проверить, а потом
действовать — это гонка, в которой два воркера проходят одни и те же ворота.
Занятый слот не возвращается сам. Если связь оборвалась и неизвестно, прошло
вступление или нет, слот остаётся потраченным, а кандидат возвращается в
очередь: недосчитать одно вступление безопаснее, чем сделать одиннадцатое.

Слот считается потраченным и тогда, когда чата мы не получили, но **запрос
наружу состоялся**. Это относится к КАЖДОМУ ответу сервера, а не к одному
случаю: «такого чата нет» (`UsernameNotOccupied`), «сюда нельзя»
(`ChannelPrivate`), «ссылка истекла» (`InviteHashExpired`), «заявка ушла
модератору» (`InviteRequestSent`), «мы уже внутри» (`UserAlreadyParticipant`) —
запрос ушёл, Telegram его записал, и лимит считает именно запросы.

Формулировка была верной, а исполнение — на один случай из семи. Правка ревью
закрыла `InviteRequestSentError`, а шесть отказов по-прежнему возвращали слот:
`release_slot` удаляет событие, вместе с ним исчезает `next_allowed_at`, то есть
пауза в час, и суточный лимит превращался в **двадцать четыре запроса** — ровно
столько, сколько влезает в сутки при часовой паузе (замер: очередь недоступных
чатов, вызов раз в час — 24 исходящих `JoinChannel` за сутки; при остановленном
времени — 40). Замер сделан, когда лимит стоял на трёх, но число 24 от лимита не
зависит вовсе: дефект убирал не часть слотов, а сам счётчик. `ChannelPrivateError`
для чата, закрывшегося за недели ожидания в очереди, — обычное дело, а не
редкость.

Кандидат при отказе выбрасывается насовсем: исход известен точно, в отличие от
обрыва связи. Группы «только по заявке» отбор отсекает заранее по
`request_needed`, так что до вступления доходит только та, что стала
модерируемой между проверкой и вступлением.

**Неизвестный исход возвращает кандидата в очередь, но не бесконечно.** Обрыв
связи посреди вступления не говорит, прошло оно или нет: слот остаётся
потраченным (недосчитать безопаснее, чем сделать одиннадцатое), а кандидат
возвращается — терять его нельзя, разбирать очередь больше некому. Но очередь
берёт наименьший приоритет, то есть **его же**, и один такой кандидат съедал
суточные слоты целиком и бессрочно: замер дал 21 бесполезный запрос за семь
суток (лимит тогда стоял на трёх), а второй кандидат не получал хода никогда. Поэтому попытки считаются в колонке
`chat_candidates.attempts` (в БД, а не в памяти воркера: счётчик, обнуляемый
перезапуском, не ограничивает ничего), и после третьей кандидат уходит в
отклонённые с причиной `too_many_attempts`.

Считать попытки, а не перечислять ошибки, — осознанный выбор: список типов
закрывает то, что вспомнили, а счётчик закрывает и седьмую ошибку, которой
никто не назвал. Именно так этот класс дефекта и жил: `UserAlreadyParticipant`
и `ChannelsTooMuch` в список не входили и падали в общий обработчик.

**Ответ на вступление без чата — исход не неизвестный, а известный.** Telegram
не обязан класть в ответ на `JoinChannel` список обновлений: когда очередь
обновлений аккаунта переполнена, приходит `UpdatesTooLong`, где чата нет вовсе,
а вступление при этом состоялось. Клиент бросал на таком ответе `LookupError`,
то есть говорил «исход неизвестен», кандидат возвращался в очередь — и через час
уходил **второй** `JoinChannel` в тот же чат. Замер на боевом аккаунте
01.09.2026: два слота из десяти на `@auto_moto_vietnam` за сутки, `chats` пуст,
чат не заглушен, очередь из 35 кандидатов стоит за первым, а на третьей попытке
лучший кандидат ушёл бы в `too_many_attempts` — при том что аккаунт всё это
время был в группе.

Лечится не новым классом в `except`, а тем, что id **читается, а не угадывается**:
после ответа без чата публичное имя добирается `ResolveUsername`, приглашение —
`CheckChatInvite` (он отдаёт `ChatInviteAlready` вместе с id, если мы уже
внутри). Оба — чтения: слота не стоят, в чате не видны, закрытый список действий
не трогают. `LookupError` остаётся ровно для случая, когда и чтение ничего не
дало, — вот тогда исход действительно неизвестен, и счётчик попыток уместен.

**Кандидат на чат, который уже в реестре, не стоит ничего.** Проверяется у
своего же реестра, до всякого запроса наружу: сид и находки разведки кладут
кандидата в очередь без `screen()`, а между отбором и вступлением проходят часы
— за них чат мог попасть в реестр другим путём. Замер на живой базе 03.09.2026:
в очереди стояли ДВАДЦАТЬ таких, ровно все чаты реестра, то есть двое суток
суточного бюджета уходило на вступление в то, что уже читается.
`UserAlreadyParticipantError` их выбрасывает и без этой проверки, но ценой
одного исходящего запроса каждый — а Telegram считает запросы, не успехи.
Приглашение (`+hash`) так проверить нечем: до вступления id закрытого чата
Telegram не отдаёт, и там от лишнего запроса защищает только ответ сервера.

**Аккаунт упёрся в свой потолок чатов** (`ChannelsTooMuchError`) — случай не
кандидата, а аккаунта: пока из чатов не выйдут, каждый следующий запрос уходит
в пустоту. Поэтому останавливаемся так же, как после флуда, а не пробуем ещё
дважды в те же сутки; кандидат ни в чём не виноват и остаётся в очереди.

Очередь `chat_candidates` разбирается по приоритету. Стартовый набор — 36 групп
из [chats-nha-trang.md](chats-nha-trang.md), засеянных
`infra/sql/002_seed_candidates.sql` волнами 10/20/30; находки разведки идут со
100 и не оттесняют то, что владелец выбрал руками. При десяти вступлениях в сутки
стартовый набор разбирается примерно за двенадцать дней.

**4. Беззвучный режим** (`account.UpdateNotifySettings`) сразу после вступления
и только для чатов нашего реестра — чужих настроек не трогаем. Провал не
откатывает вступление: оно уже стоило суточного лимита, а незаглушенный чат
чинится повтором по флагу `muted`.

**Граница жёсткая.** Разрешены ровно семь запросов к Telegram: **четыре чтения**
(`ResolveUsername`, `GetFullChannel`, `CheckChatInvite`, `contacts.Search`) и три
запроса на **два действия** — вступление (`JoinChannel` либо
`ImportChatInvite`, смотря по форме ссылки) и беззвучный режим
(`UpdateNotifySettings`).

Закрытый список CLAUDE.md ограничивает именно **действия**, и их по-прежнему два.
`CheckChatInvite` третьим исключением не является и стать им не может: это
чтение — оно никому не адресовано, ничего не отправляет и в чате не видно, ровно
как `ResolveUsername`, только для закрытой группы. Под `PEER_FLOOD` такое не
подпадает. Новое чтение — вопрос инженерный; новое действие — вопрос к владельцу,
и тесты эту разницу держат порознь.

Список проверяется тестами, которые перечисляют разрешённое, а не запрещают по
образцу: запретный список пропускает то, чего в нём не додумались написать. Их
три, и третий появился после того, как вынос кода в новый модуль оказался
способом выйти из-под стража: `test_every_discovery_module_is_under_guard`
сверяет список проверяемых модулей с тем, что лежит в пакете, поэтому новый файл
разведки под запрет попадает сам.

**Что работает сейчас.** `collector/discovery.py` запускает
`ChatJoiner.join_next()` каждые 15 минут, но сам join делает максимум один раз
за проход и только если БД пропустила лимиты. Он же догоняет беззвучный режим
для уже вступивших чатов. Реализации `ChatRegistry` / `CandidateQueue` /
`RejectedLog` / `JoinLedger` открывают отдельную короткую транзакцию на каждый
шаг; `claim_slot` дополнительно защищён transaction-level advisory lock, чтобы
два контейнера не получили лишний слот. После вступления коллектор читает
последние 200 сообщений каждого из первых десяти активных чатов после
сохранённого курсора, пишет текст в `raw_messages` с дедупликацией по
`(chat_tg_id, msg_id)` и передаёт их в `ChatDiscovery.harvest()` для
перекрёстных ссылок. Курсор сдвигается в той же транзакции, что и вставка.
Live-подписки пока нет: следующий проход спокойно дочитает пропущенное.

**Архив дочитывается отдельным курсором, вниз.** Догон свежего отвечает на
вопрос «что нового с прошлого раза» и по определению короткий. Без второго
курсора чат отдавал ровно те 200 сообщений, что висели в нём на момент
вступления, — замер 01.09.2026: два чата и 148 сообщений в сырье при 28 113 в
одном только первом. Поэтому у `chats` два курсора: `last_msg_id` идёт вверх за
новыми постами, `backfill_msg_id` — вниз за старыми, а `backfill_done`
закрывает чат навсегда, когда Telegram отдал пустую страницу.

Осторожность здесь не общая, а против конкретного риска: **один чат за проход**
(идти по десяти сразу — это выкачка, по одному — человек, листающий ленту
вверх), **потолок в пять страниц** (тысяча сообщений раз в пятнадцать минут,
то есть один запрос в три минуты в среднем), **любая ошибка останавливает
проход**, а курсор остаётся на последней удавшейся странице. Отдельного разбора
`FloodWaitError` нет намеренно: перечень классов ошибок закрывает только то, что
вспомнили, а «остановиться и прийти через пятнадцать минут» — верный ответ на
любую из них. Архив читается ПОСЛЕ свежего и последним в проходе: свежее
объявление клиенту нужнее вчерашнего, а добор длинный.

Если подключение юзербота не удаётся, коллектор пишет владельцу через обычный
Bot API один раз за период недоступности и не пытается «лечить» сессию каждым
проходом. Для продолжения нужен вход в переавторизацию на дашборде.

## 5. Публичный бот — антиспам и монетизация

Бот публичный, но тестируется в одиночку. Механика ограничений закладывается
сразу, пороги ставятся щедрыми и правятся конфигом.

### 5.1 Квоты

```
users.tier ∈ (free, paid, owner)

free   3 поиска в сутки · выдача 5 карточек · подписок нет
paid   50 поисков · выдача 20 карточек (подписки покупаются по одной)
owner  без лимитов
```

**Подписка стала платной — 1 ⭐ в месяц за тему** (решение владельца,
01.09.2026). Раньше в этой таблице стояла «1 активная подписка» в бесплатном
тарифе; теперь слежение за темой продаётся отдельно и поштучно, а `tier`
остаётся про объём поиска. Одна звезда — меньше цента, и она не про деньги: она
про то, чтобы подписка была осознанным действием. Бесплатная кнопка «следить»
набирает подписчиков, которым уведомления не нужны, и заканчивается это блоком
бота, а не выручкой.

Счётчики в `usage_counters(user_id, day, searches, notifications)`. Проверка
квоты — **до** планировщика, чтобы отказ не стоил ни одного LLM-вызова.

### 5.2 Антиспам

| Защита | Механика |
|---|---|
| Флуд команд | rate-limit 1 запрос в 10 с на пользователя, middleware aiogram |
| Дорогие запросы | поиск стартует только по готовому паспорту, а не на каждое сообщение |
| Абуз LLM | дневной cap на project-key AIbroker — жёсткий потолок расходов |
| Накрутка | капча-вопрос при первом запуске, блок по `user_id` |
| Скам в выдаче | `sellers.scam_score`, жалоба кнопкой на карточке |

### 5.3 Монетизация — что заложить в схему сейчас

Платежи не реализуем, но данные под них закладываем, иначе потом миграция по
живой базе:

```sql
users            tier, tier_expires_at, referred_by
payments         provider, amount, currency, status, external_id, created_at
usage_counters   user_id, day, searches, notifications
```

**Провайдер — Telegram Stars** (владелец, 31.08.2026). Не требует юрлица,
оплата идёт внутри Telegram, вывод через Fragment. Внешнего платёжного
провайдера не появляется вовсе, то есть ни одного лишнего аккаунта и ни одного
лишнего секрета в `.env`.

### 5.3.1 Подписка за звезду — что проверено вызовом, а не памятью

Реализовано 01.09.2026. Ограничения Telegram сняты живым `createInvoiceLink`,
потому что документация о минимальной цене подписки для бота молчит:

| Проверка | Ответ Telegram |
|---|---|
| 1 звезда, период 2592000 | ссылка создана |
| 0 звёзд | `Bad Request: total price must be positive` |
| период 86400 (сутки) | `Bad Request: SUBSCRIPTION_PERIOD_INVALID` |

Период ровно 30 суток — не наш выбор, а единственное принимаемое значение.

**Где предлагается.** Там, где предложение честно: под выдачей рядом с «дорого»
и «не то», и на пустом ответе. Второе — самый прямой случай: искать больше
негде, а новое появится. Цена стоит на самой кнопке (`🔔 Следить за новыми —
1 ⭐/мес`): кнопка, ведущая к счёту без предупреждения о деньгах, — тёмный
паттерн, даже если речь про звезду.

**Подписка следит за НОВЫМИ объявлениями.** У неё есть точка отсчёта —
`subscriptions.since_listing_id`, последняя карточка на момент оплаты. Без неё
свежая подписка вываливает клиенту весь двухнедельный запас разом, включая
ровно те объявления, за отсутствие интереса к которым он и заплатил. Продление
точку отсчёта НЕ сдвигает: иначе клиент терял бы всё накопленное за оплаченный
месяц.

**Деньги нельзя обработать «примерно один раз».** Telegram повторяет апдейт,
если бот не ответил вовремя. Идемпотентность держится уникальным индексом
`payments.external_id` и `ON CONFLICT DO NOTHING` — а не проверкой «а нет ли уже
такого», которая оставляет окно между собой и вставкой. Проверено на живом
Postgres: без `ON CONFLICT` тест краснеет `IntegrityError`.

**Отказывать можно только до списания.** `pre_checkout_query` — последняя точка,
где отказ ничего не стоит клиенту, и там же единственная проверка: принадлежит
ли цепочка паспортов тому, кто платит. `payload` формируем мы, но приходит он от
Telegram и доверенным не является. Отвечать обязаны за 10 секунд, поэтому в
обработчике нет ни поиска, ни модели, ни сети.

**Срок берётся у Telegram** (`subscription_expiration_date`), а не считается
нами: продлевает подписку он, и его дата единственная правильная. Своя
арифметика разошлась бы с ней на любой задержке платежа, и подписка выключалась
бы раньше оплаченного. Проверка срока стоит прямо в запросе активных подписок, а
не в отдельном стороже: пропущенный проход сторожа означал бы бесплатную
рассылку, а пропущенное условие в запросе не означает ничего.

Чего пока нет: возврата звезды (`refundStarPayment`) и отмены подписки со
стороны бота (`editUserStarSubscription` — ключ платежа для этого уже хранится
в `subscriptions.charge_id`). Режим дайджеста, тихие часы, точный `sent_at` и
курсор просмотра подписки реализованы; детали —
[universal-search.md](universal-search.md).

## 6. Риски

### 6.1 Бан юзербота

Отдельный номер снимает риск для личного аккаунта, но не для сервиса. Правила:
только чтение, **ноль исходящих сообщений**, `FloodWaitError` с экспоненциальной
паузой, `StringSession` в БД.

Вступление в группы и беззвучный режим — два исключения, открытые владельцем
31.08.2026 (CLAUDE.md, «Работа с Telegram»). Оба не адресованы людям и в чате
не видны, поэтому под `PEER_FLOOD` не подпадают. Ручное вступление отменено:
работает то, что поедет в прод, — очередь с лимитами, см. 4.4.

Основание: 17 августа 2026 личный аккаунт поймал `PEER_FLOOD` после пяти
сообщений незнакомым людям подряд. Отправка отбилась, лимит снимается часами.
Для сервиса, который живёт на одном аккаунте, это означает простой — поэтому
исходящих действий у юзербота не должно быть вообще.

**Чем именно этот запрет держится — и чем не держится.** Клиент виден адаптеру
через протокол `TelegramReader`, и всё, что типизировано им, mypy проверяет:
обращения к `send_message` у такого объекта не существует. Но у голого
`TelegramClient` из Telethon для mypy есть любой метод — библиотека без
`py.typed`, при `ignore_missing_imports` это `Any`, — и отправку через такой
объект не заметят ни mypy, ни ruff (проверено 31.08.2026: `mypy` ловит вызов
через протокол и молчит на вызове через голого клиента). Поэтому вторая
половина защиты — тест `test_adapter_never_calls_an_outgoing_method`: он ищет
исходящие вызовы регуляркой по исходникам, а список файлов выводит **из графа
импортов** источника, а не из перечисления руками, — иначе новый модуль на пути
чтения в проверку просто не попадал бы.

### 6.2 Chotot меняет API

API недокументирован. Защита: адаптер изолирован, при ошибке парсинга источник
помечается `degraded` и исключается из планов до ручной починки. Клиент этого
не замечает — получает выдачу из остальных источников.

### 6.3 Facebook Marketplace — почему выключен

Meta запретила автоматический сбор данных в ToS с 1 января 2025 независимо от
того, залогинен ли сборщик. Разлогиненный поиск заблокирован технически,
известные краулеры в чёрном списке, аккаунты за скрейпинг банят.

Адаптер в реестре предусмотрен, `enabled = false`. Включение — осознанное
решение владельца с пониманием, что это нарушение ToS и риск бана аккаунта.
Технически потребует отдельный аккаунт и резидентные прокси, то есть деньги, а
не бесплатно.

## 7. Полевые уроки — откуда взялись требования

Выведено из ручного поиска скутера в Нячанге 14–17 августа 2026: 25
просмотренных чатов, около 40 найденных объявлений, три диалога с продавцами.
Это не гипотезы.

| Наблюдение | Следствие для продукта |
|---|---|
| «скутер» не находил половину лотов, а «инжектор» и «блюкарт» находили | планировщик обязан расширять запрос синонимами и жаргоном рынка |
| на «нужен скутер» приехал Honda Winner X 2021 — спортбайк с механикой | свойство предмета берётся структурным полем источника, а не словом: замер 71% → 100%, см. 4.1.1 |
| на «нужен скутер honda lead» приехал Airblade трижды и лот 59-дневной давности | модель — отдельный атрибут паспорта, а не слово в списке марок; поля модели у доски нет, поэтому отбор по ней клиентский, и у живой выдачи появился порог показа, см. 2.7 |
| «xe ga» в словаре рынка не находило на Chotot ни одного объявления | слово, дающее ноль, из словаря убирается: пустая выдача выглядит как «на рынке нет» и живёт незаметно |
| одно объявление лежит в пяти группах | дедуп по нормализованному тексту обязателен, иначе выдача из копий |
| майские объявления висят как живые | verifier, раздел 3.3 |
| цена в повторах падала 25 → 24 → 23 → 22 | `price_history` — сигнал «продавец готов торговаться» |
| «документы в порядке» ≠ блюкарт на продавце | grounding: не превращать расплывчатое в конкретное |
| «двигатель в отличном состоянии» при чеке о расточке неделю назад | оценки продавца не факт; чеки и фото — отдельная ценность, их надо извлекать |
| вьетнамцы в Telegram байки не продают вообще | без Chotot теряется весь локальный рынок и 10–20% разницы в цене |
| `search_dialogs` стабильно отваливается по таймауту | использовать `resolve_username` + `contacts.Search`, не перебор диалогов (4.4) |
| API не отдаёт username автора поста в группе | контакт берём только из текста объявления, иначе отдаём ссылку на пост |

## 8. Этапы

| Этап | Содержание | Критерий готовности |
|---|---|---|
| **P0** | диалог → паспорт → планировщик → 2 источника (telegram_groups, chotot) → 5 карточек | выдача полезна на реальном запросе про байк |
| **P1** | ингест, воронка, Postgres, verifier grounding + liveness, **курс USD→VND** | карточки не врут, мёртвые помечены, ценовой фильтр доски работает на долларовом бюджете |
| **P2** | SearXNG + Firecrawl, telegram_discover, подписки, outbox | источники расширяются без правки кода |
| **P3** | квоты, tier, платежи, скам-скоринг, второй город | бот выдерживает чужих пользователей |

Точка принятия решения между P0 и P1 не техническая: вопрос в том, попадает ли
выдача в запрос. Если карточки мусорные, остальное бессмысленно.
