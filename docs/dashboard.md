# Веб-интерфейс владельца

`https://lbot.zapleo.com/` — шестой процесс, единственный, который слушает
порт. Требование владельца от 31.08.2026. До этого момента «ни один процесс не
слушает порт» было записано как свойство архитектуры; требование его отменило.

Сделано в ветке `feat/dashboard`. Ниже — как оно устроено, а не как
планировалось.

## 1. Что показывает

| Страница | Что на ней | Откуда данные |
|---|---|---|
| `/` | сводка, состояние сессии, лог запросов, список клиентов | `client_requests`, `broker_calls`, `users`, `chats`, `listings`, `telegram_sessions` |
| `/requests/{id}` | формулировка клиента, время по этапам, расходы по каждому вызову модели, переписка этого запроса | `client_requests`, `broker_calls`, `dialog_messages` |
| `/users/{id}` | клиент и его переписка целиком | `users`, `dialog_messages` |
| `/session` | состояние сессий юзербота и форма переавторизации | `telegram_sessions` |
| `/healthz` | `{"status": "ok", "missing": [...]}` — без авторизации, без данных | настройки |

Сводка на главной отвечает на вопросы, за которыми страницу и открывают:
сколько запросов, сколько упало, какая доля ушла в фолбэк плана, среднее время,
сколько чатов активно, сколько карточек свежих, сколько всего потрачено.

## 2. Учёт расходов — связь по ключу, а не по времени

Брокер в завершённой задаче отдаёт `request_id` — id строки в его `usage_log`,
— а также `provider`, `model`, `tokens_in`, `tokens_out`, `cost_usd`,
`latency_ms`. До этой работы `BrokerResult` нёс только текст, провайдера и
стоимость, и всё остальное терялось.

Теперь:

```
bot: сообщение клиента
  └── client_requests: строка «running»
       └── request_scope(request_id)          contextvar на время обработки
            ├── intake  → BrokerClient.chat → broker_calls (request_id, ...)
            └── planner → BrokerClient.chat → broker_calls (request_id, ...)
       └── client_requests: «done», duration_ms, stages
```

Три решения, из-за которых это выглядит именно так:

- **`client_requests` как отдельная сущность.** Без общего ключа связать
  «клиент спросил про байк» и «потрачено N токенов» можно только по времени —
  то есть неверно при двух параллельных запросах. Тест на это есть:
  `test_parallel_requests_do_not_mix_up_costs`.
- **`request_id` едет в contextvar, а не параметром.** Модель вызывают `intake`
  и `planner` через несколько слоёв, которым id запроса не нужен; протаскивать
  его параметром значило бы менять их сигнатуры ради учёта. Contextvar, а не
  глобальная переменная: у каждой задачи asyncio свой контекст.
- **Приёмник учёта внедряется в клиент брокера.** `broker/client.py` не знает
  ни про базу, ни про репозитории — иначе его нельзя собрать в тесте без
  Postgres. Запись в базу живёт в `broker/usage.py`.

**Ошибка учёта не отменяет ответ модели.** Он уже оплачен; падать из-за
недоступной базы означало бы выбросить то, за что заплатили. Ошибка идёт в лог
событием `broker.usage_not_recorded`.

**Повтор не удваивает расход.** `broker_calls.broker_request_id` накрыт частичным
уникальным индексом, запись идёт через `ON CONFLICT DO NOTHING`: поллинг
возвращает завершённую задачу повторно при ретрае сети.

**Дашборд не ходит в брокер.** Ни при одном просмотре. Страница, зависящая от
доступности чужого сервиса, показывает пустоту ровно тогда, когда на неё смотрят
из-за инцидента.

### Время по этапам

`client_requests.stages` — JSONB вида `{"intake_ms": 1200, "plan_ms": 900,
"search_ms": 8000}`. Именно по этапам, а не одной цифрой: «запрос шёл 40 секунд»
не отвечает на вопрос, разбор это или источники, а от ответа зависит, что
оптимизировать. JSONB, а не колонки: ступеней у воронки станет больше, и каждая
новая не должна требовать миграции ради одного числа.

`duration_ms` считается от `started_at`, прочитанного из базы, а не по своему
таймеру: часы процесса и часы Postgres расходятся, и разъехавшись, дают
отрицательное время в логе.

### Журнал не мешает клиенту

`bot/journal.py` фейл-софт целиком: недоступная база означает пустой лог в
дашборде, а не «бот не ответил». Ответ уходит человеку **до** записи в журнал —
порядок «сначала записать» задерживал бы ответ на время недоступной базы.

## 3. Вход — Telegram Login Widget

Владелец сделал `/setdomain` для `@RecVNbot` → `lbot.zapleo.com`, виджет
разблокирован.

**Три ключа, три задачи, ни одного переиспользования:**

| Ключ | Что подписывает/шифрует | Почему отдельный |
|---|---|---|
| `sha256(BOT_TOKEN)` | подпись данных виджета | так требует Telegram; владеть им может только владелец токена бота |
| `DASHBOARD_SESSION_SECRET` | нашу cookie и токены CSRF | один ключ на две цели означает, что утечка одной обесценивает обе |
| `SECRET_ENCRYPTION_KEY` | строку сессии юзербота в БД | у шифрования данных в покое другой срок жизни и другой радиус ущерба |

Что закрыто и чем:

| Атака | Чем закрыта |
|---|---|
| подделка cookie | HMAC-SHA256 payload'а `owner:<id>:<issued>` |
| тайминг-атака на сравнение подписи | только `hmac.compare_digest`, никогда `==` |
| повтор параметров виджета | окно `auth_date` **5 минут** плюс одноразовость `hash` в памяти процесса |
| `auth_date` из будущего | допуск 60 секунд на расхождение часов, дальше отказ |
| смена владельца | id владельца внутри подписанного payload: сменили `OWNER_CHAT_ID` — старые cookie мертвы, без списка отзыва |
| чужой Telegram-аккаунт | сверка с `OWNER_CHAT_ID` → **403 с текстом**, а не пустая страница |
| CSRF на форме переавторизации | подписанный токен с префиксом `csrf:` (не взаимозаменяем с cookie) + `SameSite=Lax` |
| XSS из чужих чатов | всё динамическое проходит `html.escape(..., quote=True)`; своя разметка собирается только в `dashboard/html.py` |
| утечка подробностей | обработчик исключений отдаёт обобщённую 500, трейсбек только в лог; `/docs` и `/openapi.json` выключены |
| кража cookie | `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/` |

Неавторизованный получает **401 со страницей входа** — только виджет, ни строки
данных.

Окно `auth_date` сознательно сужено с суток до пяти минут (так же сделано в
дашборде Веры): перехваченный однажды набор параметров иначе работает почти
день. Одноразовость `hash` закрывает и эти пять минут; она живёт в памяти
процесса, и это достаточно — окно короче любого рестарта, а cookie рестарт
переживает, потому что подписана, а не хранится.

## 4. Переавторизация сессии юзербота

`/session` → номер → код из Telegram → при включённом 2FA облачный пароль.
Поток: `dashboard/reauth.py`.

**Это единственное место во всём проекте, где секрет проходит через HTTP**, и
правила здесь жёстче обычных:

- **код и облачный пароль не логируются и не сохраняются** — живут только внутри
  POST-запроса, ровно чтобы довершить `sign_in`;
- **строка сессии не попадает ни в HTML, ни в лог, ни в историю браузера** — из
  потока она уходит прямо в `crypto.encrypt` и в базу; `reauth.verify` возвращает
  только номер телефона;
- **состояние потока живёт в памяти процесса с TTL 600 с** — незаконченный вход
  не оставляет на диске ничего; просроченные потоки закрывают соединение с
  Telegram, иначе каждый брошенный держал бы его открытым;
- **строка сессии в базе зашифрована** Fernet (`enc1:` + AES-128-CBC + HMAC).
  Открытый текст в колонке при чтении **отвергается**, а не читается «как есть»:
  это закрывает вектор «кто-то с правом записи в базу подложил своё значение».
  Ключ короче 32 символов не принимается — слабый ключ работает так же, как
  сильный, и молча.

Доменная запись `SessionState` шифртекста не несёт вообще: у репозитория два
разных метода чтения — `active_state()` для дашборда и
`active_session_string()` для коллектора. Один метод «отдай всё» рано или поздно
попал бы в HTML.

## 5. Схема

Четыре таблицы в разделе `── наблюдаемость и сессии ──` файла
[`infra/sql/001_init.sql`](../infra/sql/001_init.sql):

| Таблица | Зачем |
|---|---|
| `client_requests` | запрос клиента как единица наблюдения: якорь для расходов и времени |
| `dialog_messages` | переписка. Отдельно от `passport_events`: те — история разбора, а здесь то, что человек увидел |
| `broker_calls` | расход по каждому вызову модели, с `broker_request_id` для сверки |
| `telegram_sessions` | сессия юзербота: шифртекст, активность, последняя ошибка |

Репозитории: `db/repositories/requests.py`, `dialog.py`, `broker_calls.py`,
`telegram_sessions.py`, `stats.py`. SQL, как и раньше, только в `db/`.

**`001_init.sql` выполняется только при создании тома.** На уже созданной базе
новые таблицы надо накатить руками — файл идемпотентен
(`CREATE TABLE IF NOT EXISTS`), поэтому достаточно прогнать его целиком:

```bash
docker exec -i sniffer-postgres psql -U sniffer -d sniffer < infra/sql/001_init.sql
```

Механизма миграций в проекте нет (deploy.md, раздел 11), и это место придётся
переписать, когда он появится.

## 6. Инфраструктура

- **Процесс `dashboard`**, `python -m sniffer.dashboard`, uvicorn на **8005**.
  Внутри общего каркаса `runtime/`: без обязательных секретов не падает, а
  пишет в лог, чего ждёт, и перепроверяет окружение раз в минуту.
- **Порт публикуется только на `127.0.0.1`.** Снаружи ходит nginx, а не браузер.
  Публикация на `0.0.0.0` сделала бы страницу с перепиской клиентов доступной по
  IP машины в обход TLS и проверки подписи.
- **`mem_limit`** `${SNIFFER_MEM_DASHBOARD:-256m}` — как у соседей; правило
  потолков из [deploy.md, раздел 9](deploy.md#9-память-кончилась) действует и здесь.
- **Healthcheck контейнера** ходит на `/healthz` изнутри (через `python`, не
  `curl`: в образе его нет).
- **Деплой проверяет интерфейс по HTTP**, а не по состоянию контейнеров:
  `infra/deploy.sh`, шаг 6.5, пункт 4. Незаполненный `.env` — предупреждение, а
  не красный деплой: процесс ждёт конфигурации и не падает.
- **nginx править не нужно.** `location /` уже проксирует на `127.0.0.1:8005`, а
  заглушка через `error_page 502 504` перестанет срабатывать сама, как только
  сервис поднимется.

Что осталось сделать при выкладке (одним движением): Origin Rule для
`lbot.zapleo.com` → порт `8443` и режим SSL **Full** для этого хоста. Зонный
режим трогать нельзя — [deploy.md, раздел 1](deploy.md#1-где-что-живёт).

## 7. Настройки

Новое в `.env` (полный список — `.env.example`):

```
OWNER_CHAT_ID=169510539        # уже заполнен
BOT_USERNAME=RecVNbot          # имя бота для виджета
DASHBOARD_SESSION_SECRET=      # подписывает cookie; openssl rand -hex 32
SECRET_ENCRYPTION_KEY=         # шифрует строку сессии; openssl rand -hex 32
DASHBOARD_PORT=8005
SNIFFER_MEM_DASHBOARD=256m
```

Без `BOT_TOKEN`, `DASHBOARD_SESSION_SECRET` или `OWNER_CHAT_ID` вход выключен
целиком, и `/healthz` называет, чего именно не хватает.

## 8. Чего здесь нет

- **Уведомлений владельцу.** Бот пишет в личку, когда отвалилась сессия
  юзербота, — это отдельная ветка `feat/session-watchdog`. Одно событие — одно
  сообщение, с подавлением повторов: сервис, который шлёт «сессия отвалилась»
  каждую минуту, отключают в первый же день. Ограничение Telegram: бот не может
  написать первым тому, кто не начинал с ним диалог; владельцу нужно один раз
  нажать «Старт» у `@RecVNbot`, `chat_id` уже сохранён в настройках.
- **Записи `last_ok_at` из коллектора.** Методы `mark_ok` / `mark_failed` в
  репозитории есть и покрыты тестами, но вызывать их будет коллектор — его тела
  пока нет (`feat/collector-ingest`). До этого момента страница покажет сессию
  без последнего успеха.
- **Правки на живой Postgres.** Новые таблицы накатываются вручную (раздел 5).
- **Фильтров и пагинации в логе.** Показываются последние 50 запросов и 200
  реплик переписки. Потолки стоят затем, чтобы через год страница не начала
  тянуть всю таблицу; фильтры добавятся, когда станет тесно.
