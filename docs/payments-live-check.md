# Проверка оплаты звёздами без списаний

Пошаговая проверка для владельца бота: что убедиться в Telegram живьём до того, как оплату
увидит клиент. Автотесты проверяют **нашу** логику на записанных ответах; поведение сервера
Telegram моками не проверить, и записать эти ответы можно только живьём. Порядок такой:
чтение, создание ссылок без оплаты, тестовая среда, пилот.

Правила проверки (нарушать нельзя):

- **Токен не печатать и не вставлять ни в чат, ни в лог.** Во всех командах ниже он
  читается из `.env` в переменную и нигде не выводится. Не включайте `-Verbose` и не
  копируйте адрес запроса: в нём токен.
- До шага 4 ничего не списывается: шаги 1–3 читают данные и создают ссылки, которые никто не
  оплачивает. Звёзды тратит только шаг 5, и то по вашему решению.
- В базу только `SELECT`. Идентификаторы клиентов и платежей в скриншотах и сообщениях
  закрывайте.
- Тестовую среду поднимают **отдельно** от боевой: свой токен, своя база, свой экземпляр.

## Шаг 0. До выкладки: подтвердить дефект Д1 в боевом боте (2 минуты, без кода)

Нужен только пока в проде старая версия, которая слала счёт сообщением. Нажать «🔔 Следить за
новыми — 1 ⭐/мес» под любой выдачей, под присланным счётом нажать **Pay** и посмотреть форму
оплаты: есть ли формулировка о ежемесячном списании (подписка) или это разовая сумма. Форму
закрыть, не подтверждая: списание происходит только после подтверждения в форме. Сохранить
скриншот. Нет «ежемесячно» — Д1 подтверждён: подписочный параметр у `sendInvoice` не
существует, и клиент покупал разовый платёж. Если форма не открывается у владельца бота
(неофициально, это так бывает), повторить со второго аккаунта.

## Шаг 1. Чтение через Bot API (ничего не создаёт и не списывает)

```powershell
$t = ((Get-Content .env | Where-Object { $_ -like 'BOT_TOKEN=*' }) -replace '^BOT_TOKEN=','').Trim()
$api = "https://api.telegram.org/bot$t"
Invoke-RestMethod "$api/getMe"                          # токен рабочий, username тот
Invoke-RestMethod "$api/getMyStarBalance"               # баланс звёзд бота (ожидаемо 0)
Invoke-RestMethod "$api/getStarTransactions?limit=5"    # история (ожидаемо пуста)
```

Записать: порядок выдачи `getStarTransactions` (новые сначала или старые) — это снимает
неизвестное U6 и понадобится сверке платежей.

## Шаг 2. `createInvoiceLink`: ссылка создаётся, списаний нет

Положительная проба и отрицательные, каждая со своим ожидаемым ответом. Ссылку никто не
оплачивает.

```powershell
function Probe([hashtable]$over) {
  $b = @{ title='Probe'; description='probe, do not pay'; payload='probe:1'; currency='XTR';
          prices=@(@{label='month'; amount=10}); subscription_period=2592000 }
  foreach ($k in $over.Keys) { $b[$k] = $over[$k] }
  try   { (Invoke-RestMethod -Method Post -Uri "$api/createInvoiceLink" -ContentType 'application/json' -Body ($b | ConvertTo-Json -Depth 5)).result }
  catch { $_.ErrorDetails.Message }
}
Probe @{}                                                      # ожидается ссылка вида https://t.me/$...
Probe @{ prices=@(@{label='month'; amount=0}) }                # ошибка про положительную цену (как 01.09.2026)
Probe @{ subscription_period=86400 }                           # SUBSCRIPTION_PERIOD_INVALID (как 01.09.2026)
Probe @{ prices=@(@{label='month'; amount=10001}) }            # проверка потолка 10000; текст ошибки не документирован
Probe @{ prices=@(@{label='a'; amount=5}, @{label='b'; amount=5}) }   # две позиции для XTR
Probe @{ currency='USD' }                                      # подписка не в XTR
```

## Шаг 3. Форма подписки без оплаты

Открыть ссылку из шага 2 (или выданную самим ботом: `/subscription` → «Принимаю условия,
перейти к оплате») со **второго** аккаунта. Форма должна показать подписку «10 ⭐ в месяц»
(формулировка зависит от клиента и языка). Закрыть, не оплачивая. Если форма разовая, а не
подписочная при `subscription_period`, — это находка для U1: остановиться и написать.

Заодно проверить глазами в клиенте Telegram: в `/terms` написано, где отменяют подписку
(«Настройки → Мои звёзды → подписки») — сверить подпись пунктов с реальной.

## Шаг 4. Тестовая среда Telegram (звёзды там бесплатны)

Тестовая среда — отдельный мир со своими аккаунтами и ботами; платежи звёздами там проверяют
без списаний ([руководство](https://core.telegram.org/bots/payments-stars#testing-payments)).

1. Завести тестовый аккаунт: Telegram Desktop, Настройки, `Shift+Alt` + правый клик по «Add
   Account», «Test Server»; iOS: десять нажатий на значок настроек, затем аккаунты, тестовый
   вход. Лимиты на флуд в тестовой среде не повышены.
2. В **тестовом** @BotFather создать бота и получить его токен. Как получить тестовые
   звёзды, документация не описывает: посмотреть в кошельке тестового аккаунта.
3. Запустить **отдельный** экземпляр бота: другая база (не боевая), `.env` с токеном
   тестового бота, `TELEGRAM_ENV=test`, `OWNER_CHAT_ID` — id тестового аккаунта владельца,
   `PAYSUPPORT_REPLY_HOURS` по желанию. Схема в тестовой базе накатывается так же, как
   на сервере (`infra/sql/[0-9][0-9][0-9]_*.sql` по алфавиту). Токен тестового бота в боевой
   среде не работает, и наоборот: перепутать нечем.
4. Прогнать сценарии и записать, что видно. Платёж и его сырой JSON лежат в базе
   (`payments.raw`), события подписки — в `billing_events`; запросы только на чтение:

```sql
SELECT external_id, kind, status, amount, is_recurring, is_first_recurring, period_end, refunded_at
FROM payments ORDER BY id DESC LIMIT 5;
SELECT kind, tg_user_id, charge_id, payload FROM billing_events ORDER BY id DESC LIMIT 10;
SELECT version, accepted_at FROM user_consents ORDER BY accepted_at DESC LIMIT 5;
```

| № | Сценарий | Что фиксируем | Ожидаемое поведение бота |
|---|---|---|---|
| S1 | Первая подписка по ссылке из `/subscription` | поля `successful_payment`: `is_first_recurring`, `is_recurring`, `subscription_expiration_date`, `telegram_payment_charge_id`; время ответа на `pre_checkout` | платёж в `payments` (`kind='first'`, срок от Telegram), клиенту «Оплата получена…» с датой |
| S2 | Повторное открытие и оплата той же ссылки (с того же и с другого устройства) | что видит пользователь; создаётся ли вторая подписка | до оплаты второй раз бот ничего не отвергает (защита по намерениям — следующая работа); два платежа — две записи, у каждой свой charge id |
| S3 | Две подписки одного пользователя (два раза `/subscription`) | как они выглядят в клиенте; различаются ли апдейты по `invoice_payload` | у каждой своя нагрузка (соль), экран перед второй говорит «у вас 1 подписка» |
| S4 | Отмена в клиенте и возобновление | апдейты `subscription` (`canceled`, `active`); доступ до даты | строки `sub_canceled` / `sub_active` в `billing_events`, слот не меняется |
| S5 | Нехватка звёзд к дате продления (если в тесте разрешён короткий `subscription_period`) | `failed`; что после пополнения; поздний платёж | строка `sub_failed`; поздний платёж приходит как продление |
| S6 | Продление | нет ли `pre_checkout`; тот же ли `invoice_payload`; новый ли charge id; нет ли `is_first_recurring` | `kind='renewal'`, ответ «Подписка продлена до…» (не «Оплата получена»); если `pre_checkout` пришёл — он проходит (согласие с версией из счёта записано) |
| S7 | `/refund <charge_id>` для первого платежа и для продления, затем та же команда второй раз | эффект на подписку (U4); сообщение `refunded_payment`; **точный текст ошибки повторного возврата** (бот ищет в нём `CHARGE_ALREADY_REFUNDED`: если Telegram пишет иначе, поправить `already_refunded`) | `status='refunded'`, клиенту «Платёж возвращён», продление отключено; повтор команды — успех |
| S8 | `editUserStarSubscription(True)` по первому и по последнему charge id; затем `False` | какой id принимается (U3); может ли пользователь вернуть подписку | бот вызывает по самому раннему платежу подписки; если Telegram принимает другой id — править |
| S9 | `getStarTransactions` после платежей | порядок, пагинация, наличие `invoice_payload` и `subscription_period` (U6) | бот его пока не вызывает: фиксируем для сверки |
| S10 | `sendInvoice` с `subscription_period` (как в прежнем коде) | что показывает форма и что приходит (U1) | закрывает FLOW-31; наш бот так больше не шлёт |
| S11 | Остановить бота посреди обработки платежа и поднять заново | есть ли платёж в `payments` | платёж, не успевший записаться, сообщается владельцу; без сверки (следующая работа) возможна потеря: отметить |
| S12 | Владелец бота платит собственную ссылку | возможно ли (U8) | при невозможности нужен второй аккаунт для всех тестов |

Дополнительно на S1: купить по **чужой** ссылке (переслать ссылку другому аккаунту) — бот
обязан отказать в окне оплаты словами «счёт выписан для другого аккаунта», звёзды не
списываются. И по устаревшей: оплатить счёт после смены цены (поменять
`SUBSCRIPTION_STARS` в тестовом экземпляре) — отказ «цена изменилась».

## Шаг 5. Пилот в проде (по желанию, платит реальный аккаунт)

Только после зелёных сценариев тестовой среды и выкладки. Чек-лист перед пилотом:

- включена двухфакторная проверка на аккаунте, которому принадлежит бот;
- **темы в личных чатах бота выключены** в @BotFather: при них Telegram удерживает 15% с
  каждой покупки звёздами (ToS 6.2.6);
- `OWNER_CHAT_ID` задан (иначе экран «Подписка» говорит, что оформление недоступно);
- `/terms`, `/paysupport`, `/support` отвечают; `/subscription` показывает цифры;
- резервная копия базы включает `payments`, `user_consents`, `billing_events` (требование
  Telegram: платёжные данные не терять).

Пилот: подписка со второго реального аккаунта на 10 звёзд (минимальный пакет). Либо возврат
сразу (`/refund`), либо оставить до первого продления (через 30 суток), чтобы на проде
закрыть U2, U3 и U5. Стоимость порядка 0,13 USD чистыми, если не возвращать (ToS 6.2.4).

## Шаг 6. Слот и слежение (S13): перед включением продажи

Только в тестовой среде Telegram (шаг 4) либо пилот владельца (шаг 5). `SALES_ENABLED=true`
ставится на время проверки, потом снова `false`, пока всё не пройдено.

1. Любая выдача с предложением подписки → кнопка «Подписка — 10 ⭐/мес» открывает экран с
   цифрами (раньше был ответ-заглушка «оформление не открыто»). Кнопка «Следить за новыми» цены
   не несёт.
2. Условия → согласие → оплата. Ожидаемо: в ответе «слот слежения свободен: откройте /requests
   и нажмите «Следить»» (а не «подписка действует»); `SELECT count(*) FROM payments` вырос на
   один, `kind = 'first'`.
3. «Следить» у поиска → «Слежение включено»; в `subscriptions` строка с `expires_at` =
   `payments.period_end`. Второй поиск → предложение «Перенести слот с …» и «Добавить слот».
4. «Перенести слот» → монитор берёт второй поиск, прежний на паузе (⌛), строки не удалены.
5. `/refund <charge_id>` → статус платежа `refunding`, затем `refunded`; слот снят сразу;
   сообщение `refunded_payment` НЕ приходит владельцу как «возврат не через бота».
6. Остановить `sniffer-notifier` на 20 минут после оплаты, поднять: сверка находит платёж без
   записи (если обработчик его потерял) — иначе в логе `service.tick` без расхождений.

## Что остаётся неизвестным, пока не проверено живьём

| № | Неизвестное | Чем снять |
|---|---|---|
| U1 | принимает ли сервер `subscription_period` в `sendInvoice` и что показывает форма | шаг 0 или S10 |
| U2 | присылается ли `pre_checkout_query` на автопродление | S6 |
| U3 | отдельный ли charge id у каждого продления; какой id нужен `editUserStarSubscription` | S6, S8 |
| U4 | отменяет ли возврат платежа подписку | S7 |
| U5 | сколько попыток и какой льготный срок при `failed`; придёт ли поздний платёж | S5, затем пилот |
| U6 | порядок и пагинация `getStarTransactions` | шаг 1, S9 |
| U7 | как получить тестовые звёзды; разрешены ли короткие `subscription_period` | шаг 4 |
| U8 | может ли владелец бота платить собственный счёт | S12 |
| U9 | срок жизни ссылки на счёт | наблюдение |
| U10 | доставка `successful_payment` после простоя более 24 часов | не проверяется, закрывается сверкой |
| U11 | как возврат выглядит в `getStarTransactions`: исходящая запись с тем же id или иначе; адаптер `AiogramBotApi.star_transactions` читает именно так | шаг 1, S9; от ответа зависит `StarsReconciler._mark_refunds` |
| U12 | работает ли весь путь «оплата → слот → слежение»: кнопка «Подписка» → экран с цифрами → оплата → «Следить» → карточка слежения | S13 ниже; продажу включать (`SALES_ENABLED=true`) только после него |

Результаты (скриншоты форм, JSON платежей, ответы на пробы) сохранить в
`tests/fixtures/payments/` без токенов и идентификаторов клиентов: по ним пишутся тесты на
записанных ответах, и порядок «тестовая среда, затем фикстуры, затем CI» держится именно на них.
