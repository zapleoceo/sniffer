# Два агента SnifferBot: план перехода

Статус: по запросу владельца начато поэтапное внедрение в новой ветке
`codex/two-agent-mcp`. Дата: 03.09.2026. Изменения AIbroker — в отдельной ветке
`codex/sniffer-native-tools`. До завершения ворот пилот и production не переключаются.
Каждая фича — отдельный коммит с тестами, документацией и проверкой другой моделью.

## 1. Решение простыми словами

Один агент разговаривает с человеком и ищет в готовом каталоге. Второй агент
раз в час разбирает задания: где собрать объявления, что обновить и какие
характеристики извлечь. Они передают работу через сохранённые задания, а не
через бесконечную переписку друг с другом.

MCP — интерфейс разрешённых действий. Это не сама модель, не планировщик
запусков и не гарантия правильного JSON. Между моделью и MCP нужен исполнитель:
он проверяет действие, вызывает инструмент, возвращает результат модели и
останавливает цикл по лимиту.

Два агента — две роли, а не требование оставить ровно два процесса. Сохраняем
Postgres, адаптеры источников, доставку уведомлений и технический сборщик.
Модель решает, что искать; скачивание страниц, SQL, расписание и отправку
сообщений выполняет обычный проверяемый код.

## 2. Что получает пользователь

Пример: «Нужен скутер» → «В каком городе?» → «Дананг, до 500 долларов».
Город и бюджет берём из одного ответа, автомат следует из слова «скутер».
Агент читает каталог и показывает найденное со ссылками и датой проверки.

Если данных недостаточно: «В базе сейчас нет подходящих свежих вариантов.
Задание на обновление создано; ближайший запуск — в …». Час запуска и статус
берутся из системы. Обещания «найду через час» нет: запуск не гарантирует находку.
Уведомление о результате — только если пользователь согласился и имеет право
на него по действующим правилам подписки; иначе результат доступен в запросе.

У каждого клиента несколько независимых запросов. Сохраняем меню «Мои запросы»:
выбрать, уточнить, повторить, включить/выключить мониторинг, посмотреть статус.
Состояние запроса и статус задачи сбора — разные вещи. Изменение запроса создаёт
новую версию; старое задание не подменяет новые условия поиска.

До первого поиска — только недостающие важные сведения, ориентир 0–3 разных
уточнения. Названное повторно не спрашиваем; бюджет можно явно пропустить.
Если человек всё ещё не определился, сохраняем черновик и предлагаем понятный
выбор, а не запускаем цикл одинаковых вопросов и не выдумываем параметры.

## 3. Полномочия

| Действие | Главный агент | Агент-сборщик |
|---|---|---|
| Читать опубликованный каталог и его свежесть | Да | Да |
| Читать/изменять запросы и мониторинг текущего клиента | Через ограниченные инструменты | Нет |
| Создать задание на сбор, узнать его статус | Да | Взять и исполнить выданное задание |
| Читать разрешённые источники | Нет в первой версии | Через существующие адаптеры |
| Добавлять/обновлять объявления | Нет | Через проверку и версионирование |
| Предложить новый атрибут/источник/изменение структуры | Да | Да |
| Выполнить SQL, ALTER/DROP, получить секреты или shell | Нет | Нет |

Сервер MCP проверяет права сам. Идентификатор клиента поступает из доверенной
сессии приложения, а не из аргумента, придуманного моделью. Разные служебные
учётные записи и права БД; запрет нельзя обойти выбором другого инструмента.
MCP не публикуем в интернете. Транспорт, аутентификацию и версию SDK фиксируем
после прототипа; даже во внутренней сети проверка роли обязательна.

Права сборщика ограничены также конкретным заданием. `sources.collect` и
`catalog.stage` проверяют task_id, действующий lease_token, разрешённые источники,
область и остаток лимита. Агент не расширяет область аргументами вызова. Попытка
выйти за неё отклоняется до обращения к источнику или изменения записи.

Объявления — недоверенные данные, а не инструкции. Коллектор не может исполнить
«удали таблицу» или «отправь токен», встреченное в тексте. Доступ к источникам
ограничен адаптерами/реестром; обходы через редиректы, внутренние адреса и SSRF
должны блокироваться кодом. Личные переписки не уходят в задания общего сбора.

## 4. Что означает «перестроить БД»

1. Новые факты: агент предлагает запись; валидатор проверяет источник, типы,
   идентичность объявления и непротиворечивость. Проверенное публикуется.
2. Новые характеристики: значение хранится в JSONB с версией словаря и
   доказательством из источника. Неизвестный атрибут сначала кандидат, он не
   становится обязательным фильтром и не меняет смысл существующего поля.
3. Новые категории, индексы, таблицы и типы: предложение изменения. Разработчик
   готовит миграцию, тестирует и отдаёт на подтверждение/обычный CI-деплой.
   Модель не применяет DDL к рабочей базе.

В текущем коде категории — Python enum, а наборы атрибутов/поисковые веса заданы
кодом. Поэтому обещать «любой новый предмет автоматически» сейчас нельзя.
Первая версия поддерживает действующие категории и источники. Переход к
универсальному реестру категорий — отдельное расширение после проверки MVP.

## 5. Как работает часовой сбор

- Серверный регламент, не Codex-задача и не таймер внутри модели, раз в час
  запускает один ограниченный проход. Без работы LLM не вызывается.
- Сначала подбираются ожидающие задания; просроченные данные обновляются по
  политике свежести и спросу. Однотипные задания объединяются по смыслу и области
  сбора, но статусы и запросы разных клиентов остаются приватными.
- Существующий технический Telegram-сбор каждые 15 минут предлагается сохранить:
  час относится к агентскому планированию/пополнению. Если нужен строго часовой
  сбор вообще всего, принимаем ухудшение свежести до часа плюс время обработки.
- До следующего запуска можно ждать почти час. При очереди, лимитах источников
  или повторной попытке — дольше. Интерфейс показывает фактическое состояние.
- Задание имеет область, тип, приоритет, срок, лимит страниц/записей/вызовов/
  денег, число попыток и ссылку на версию запроса. Модель не повышает свои лимиты.
- Состояния: ожидает → выполняется → выполнено / частично / отложено /
  окончательная ошибка / отменено / требует согласования.
- Выдача задания атомарна; lease с heartbeat и уникальным токеном не позволяет
  старому исполнителю писать после повторного захвата. Есть восстановление
  после падения, конечные повторы и проверка отмены перед публикацией.
- Захват, heartbeat, deadline, подсчёт расходов, повторы и освобождение задания
  выполняет обычный runtime, не модель. Инструменты task lifecycle нужны
  исполнителю; задержка ответа LLM не должна останавливать продление lease.
- Вызовы модели и источников идут вне транзакции. Повторная доставка задания
  допустима; повторный логический результат не создаёт дублей записей/outbox.
- При смене или паузе запроса устаревшие результаты не отправляются клиенту.
  Общий сбор не отменяется, если он ещё нужен другому действующему запросу.

Ограничения Telegram сохраняем: один владелец MTProto-сессии; никаких сообщений,
реакций и прочтений от userbot. Join/mute — только через существующие ограниченные
операции: не более 10 попыток join за скользящие сутки, интервал не меньше часа,
FloodWait останавливает до конца суток, минимум на 12 часов. Часовой регламент
не отменяет этих ограничений.

## 6. Данные и минимальные инструменты MCP

Сохраняем сырьё, объявления, паспорта, подписки и outbox. Добавляем/расширяем:
задания сбора и подписчиков на результат, сведения о покрытии источников,
версионированные наблюдения/изменения, предложения новых атрибутов, журнал
вызовов инструментов. Не копируем весь каталог в контекст модели.

У каждого используемого факта: source/id/ссылка, posted_at если известно,
fetched_at, verified_at, версия извлечения. Отсутствие подтверждения не считается
подтверждением; недоступность источника не означает продажу или отсутствие лотов.
Конфликтующие значения сохраняются с происхождением, не перезаписываются молча.
Карточки со ссылками/ценами формирует приложение из опубликованных записей.

Особая работа при переносе: сейчас `sources/catalog_sink.py` переносит city,
category, deal_type и price_period из паспорта пользователя. В новой системе
паспорт задаёт только фильтры. Эти поля извлекаются независимо из источника;
каждое имеет evidence либо отметку inference/unknown. Поиск в Дананге не делает
объявление из Нячанга объявлением из Дананга. Если город не доказан — он неизвестен.
Старые записи без происхождения полей перепроверяются либо остаются с признаком
неизвестной достоверности. Простая смена verified_at не делает их проверенными.

Примеры инструментов (контракты уточняются на этапе 1):

- Главный: `catalog.search`, `catalog.coverage`, `requests.list/get/update`,
  `monitoring.set`, `collection.request/status`, `schema.propose`.
- Сборщик: `tasks.claim/heartbeat/complete/fail`, `sources.collect`,
  `catalog.stage`, `schema.propose`. Публикация — контролируемая операция после
  валидации, а не право произвольно обновить любую строку.

`catalog.coverage` различает: свежие данные без совпадений; ещё не собирали;
собирали давно; ошибка источника; нет нужной характеристики; неподдерживаемый
источник/категория. Задания создаются по реальному пробелу, с dedup/cooldown,
а не после каждого пустого ответа. Невозможный бюджет не порождает вечный сбор.

## 7. План внедрения и ворота проверки

| Этап | Что делаем | Как проверяем до перехода дальше |
|---|---|---|
| 0. Проверить агентский исполнитель | Маленький стенд: модель выбирает безопасный инструмент, получает результат и отвечает. Проверяем native tool calling через AIbroker, результаты и ошибки на каждом провайдере/fallback. | Полный цикл tool→result→final с tool_call_id; пустой text при корректном tool_calls не ошибка; обрезание, отказ, неверные аргументы, таймаут. | 1. | 4. | 5. Контролируемое развитие структуры | Кандидаты атрибутов и предложения миграций; одобренное изменение через тесты и деплой. | Предложение не меняет схему; старые запросы читаются; неверный тип изолирован; миграция проверена на копии и имеет путь отката. |

Переключение/откат во время сбора и готового уведомления не дают двойной публикации, доставки или зависшего задания. |

Переиспользуем нынешний стек Python/Postgres, без обязательного Redis/RabbitMQ.
Существующие jobs — заготовка, а не готовый агентский исполнитель: реального
потребителя, lease/reclaim и защиты завершения старым исполнителем сейчас нет.
Существующий внешний catalog upsert не обновляет конфликтующую запись — это
нужно исправить до обещания обновлять объявления раз в час.

Переключение включает владельца записи, не только ответ бота. Прекращаем выдачу
задач отключаемому пути, завершаем либо отзываем его активные lease, публикацию
разрешаем только выбранному пути через единую границу. Доставка остаётся у
одного notifier с проверкой актуальности и дедупликацией. Старый `remember()`
не должен параллельно возвращать недоказанные поля в проверенный каталог.
На весь пилот схема и форматы заданий совместимы со старой версией; разрушительных
миграций нет. Откат не удаляет данные, историю дедупликации или outbox.
До пилота фиксируем измеренные исходные показатели и пороги допуска: ноль утечек,
несанкционированных записей и повторных публикаций; релевантность не хуже базовой;
целевые p95 времени и расход на запрос согласованы после стенда, а не выдуманы.

## 8. Реализуемость и главный технический риск

AIbroker сейчас принимает messages/response_format и возвращает text. Его
ChatRequest/ChatMessage не передают native tools/tool_choice/tool_calls/tool_call_id
по всей цепочке. Он не является MCP-клиентом. Для рекомендуемого варианта нужен
agent runtime в SnifferBot и поддержка native tool calls в брокере end-to-end:
вход → очередь → провайдер → результат → следующий шаг. Fallback разрешён только
между провайдерами, прошедшими тест контракта инструментов.

Это отдельный межрепозиторный этап, не замена `prefilter` на `chat:sales`.
По требованию владельца ВСЕ обращения к моделям идут только через AIbroker;
прямой провайдерский клиент не является запасным путём. Не принимаем большую
текстовую JSON-инструкцию с действиями за готовую поддержку MCP. Если брокер
не поддерживает нужный контракт, новый режим остаётся отключённым до доработки.

Цель защиты от JSON-ошибок — исключить выполнение неверного действия и запись
невалидных данных. Нельзя гарантировать, что внешний провайдер никогда не вернёт
обрезанный ответ. Сравниваем увеличение выходного бюджета, компактные/небольшие
пачки и native tool calling. Во всех вариантах обязательны проверка схемы и
полноты до применения, ограниченные повторы и прозрачная диагностика.

Контракт безопасности: malformed/truncated/refusal/unknown-tool/invalid-arguments
ответ отклоняется ДО MCP, с нулём побочных эффектов. Runtime проверяет envelope,
разрешённое имя, полную схему аргументов и лимиты, пишет диагностический результат
и лишь затем решает о допустимом ограниченном повторе. На этапе 0 тесты отсутствующих
и лишних полей, неверных типов, превышения диапазонов и всех перечисленных отказов
обязаны проверять счётчик выполненных действий: строго ноль. Процент успешных
ответов провайдера измеряется отдельно и не подменяет эту гарантию.

MCP использует типизированные сообщения, но модель всё ещё может дать неверные
аргументы. Исполнитель проверяет их до побочного эффекта, сохраняет stop/length/
refusal и идентификаторы, ограничивает повтор исправления и число шагов. Для
извлечения большой пачки — отдельный достаточный бюджет или небольшие пачки;
не повторяем нынешнюю ситуацию 12 карточек / 896 токенов.

Каждое действие имеет устойчивый idempotency key и журнал результата. При
смене провайдера или рестарте уже выполненный write не повторяется как новый:
исполнитель передаёт сохранённый результат. Неизвестный исход сверяется с
операцией в БД до повтора. Нельзя перезапускать всю цепочку действий вслепую.

Начальные пределы для стенда, не обещание производительности: главный — до
4 инструментов и жёсткого общего deadline; сборщик — конечный лимит шагов на
задачу и времени на проход. Точные deadline, batch size и дневной cap выбираем
по измерению на этапе 0. В режиме деградации остаются меню и детерминированный
поиск по сохранённому паспорту, а не бесконечное ожидание LLM.

Внешние модели не требуют отдельного GPU на сервере. Но сервер общий: перед
пилотом измеряем память/соединения/очередь и выставляем лимиты, без обещания
добавить неограниченную параллельность. Почасовой запуск не делает каждый
пользовательский ответ зависимым от часового сборщика.

## 9. Проверка плана агентами

Первичный аудит выполнен тремя независимыми агентами: текущий код и миграция;
MCP/права/надёжность; модельный runtime и брокер. Найденные замечания внесены:
нет native tools; очередь не готова; upsert не обновляет; MCP не лечит JSON;
категории не полностью динамические; часовой сбор меняет обещания свежести.

После чтения полного документа и повторной проверки исправлений получены
окончательные вердикты:

| Область | Проверяющий агент | Итог |
|---|---|---|
| Этапы 1, 2, 4, 6: соответствие текущему коду и переход | migration_feasibility | PASS |
| Этапы 1, 2, 3, 5, 6: права и безопасность | mcp_security_review | PASS |
| Этапы 0, 3, 4 и весь план целиком: runtime и зависимости | agent_runtime_feasibility | PASS |

Первоначальные FAIL по происхождению полей, области полномочий задания и откату
устранены и перепроверены. Это архитектурная проверка, не утверждение о выполненных
нагрузочных испытаниях или о том, что новая система уже работает. Реализуемость
подтверждена как план с обязательными воротами; качество/стоимость/скорость
подтверждаются стендом и пилотом, не мнением проверяющего.
