# SnifferBot — архитектура

> Агент в Telegram, который выясняет у клиента, что ему нужно, формирует
> **паспорт запроса**, показывает актуальные предложения из телеграм-сообществ
> и присылает новые по мере появления.

> **Дополнено [spec-v2.md](spec-v2.md).** Там источники перестали быть
> курируемым списком чатов и превратились в реестр адаптеров с планировщиком,
> добавился обязательный verifier и задел под публичный доступ. Где документы
> расходятся, верен spec-v2.

## 1. Что делаем и чего не делаем

**Делаем:** диалог → структурированный паспорт запроса → подбор из уже
собранных объявлений + живой поиск по чатам → подписка на новые совпадения.

**Не делаем (сознательно):**

| Не делаем | Почему |
|---|---|
| Не перепечатываем объявления | отдаём ссылку на оригинал; снимает вопрос ответственности за чужой контент и контакты. Форма ссылки зависит от чата: у публичной группы `t.me/<username>/<msg>` (открывается у кого угодно), у закрытой — `t.me/c/<chat>/<msg>` (только для участников), в форуме между ними встаёт номер темы — [spec-v2, 4.4](spec-v2.md#44-telegram-группы--что-стоило-дорого-узнать) |
| Не пишем от имени юзербота | любое исходящее действие с userbot-аккаунта кратно повышает риск бана; аккаунт только читает |
| Не сводим людей и не берём комиссию | это поисковый помощник, а не маркетплейс — нет эскроу, нет модерации сделок, нет ответственности за них |
| Не держим базу контактов продавцов | контакт живёт внутри исходного сообщения, мы храним ссылку |

Первый рынок — **Нячанг**: байки, апартаменты и комнаты. Категории и город
задаются данными, а не кодом: добавить «Дананг + скутеры» — это строки в
таблицах, а не релиз.

## 2. Ключевое решение — паспорт запроса

Разница между поисковой строкой и агентом ровно одна: **агент хранит намерение
клиента как объект и переиспользует его**. Паспорт — центральная сущность, из
неё растёт всё остальное:

```
паспорт → запрос к базе (что есть сейчас)
паспорт → ключевые слова для живого поиска по чатам
паспорт → фильтр подписки (что присылать потом)
паспорт → критерии ранжирования (почему это в топе)
паспорт ← обратная связь «дорого» / «не то» уточняет паспорт
```

Один и тот же объект обслуживает и разовый подбор, и подписку. Поэтому
подписка — не отдельная фича, а **статус паспорта** (`active`).

Полная схема полей: [passport.md](passport.md).

**Правило диалога: задаём только те вопросы, которые реально сужают выдачу.**
Для байка в Нячанге бюджет и «автомат или механика» режут выборку вдвое, а цвет
не режет почти никак. Агент оценивает, сколько кандидатов отсекает каждое
незаполненное поле, и спрашивает максимум два-три самых информативных. Допрос
из десяти вопросов убивает конверсию сильнее, чем неточная выдача.

## 3. Компоненты

```
                    ┌──────────────────────────────────────┐
   клиент  ────────►│  bot (aiogram 3)                     │
   в Telegram       │  диалог, паспорт, выдача, подписки   │
                    └───────┬──────────────────────▲───────┘
                            │                      │ уведомления
                            ▼                      │
                    ┌──────────────────────────────┴───────┐
                    │  Postgres                            │
                    │  chats · raw_messages · listings     │
                    │  passports · subscriptions · outbox  │
                    └───▲──────────────▲───────────────▲───┘
                        │              │               │
       ингест ──────────┘              │               └──── матчинг и рассылка
                        │              │                          │
        ┌───────────────┴───────┐  ┌───┴──────────────┐  ┌────────┴─────────┐
        │ collector (Telethon)  │  │ worker           │  │ notifier         │
        │ live-подписка на чаты │  │ воронка обработки│  │ дедуп, троттлинг │
        │ messages.search       │  │ извлечение карточ│  │ digest / instant │
        └───────────┬───────────┘  └───────┬──────────┘  └──────────────────┘
                    │                      │
                    │              ┌───────▼──────────────────────────┐
                    │              │ AIbroker  aib.zapleo.com         │
                    │              │ prefilter · structured · fast    │
                    │              └──────────────────────────────────┘
                    ▼
            ┌───────────────┐
            │ Telegram      │   фото не храним: из них берём только
            │ MTProto       │   перцептивный хеш для дедупа кросспостов
            └───────────────┘   (roadmap.md, волна 5)
```

Пять процессов на одной машине, общаются **только через Postgres** — брокер
сообщений не нужен, очередь делается на `SELECT … FOR UPDATE SKIP LOCKED`. Это
осознанный отказ от Redis и RabbitMQ: на таком объёме они добавляют
операционную сложность и не решают ни одной реальной проблемы.

Последний из пяти — `dashboard`, веб-интерфейс владельца, и он же единственный,
который слушает порт. В остальных документах он назван **шестым контейнером**:
контейнеров шесть, потому что к пяти процессам добавляется Postgres. До
31.08.2026 «ни один процесс не слушает порт» было записано здесь как свойство
архитектуры; требование владельца его отменило.

| Процесс | Ответственность | Почему отдельный |
|---|---|---|
| `bot` | диалог, показ карточек, управление подписками | падение ингеста не должно ронять общение с клиентом |
| `collector` | единственный держатель MTProto-сессии | сессия одна на аккаунт; два процесса с одной сессией дают `AuthKeyDuplicated` |
| `worker` | воронка: гейт → минимальная карточка → нормализация → матчинг; плюс уборка сырья по сроку хранения | тяжёлый и перезапускаемый, его можно убить без потерь |
| `notifier` | доставка с троттлингом | доставка обязана переживать рестарт воркера, отсюда таблица `outbox` |
| `dashboard` | интерфейс владельца: лог запросов, расходы, переписка, сессия | единственный процесс с HTTP; падение страницы не должно ронять ни диалог, ни ингест — [dashboard.md](dashboard.md) |

### 3.1 Точки входа

У каждого процесса свой `__main__.py`, ровно те пять команд, что стоят в
`docker-compose.yml`:

```
python -m sniffer.bot         диалог и выдача (aiogram, long polling)
python -m sniffer.collector   MTProto-сессия, чтение сообществ
python -m sniffer.worker      воронка, очередь jobs, уборка сырья
python -m sniffer.notifier    доставка из outbox
python -m sniffer.dashboard   интерфейс владельца (uvicorn, порт 8005)
```

Общий каркас — `sniffer/runtime/`: настройка лога, обработка сигналов и
холостой цикл. Слоем он не является, бизнес-логики в нём нет; он существует,
чтобы пять точек входа не описывали одно и то же пятью способами.

Шестой `__main__` — `python -m sniffer.simulation` — в этом списке не стоит и в
`docker-compose.yml` его нет: это не сервис, а измерительный инструмент.
Отрабатывает и выходит, сети, модели и базы не требует, печатает таблицу
«сценарий → метрики → вердикт» по качеству диалога. Живёт в `src/`, а не в
`scripts/`, ровно потому, что запускать его надо и в CI, и в боевом контейнере:
зелёный прогон на раннере не доказывает, что на сервере то же самое, а тестов
образ не везёт. Что он меряет — [passport.md, «Симуляция диалога»](passport.md#симуляция-диалога--качество-в-цифрах).

**Процесс без обязательной настройки не падает.** Он пишет в лог, чего именно
не хватает — именами из `.env`, — и уходит ждать, перепроверяя окружение раз в
минуту:

```
{"event": "service.not_configured", "service": "bot", "missing": ["BOT_TOKEN"],
 "message": "не настроен: нет BOT_TOKEN, жду конфигурации"}
```

Причина конкретная: контейнер, перезапускающийся каждые пять секунд, выглядит
как сломанный деплой и заваливает healthcheck, хотя на деле просто не заведён
секрет. Ожидание отличает «не настроен» от «сломан» и в логе, и в `docker ps`.
Перепроверка не декоративная: секрет заводят уже после первого запуска, и
процесс подхватывает его сам, без `docker compose restart`.

Пустой токен и неверный токен — разные вещи. Пустой означает ожидание, неверный
означает падение с внятной ошибкой: молча ждать при опечатке в секрете хуже,
чем упасть.

| Процесс | Без чего не работает |
|---|---|
| `bot` | `BOT_TOKEN` |
| `notifier` | `BOT_TOKEN` — доставка идёт тем же Bot API |
| `collector` | `TG_API_ID`, `TG_API_HASH`, `TG_SESSION`; код подтверждения в фоновом контейнере ввести негде, поэтому строка сессии обязательна — её выдаёт `python -m sniffer.collector auth` ([deploy.md, 3.5](deploy.md#35-авторизация-юзербота)) |
| `worker` | ничего: без базы он просто не найдёт задач |
| `dashboard` | `BOT_TOKEN` (проверить подпись виджета), `DASHBOARD_SESSION_SECRET` (подписать cookie), `OWNER_CHAT_ID` (кого пускать). Не хватает любого — пускать некого и нечем, а открытая страница хуже закрытой |

**Подкоманда — это `auth` и только `auth`.** Любой другой аргумент —
неизвестное имя, опечатка, лишний позиционный — заканчивается кодом 9 и
подсказкой, а не запуском сервиса. Разбор строгий намеренно:
`python -m sniffer.collector notauth` раньше молча уходил в демона, аргумент
терялся, и владелец ждал диалога авторизации, глядя на обычный старт
коллектора.

**Как мы подписаны в Telegram → Настройки → Устройства — общий контракт трёх
точек входа.** Клиента создают `collector/client.py` (разовый вход за строкой
сессии), `sources/telegram_client.py` (боевое чтение) и
`sources/telegram_discover_client.py` (вступление и беззвучный режим).
Telegram считает устройством пару (auth key, подпись клиента), поэтому одна и
та же сессия с разными `device_model` показывается там ДВУМЯ строками — и
владелец, решая, какой сеанс отозвать, не понимает, откуда второй. Подпись
поэтому лежит в `sniffer/telegram_identity.py` — модуле-листе, который видят
все три точки входа и который не создаёт между ними зависимости; расхождение
ловит `tests/test_telegram_identity.py`.

**SIGTERM останавливает, а не убивает.** `docker compose stop` даёт десять
секунд; бот дослушивает текущий апдейт и закрывает сессию, фоновые процессы
выходят из цикла на ближайшей проверке. Лог структурный: JSON в контейнере,
человекочитаемый рендер в терминале, уровень из `LOG_LEVEL`.

Холостой цикл фоновых процессов молчит: «нечего делать» пишется не чаще раза в
пять минут, иначе `max-size: 10m` из compose открутится за час. Пока работа
находится, цикл не спит вовсе — очередь разгребается пачками, а не по таймеру.

## 4. Воронка обработки — где решается стоимость

Главная ошибка в таких ботах — отправлять каждое сообщение в LLM. Лестница
«дёшево → дорого», где каждая ступень отсеивает мусор до того, как он дойдёт до
дорогого слоя:

| # | Ступень | Стоимость | Отсев |
|---|---|---|---|
| 0 | Дедуп: `UNIQUE(chat_id, msg_id)` плюс хэш нормализованного текста | 0 | кросспостинг одного байка в пять групп |
| 1 | Regex-гейт: цена (`$`, `k`, `тр`, `VND`, `triệu`) **и** глагол сделки | 0 | ~85–90% |
| 2 | LLM `prefilter`: «объявление? да/нет», **пачками по 20** | free, кэш 10 мин | ~60% остатка |
| 3 | LLM `structured`: карточка по strict `json_schema` | free | — |
| 4 | Эмбеддинг для семантики | опционально, этап P3 | — |

Батчинг — не оптимизация, а условие бесплатности: 700 сообщений по одному это
700 вызовов, пачками по 20 — тридцать пять. Ровно разница между «влезаем в
free-квоту» и «не влезаем».

## 5. Модель данных

```
chats            справочник отслеживаемых сообществ (курируется вручную)
raw_messages     сырьё как пришло; хранится 90 дней от ingested_at
listings         нормализованная карточка предложения — то, что ищем
listing_media    отпечаток фото (перцептивный хеш) для дедупа кросспостов
sellers          агрегат по автору: частота постинга, скам-скор
users            клиенты бота
passports        паспорт запроса, версионируемый
passport_events  история диалога и обратной связи
subscriptions    активный паспорт плюс политика уведомлений
notifications    что кому уже отправлено (дедуп)
outbox           очередь доставки, переживает рестарт
jobs             внутренняя очередь воронки
client_requests  запрос клиента как единица наблюдения
dialog_messages  переписка с ботом — то, что человек увидел
broker_calls     расход на LLM по каждому вызову
telegram_sessions сессия юзербота, строка зашифрована
```

DDL: [`infra/sql/001_init.sql`](../infra/sql/001_init.sql).

Два решения стоит подсветить отдельно:

- **`raw_messages` и `listings` разделены.** Сырьё живёт 90 дней и удаляется,
  карточки живут дольше и компактны. Будь карточка колонкой в сырье, ретеншн
  удалял бы вместе с мусором и полезное.
- **Паспорт версионируется, а не перезаписывается.** Клиент говорит «дорого» —
  создаётся новая версия с изменённым бюджетом, старая остаётся. Без этого
  невозможно ни отладить агента, ни объяснить клиенту, почему выдача изменилась.

### 5.0 Срок хранения сырья — «крон», который живёт в коде

`raw_messages` растёт с каждым проходом коллектора и ничем не ограничен сверху.
Схема с самого начала обещала TTL 30 дней «чистится кроном» — и это было
неправдой: ни крона, ни какой-либо уборки не существовало до 01.09.2026.
Комментарий в DDL при этом читался как описание работающего механизма, что
хуже честного «не сделано»: заметить такое можно только по выросшему диску.

Теперь срок — **90 дней** (решение владельца), а уборку делает воркер, раз в
сутки, пачками по тысяче строк (`worker/retention.py`). Три решения, которые
там приняты, стоят объяснения:

**Не системный `crontab`.** Состояние машины определяется репозиторием: строчка
в crontab не попадёт ни в один диff, не переживёт пересборку машины и не будет
видна тому, кто читает код. Расписание в коде едет тем же деплоем и проверяется
тестами без сервера. Отдельный контейнер ради одного `DELETE` в сутки на общей
машине тоже не оправдан — поэтому уборка живёт в воркере, у которого холостой
цикл уже есть, а уборка воронки и есть работа воронки.

**Считаем от `ingested_at`, а не от `posted_at`.** Срок здесь про диск — «мы
держим скачанное столько-то», — а не про устаревание объявления. По дате
публикации уборка стирала бы догон истории ровно с той скоростью, с какой
коллектор его дочитывает: архив чата уходит на годы назад, и глубокий добор
терял бы смысл целиком.

**Не трогаем сырьё, из которого вышла карточка.** У `listings.raw_message_id`
стоит `ON DELETE CASCADE`: удаление сырья по возрасту унесло бы с собой живую
карточку, показанную клиенту, вместе с текстом, по которому verifier её
сверяет. Поэтому уборка берёт только строки без карточки. Это проверяется
тестом на настоящем Postgres (`test_retention_never_takes_a_listing_down_with_the_raw_message`)
— на подделке каскада нет, и тест был бы зелёным при любой ошибке.

Что этот срок НЕ решает: сырьё, которое воронка не успела разобрать, удалится
вместе с остальным. Пока ступени `extract` нет, всё лежит в `pending`, и через
90 дней самое старое начнёт исчезать необработанным. При работающей воронке
разрыв в 90 дней несоизмерим с её задержкой, но пока её нет — это надо знать.

### 5.0.0 Контур целиком: сырьё → карточка → подписка → доставка

До 01.09.2026 контура не было. Коллектор честно наполнял `raw_messages`, а
дальше всё обрывалось: воркер только убирал старое, `matching/` был пустым
пакетом, `outbox` не наполнял никто, нотифаер возвращал ноль. Накопленная
история групп не превращалась ни в карточки, ни в уведомления.

Теперь звенья такие, и каждое проверено на живом Postgres:

```
raw_messages ──гейт──▶ listings ──подбор──▶ outbox ──доставка──▶ клиент
   collector        worker/archive     worker/matcher      notifier/delivery
                    (+ дедуп по          (по подпискам)     (троттлинг, повтор)
                     отпечатку)
```

**Гейт и минимальная карточка** (`pipeline/archive.py`). LLM не обязателен для
появления карточки: сообщение, прошедшее бесплатный гейт, уже даёт ссылку,
категорию и явно указанную цену. Полное извлечение позже улучшит карточку, но
не блокирует ни поиск, ни подписки.

Категорию гейт узнаёт **внедрённым детектором**, а не своим списком. Знание
«какими словами, марками и моделями зовётся предмет» одно — в словаре поиска
(`CATEGORY_TERMS` плюс `motorbike_models`), — и воркер отдаёт его гейту функцией
`vocabulary.category_hints`; сама воронка про поиск не знает (`pipeline` не
импортирует `search` — обратное ребро слоёв). Раньше гейт держал свою копию
списка марок и моделей, и она разошлась с рынком: honda и vision в ней были, а
sym, kymco, lead, attila — нет, и терсовое «Sym Attila, 15тр» отсеивалось как
«без категории» ещё до базы — тот же дефект, что был у поиска, только на входе.
В самом гейте дефолтом остались лишь стабильные общие слова предмета (скутер,
квартира) — они не дрейфуют, как список моделей.

**Совпадение предмета — тоже работа кода.** Замер 01.09.2026 на пяти
вьетнамских объявлениях о домах и земле: модель ТРИ РАЗА ИЗ ТРЁХ ответила
«подходит» для запроса про мотоцикл. Правила отказа были перечислены по-русски
(«телефон, ноутбук, часы, колонка»), объявление написано по-вьетнамски
(`Bán nhà`, `căn hộ`, `Bán đất`), и связь между ними она не построила. Дописать
вьетнамские слова в список значило бы ждать следующего языка.

Поэтому вопрос к модели теперь другой: не «подходит ли», а **«что это»** — одним
значением из нашего закрытого списка категорий. Назвать предмет она умеет на
любом языке; сравнить две строки умеем мы. `unknown` проходит: непонятное
объявление решает человек, а не мы за него.

Это уже третий случай одного и того же правила в одном модуле, и стоит записать
его прямо: **модели задают вопросы восприятия, а не вопросы решения.** Что
написано в объявлении — восприятие. Влезает ли в бюджет, тот ли это предмет —
решение, и оно детерминированное.

**Арифметику у модели забрали.** Сравнение цены с бюджетом сначала было её
работой вместе со смыслом, и второй замер 01.09.2026 показал, почему так
нельзя: на «до 300 USD» (потолок 7.8 млн) она оставила байки за 10–11 млн, а на
«до 400 USD» (потолок 10.4 млн) отбраковала ВСЁ. Один промпт, соседние запросы,
противоположная строгость — это разброс, а не ошибка формулировки.

Теперь у модели два вопроса: тот ли это предмет и какой фрагмент текста
содержит цену. Числа сравнивает код, с тем же запасом в 30%, что и
ранжирование: чуть дороже клиент вправе увидеть и решить сам, вдесятеро дороже
— нет. Правило шире одного охранника: **если задачу можно свести к сравнению
двух чисел, модели её отдавать незачем** — она даст разброс там, где нужен
детерминизм, и за это ещё придётся заплатить.

**Охранник настраивается замером, а не догадкой.** Первая боевая пачка
01.09.2026 отбраковала десять карточек из двенадцати, и обе причины оказались
дефектами промпта, а не модели: «Цена в тексте отсутствует» (половина
объявлений Нячанга цену не пишет вовсе) и «Это скутер, а клиент ищет
motorbike» — модель читала значение перечисления как требование, потому что
человек так не пишет. Теперь правила отказа перечислены явным списком из двух
пунктов, отсутствие цены названо НЕ причиной, а предмет и город приходят
русскими словами из словаря рынка.

Тем же замером вскрылась вторая ошибка, тяжелее первой. Непроверенный хвост
возвращался следом за проверенным — и когда охранник вычистил голову, наверх
всплыло то, куда ранжирование сложило заведомо худшее: на «мотоцикл до 300 USD»
клиент увидел ноутбуки ThinkPad. Не потому что охранник их пропустил, а потому
что до них не дошёл. Теперь возвращается только проверенное: показываем пять,
проверяем двенадцать, и три проверенные карточки честнее, чем три проверенные и
две неизвестно какие — для клиента они выглядят одинаково.

**Одно объявление не смеет останавливать пачку.** Первая версия воронки
обрабатывала все пятьдесят сообщений одной транзакцией, и 01.09.2026 это стоило
всей обработки: продавец написал «Цена: 21.500.000 млн VND», парсер честно
умножил на миллион, получил 21.5 триллиона донгов, вставка упала на
`NUMERIC(14,2)` — и воркер ушёл в цикл перезапуска. Одно кривое объявление
остановило обработку остальных навсегда. Теперь каждое сообщение идёт своей
транзакцией, а любое падение помечает его `rejected` с причиной и не трогает
соседей.

Лечение двойное, и вторая половина важнее. `domain/prices.py` больше не отдаёт
неправдоподобных цен: потолок — 10 млрд донгов, ровно там же, где кончается
колонка. **Обрезать до потолка было бы хуже, чем отказаться от цены**:
обрезанное число выглядит как настоящее и попадёт в фильтр по бюджету, то есть
соврёт клиенту тише и опаснее, чем честное «цены не знаю».

**Подбор идёт по подпискам, а не по карточкам** (`worker/matcher.py`). Подписок
единицы, карточек будут тысячи; обход по карточкам требовал бы запроса на
каждую строку («а кому это надо»), обход по подпискам — одного запроса на
подписку. `since_listing_id` фиксирует начало, а `scan_listing_id` — докуда
реально дошёл отбор, включая неподходящие строки. `notifications` отдельно
хранит дедуп постановки в очередь: факт отправки не является курсором просмотра.

Правила подбора живут в `matching/rules.py` и SQL не содержат — запрос строит
`db/repositories/listings.py::match`. Спецификация отбора (`MatchFilter`) лежит
в `domain/`, и это не мелочь: положи её в `matching`, и репозиторий начнёт
импортировать слой, который сам его вызывает. Первая версия так и была
написана; поймал это `tests/test_layers.py`, добавленный тем же коммитом.

**Оценка подписки строже, чем ранжирование поиска.** В поиске клиент сам решил
посмотреть и вправе увидеть «дороговато, но близко»; подписка будит его сама,
поэтому дороже бюджета отбрасывается совсем, свежесть весит больше, а ниже
`MATCH_MIN_SCORE`-порога карточка не уходит вовсе.

**Суточный лимит считается запросом, а не колонкой.** `subscriptions.sent_today`
в схеме остался, но источником правды не служит: счётчик требует не забыть
обнулить его в полночь. Граница суток передаётся вызывающим явно — первая
версия сравнивала `date(sent_at)` с датой, а `date()` от `timestamptz` считается
в часовом поясе СЕССИИ базы, то есть лимит клиента сбрасывался бы в полночь того
пояса, в котором подняли Postgres.

**Доставка не теряет сообщений.** Неудача возвращает строку в очередь с
`scheduled_at` в будущем, а не помечает `failed`: недоступный Telegram — причина
подождать. `failed` ставится ровно один раз, после третьей попытки, и означает
«клиент заблокировал бота». Время постановки в очередь тоже задаётся явно, а не
`DEFAULT now()`: иначе проход не может ни отложить доставку до вечера
(дайджест), ни быть проверен на заданном времени.

Чего в контуре ещё нет: полного LLM-извлечения и продавца. Явные атрибуты
извлекаются детерминированно; digest, тихие часы и раздельные времена постановки
и фактической отправки реализованы. Полный контракт и конкурентные гарантии —
в [universal-search.md](universal-search.md).

### 5.0.1 Дедуп кросспостов — отпечаток, а не побайтовый хеш

`raw_messages.text_hash` схема с первого дня описывала как «sha256
нормализованного текста: ловит кросспостинг одного объявления в пять групп, где
меняются только эмодзи и пробелы». Считался он от сырого текста, то есть ловил
лишь побайтовый повтор: другой смайлик или лишний перевод строки — и одно
объявление становилось двумя карточками. Комментарий описывал замысел, код — нет.

Теперь отпечаток считает `domain/fingerprint.py`: регистр вниз, любые
несловесные символы схлопываются в пробел, **и ничего больше**. Цифры и буквы
не трогаются — «Honda 125» и «Honda 150» обязаны разойтись, — а `\W+` берётся
по Unicode, а не списком разрешённых алфавитов: рынок трёхъязычный, и
перечисление алфавитов означает однажды забыть чужой (`xe máy` не смеет стать
`xe m y`).

Решение о дубле принимает воронка: перед созданием карточки она спрашивает
`RawMessageRepository.has_listing_for(отпечаток, besides=id)` — есть ли карточка
у ДРУГОГО сообщения с тем же отпечатком. Уникальность `(chat_tg_id, msg_id)`
здесь бесполезна: при кросспосте сообщения разные, объявление одно. Дубль
получает стадию `duplicate`, а не `rejected`: он не мусор, у него просто уже
есть карточка, и разбираться в отклонённых потом придётся именно по этой разнице.

Строки, принятые старым коллектором, несут хеш старой схемы и с новыми не
сойдутся. Отдельного прохода пересчёта нет и не нужно: воронка читает каждую
строку ровно один раз и в этот момент держит текст в руках, поэтому освежает
отпечаток тем же запросом, что меняет стадию.

### 5.1 Слой доступа — `db/`

Единственное место в проекте, где есть SQL. Всё выше по слоям получает отсюда
доменные записи и не знает ни про SQLAlchemy, ни про имена колонок.

```
db/engine.py        async engine + сессия на единицу работы
db/models/          ORM-зеркало 001_init.sql, разбито по разделам DDL
                    (источники, разведка чатов, предложения, клиенты, доставка, очередь)
db/mappers.py       строка таблицы ↔ доменная запись
db/repositories/    по одному классу на агрегат
domain/records.py   что репозиторий отдаёт наружу
```

Четыре решения, из-за которых слой выглядит именно так:

- **Схему создаёт SQL-файл, модели её только отражают.** `metadata.create_all`
  здесь не вызывается никогда: расширения, GIN-индексы и `vector(1024)`
  описываются обычным DDL точнее, а два источника правды про схему — это
  гарантированный дрейф. Чтобы зеркало не разъехалось молча,
  `tests/test_db_models.py` сверяет имена таблиц и колонок прямо с
  `001_init.sql`, и делает это без базы — то есть на любой машине.
- **Наружу уезжают dataclass-ы, а не ORM-сущности.** ORM-объект тащит за собой
  сессию: после закрытия `async with` обращение к незагруженному полю падает
  `DetachedInstanceError` уже в боте, далеко от места, где сессия закрылась.
  Заодно это держит правило слоёв — `domain` не зависит ни от чего.
- **Репозиторий не коммитит.** Он получает открытую сессию и работает в её
  транзакции; границу единицы работы ставит вызывающий. Автокоммит сделал бы
  эту границу невидимой в коде, а «прочитал» — неотличимым от «записал».
- **Дедуп сырья живёт на уникальном индексе, а не в коде.** Батч-вставка идёт
  через `ON CONFLICT (chat_tg_id, msg_id) DO NOTHING … RETURNING id`: коллектор
  после каждого простоя перечитывает историю и приносит уже виденное, а
  проверять существование по одному сообщению значило бы делать SELECT на
  каждое и всё равно проигрывать гонку.

Один нюанс `ON CONFLICT`, который стоил падения на живой базе: **по частичному
уникальному индексу цель конфликта не выводится** без того же предиката. Дедуп
расходов (`broker_calls.broker_request_id`, индекс с `WHERE … IS NOT NULL`)
обязан передавать `index_where`, иначе Postgres отвечает «no unique or exclusion
constraint matching the ON CONFLICT specification». На подделке базы этот запрос
проходил бы — поэтому тесты слоя и требуют настоящий Postgres (ниже).

Очередь `jobs` разбирается через `SELECT … FOR UPDATE SKIP LOCKED`: задача
выбирается, помечается `running` и коммитится сразу, дальше воркер работает уже
без замка. Второй воркер не ждёт освобождения строки, а пропускает её и берёт
следующую — иначе рабочие процессы выстроились бы в очередь за одной задачей.
Возврат в очередь после ошибки идёт через `run_after`; потолок попыток ставит
вызывающий, потому что он один знает, сколько их осмысленно для его `kind`.

**Кто ещё читает этот слой: источники.** Адаптеру `telegram_groups` нужен
реестр чатов, а архивному источнику — `listings`. Зависимость идёт вниз
(`sources → db`) и целиком сведена в `sources/chat_directory.py`: там собраны
реестр, чтение каталога и материализация проверенных live-находок. Сами
адаптеры про SQL и `sniffer.db` не знают — они видят протоколы. Подробности и
цена ошибки исходной проводки —
[spec-v2, 4.4](spec-v2.md#44-telegram-группы--что-стоило-дорого-узнать).

**Второй такой потребитель — разведка чатов.** Она пишет в `chat_candidates`,
`chat_rejects` и `chat_join_events`; ORM-зеркало этих таблиц лежит в
`db/models/discovery.py`. Знание о `db` к ней тоже не протекает: нужное описано
протоколами `ChatRegistry` / `CandidateQueue` / `RejectedLog` / `JoinLedger` в
`sources/telegram_discover_reference.py` и подставляется снаружи.
`collector/discovery.py` связывает их с репозиториями Postgres: короткая
транзакция занимает слот, затем один Telegram-вызов вступает в один чат, а
запись сразу появляется в реестре поиска. Заглушек в памяти намеренно нет:
журнал вступлений в памяти обнулялся бы каждым перезапуском и разрешал бы три
вступления после каждого деплоя — отказ, который замечают по бану аккаунта, а
не по красному тесту. Устройство — [spec-v2, 4.5](spec-v2.md#45-telegram_discover--как-набирается-список-чатов).

**Тесты слоя требуют настоящий Postgres.** Схема Postgres-специфична, на sqlite
не поднимается, а подделка была бы зелёной ровно в тех местах, которые и
ломаются. Поэтому тесты с базой берут адрес из `TEST_DATABASE_URL` и
пропускаются, когда её нет: у разработчика без Docker прогон остаётся зелёным,
в CI поднимается `pgvector/pgvector:pg16`, накатывается `001_init.sql` и они
выполняются. Чистая логика — маппинг и сверка со схемой — покрыта обычными
тестами без базы.

## 6. Матчинг и ранжирование

**Жёсткие фильтры (SQL, отсекают наглухо):** город, категория, тип сделки,
deal-breakers, возраст объявления. Пока исторические объявления ещё проходят
воронку, живой поиск применяет ту же детерминированную формулу в Python до
показа карточек: иначе клиент видел бы пять самых свежих ссылок, а не пять
вариантов под свой паспорт.
**Мягкие (влияют на score):** бюджет, атрибуты, репутация продавца.

```
score = 0.35·freshness + 0.30·price_fit + 0.25·attr_match + 0.10·seller_rep

freshness  = exp(-age_hours / 48)     свежесть решает: вчерашний байк уже продан
price_fit  = 1.0 в бюджете, линейно вниз до 0 при +30% сверху
attr_match = доля совпавших must_have; deal_breaker выбрасывает кандидата
seller_rep = 1 - scam_score
```

**Сортировки мало, поэтому у живого поиска есть и отсев.** «Ниже» не значит «не
показан»: карточек показывается пять, и когда лучшего нет, первыми пятью
оказывается мусор — на «honda lead» это были три Airblade и лот 59-дневной
давности (02.09.2026). Перед показом снимаются две вещи: лот другой известной
модели, когда клиент модель назвал, и лот старше 28 дней. Первое не
возвращается никогда — это не «похуже», а не тот предмет; второе возвращается,
если после отсева не осталось ничего, и тогда честность берёт на себя карточка
(«могло быть продано»). Подробности и почему порог здесь по дате, а не по баллу
— [spec-v2, 2.7](spec-v2.md#27-что-доходит-до-клиента--отбор-перед-показом).

Ранжирует **SQL, а не LLM**. Модель подключается на последнем шаге и только
чтобы написать человеческий текст карточек и честно сказать, чем вариант не
идеален («на 50$ выше бюджета, зато 2024 год»). Ранжирование моделью медленно,
недетерминированно и невоспроизводимо при разборе жалобы «почему мне это
показали».

## 7. Подписки

Новая карточка → кандидаты по жёстким фильтрам → score → выбранный клиентом режим доставки:

| режим | Действие |
|---|---|
| `instant` | сразу, кроме тихих часов, максимум 5 в сутки на подписку |
| `digest` | одним сообщением в 18:00 Asia/Ho_Chi_Minh |
| 0.45–0.55 | серая зона: **один** LLM-вызов на проверку соответствия |
| < 0.45 | молчим |

LLM в цикле уведомлений почти не участвует: иначе каждое новое объявление
умножается на число активных подписок и фри-квота кончается за час.

Троттлинг обязателен. Бот, который шлёт сорок сообщений в день, отключается
пользователем в первые сутки — это не гипотеза, а стандартная судьба
алерт-ботов.

### Почему не managed-БД на free-тире

Neon Free даёт 100 CU-hours в месяц — по их же документации это 0.25 CU в
течение 400 часов, то есть ~13 часов в сутки при 720 часах в месяце.
Приложение, держащее пул соединений круглосуточно, выедает месячную квоту
примерно за две недели, после чего компьют встаёт до следующего цикла.
Managed-БД на бесплатном тарифе и всегда-живой сервис плохо совместимы.

Раз VM всё равно нужна под Telethon, Postgres на ней же означает ноль сетевых
хопов, ноль внешних квот и ноль лишних аккаунтов. Устойчивость к потере машины
закрывается `pg_dump` по крону в R2 — одна строка в crontab.

### Почему не полный serverless

Соблазнительный вариант: коллектор как задача по расписанию (подключился,
догнал историю по `last_msg_id`, отключился), бот на webhook, БД в Neon. При
интервальном доступе квоты сходятся, и платить не нужно вообще ни за что.

Ломает его не экономика, а **плавающий IP**: при каждом холодном старте
контейнер получает новый адрес датацентра, а юзербот, логинящийся с постоянно
меняющихся IP, — ровно тот паттерн, на который Telegram отвечает блокировкой.
Аккаунт один, и переподписываться с нового номера на 30 групп после каждой
блокировки — это не работающий продукт. Фиксированный IP маленькой VM здесь
функциональное требование, а не привычка.

Второй, меньший минус: задержка уведомлений становится равна интервалу
запуска (10–15 минут) вместо мгновенной.

Почему **не Cloudflare D1**: `rows written` считает и записи в индексы,
`rows read` считает просканированные строки, так что поисковая нагрузка выедает
5 млн в день; доступ снаружи Workers требует прокси-Worker, а collector на
Telethon внутри Workers жить не может в принципе.

## 9. Экономика — почему это бесплатно

Расчёт на 20 чатов по 300 сообщений, то есть 6000 в день:

```
regex-гейт      6000 → ~700          0 вызовов
prefilter        700 → батчи по 20   35 вызовов
structured       250 → батчи по 10   25 вызовов
диалог           100 запросов × 2    200 вызовов
выдача           100 запросов × 1    100 вызовов
подписки         серая зона          ~20 вызовов
                                    ─────────────
                                    ~380 вызовов в день
```

Free-лимитов брокера хватает с запасом. Критично держать три вещи: regex-гейт
перед LLM, батчинг и **отдельный project-key с низким дневным cap**, чтобы бот
физически не мог выесть чужую квоту.

## 10. Риски

| Риск | Что делаем |
|---|---|
| Бан юзербота | отдельный номер, только чтение, 20–30 групп вручную с паузами в дни, лимит запросов, `FloodWaitError` с экспоненциальной паузой |
| `FloodWait` на поиске | максимум 10 чатов на запрос, семафор, кэш результатов 5–10 минут |
| Мультиязычность | чаты Нячанга русско-англо-вьетнамские; **regex-гейт сразу мультиязычный**, иначе первая ступень выкосит половину настоящих объявлений |
| Кросспостинг | дедуп по нормализованному тексту и телефону, иначе выдача из пяти копий одного байка |
| Скам и риелторы-спамеры | `sellers.scam_score`: частота постинга, повторяющийся текст, жалобы клиентов |
| Простой сбора (выключенный ноутбук, деплой, падение коллектора) | `chats.last_msg_id`: каждые 15 минут дочитываем до 200 последних сообщений каждого из первых десяти активных чатов после курсора и вставляем их с дедупликацией. Telegram очередь для нас не держит — без догона объявления за время простоя пропадают молча |
| Потеря сессии | `StringSession` в БД или секрете, не файлом — на эфемерной ФС она умрёт |
| Качество выдачи | кнопки обратной связи на каждой карточке уточняют паспорт |

## 11. Этапы

**P0 — проверка идеи (вечер).** Пять чатов, только живой поиск, без ингеста:
диалог → паспорт → `messages.search` → пять карточек. Цель — увидеть, полезна
ли выдача вообще. Если карточки мусорные, остальная инфраструктура
бессмысленна, и это выясняется за часы, а не за неделю.

**P1 — база.** Ингест, воронка, Postgres, полнотекстовый поиск (`pg_trgm` и
`tsvector`), карточки из базы вместо живого поиска.

**P2 — подписки.** Матчинг, outbox, троттлинг, дайджесты.

**P3 — качество.** pgvector и семантика, скам-скоринг, репутация продавцов,
второй город.

Между P0 и P1 стоит явная точка принятия решения. Она не техническая — код к
тому моменту работает; вопрос в том, попадает ли выдача.
