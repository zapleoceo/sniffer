# SnifferBot — архитектура

## Agent runtime и production-каталог

Пакет `agents/` остаётся изолированным ядром: конечный read-only цикл,
брокерный адаптер и MCP ClientSession-протокол. Production-интеграция живёт в
`agent_app/`: бот читает проверенный каталог через scoped MCP, а отдельный
`agent-collector` выполняет почасовые задачи пополнения через AIbroker.
Модель не получает SQL и write-tool; публикацию после строгой проверки делает
приложение. После публикации главный агент повторно читает тот же scoped-каталог
и кладёт конечный ответ каждому ожидающему клиенту в `outbox`; клиенту не нужно
повторять исходный запрос. `notifier` разрешает внутренний FK клиента в Telegram
ID только на границе отправки. `domain` и `db` не зависят от `agents`, границы проверяет
`tests/test_layers.py`. История исходного прототипа — [agent-runtime.md](agent-runtime.md),
план и принятые ограничения — [two-agent-mcp-plan.md](two-agent-mcp-plan.md).

> Агент в Telegram, который выясняет у клиента, что ему нужно, формирует
> **паспорт запроса**, показывает актуальные предложения из телеграм-сообществ
> и присылает новые по мере появления.

> **Дополнено [spec-v2.md](spec-v2.md).** Там источники перестали быть
> курируемым списком чатов и превратились в реестр адаптеров с планировщиком,
> добавился обязательный verifier и задел под публичный доступ. Где документы
> расходятся, верен spec-v2.

## 1. Что делаем и чего не делаем

**Делаем:** диалог → структурированный паспорт запроса → подбор из уже
собранных объявлений + живой поиск по чатам → подписка на новые совпадения.

**Не делаем (сознательно):**

| Не делаем | Почему |
|---|---|
| Не перепечатываем объявления | отдаём ссылку на оригинал; снимает вопрос ответственности за чужой контент и контакты. Форма ссылки зависит от чата: у публичной группы `t.me/<username>/<msg>` (открывается у кого угодно), у закрытой — `t.me/c/<chat>/<msg>` (только для участников), в форуме между ними встаёт номер темы — [spec-v2, 4.4](spec-v2.md#44-telegram-группы--что-стоило-дорого-узнать) |
| Не пишем от имени юзербота | любое исходящее действие с userbot-аккаунта кратно повышает риск бана; аккаунт только читает |
| Не сводим людей и не берём комиссию | это поисковый помощник, а не маркетплейс — нет эскроу, нет модерации сделок, нет ответственности за них |
| Не держим базу контактов продавцов | контакт живёт внутри исходного сообщения, мы храним ссылку |

Первый рынок — **Нячанг**: байки, апартаменты и комнаты. Категории и город
задаются данными, а не кодом: добавить «Дананг + скутеры» — это строки в
таблицах, а не релиз.

## 2. Ключевое решение — паспорт запроса

Разница между поисковой строкой и агентом ровно одна: **агент хранит намерение
клиента как объект и переиспользует его**. Паспорт — центральная сущность, из
неё растёт всё остальное:

```
паспорт → запрос к базе (что есть сейчас)
паспорт → ключевые слова для живого поиска по чатам
паспорт → фильтр подписки (что присылать потом)
паспорт → критерии ранжирования (почему это в топе)
паспорт ← обратная связь «дорого» / «не то» уточняет паспорт
```

Один и тот же объект обслуживает и разовый подбор, и подписку. Поэтому
подписка — не отдельная фича, а **статус паспорта** (`active`).

Полная схема полей: [passport.md](passport.md).

**Правило диалога: до первой выдачи задаём только блокирующий вопрос.** Сейчас
это категория, когда её нельзя вывести из слов, марки или модели. Город рынка
подставляется по умолчанию, бюджет и предпочтения уточняются обратной связью уже
на выдаче. Названная сущность не может исчезнуть ради раннего поиска: неизвестная
модель сохраняется как точный критерий. Пустой точный результат честнее молча
расширенного, а расширение запускается отдельным действием клиента.

Публичный каталог применяет марку и модель в SQL **до** сортировки и `LIMIT`.
Иначе точный, но не входящий в двадцать самых новых общих объявлений лот был бы
невидим. Один паспорт управляет SQL, финальным отсевом, coverage/коллектором и
подпиской; расхождение критериев между этими путями считается дефектом.
Для уже точной модели второй LLM-read не запускается: он не может менять
server-owned условия, поэтому только добавлял до 18 секунд ожидания. Semantic
intake остаётся агентным разбором, а каталог исполняет полученный точный паспорт.

```
            └───────────────┘   (roadmap.md, волна 5)
```

Шесть процессов на одной машине координируются **только через Postgres** — брокер
сообщений не нужен, очередь делается на `SELECT … FOR UPDATE SKIP LOCKED`. Это
осознанный отказ от Redis и RabbitMQ: на таком объёме они добавляют
операционную сложность и не решают ни одной реальной проблемы.

Последний из шести — `dashboard`, веб-интерфейс владельца, и он же единственный,
который слушает порт. Он является **седьмым контейнером**: к шести процессам
добавляется Postgres. До
31.08.2026 «ни один процесс не слушает порт» было записано здесь как свойство
архитектуры; требование владельца его отменило.

| Процесс | Ответственность | Почему отдельный |
|---|---|---|
| `bot` | диалог, показ карточек, управление подписками | падение ингеста не должно ронять общение с клиентом |
| `collector` | единственный держатель MTProto-сессии | сессия одна на аккаунт; два процесса с одной сессией дают `AuthKeyDuplicated` |
| `agent-collector` | почасовое пополнение каталога и постановка отложенного ответа в `outbox` | модель и источники изолированы от клиентского процесса; ответ переживает рестарт и доставляется отдельно |
| `worker` | воронка: гейт → минимальная карточка → ИИ-проверка (`worker/screening.py`) → нормализация → матчинг; плюс уборка сырья по сроку хранения; разовой подкомандой — проход догона `enrich` по накопленным карточкам ([5.0.4](#504-проход-догона-накопленные-карточки-пересчитанные-из-исходного-текста)) | тяжёлый и перезапускаемый, его можно убить без потерь |
| `notifier` | доставка с троттлингом | доставка обязана переживать рестарт воркера, отсюда таблица `outbox` |
| `dashboard` | интерфейс владельца: лог запросов, расходы, переписка, сессия | единственный процесс с HTTP; падение страницы не должно ронять ни диалог, ни ингест — [dashboard.md](dashboard.md) |

### 3.1 Точки входа

У каждого процесса свой `__main__.py`, ровно те шесть команд, что стоят в
`docker-compose.yml`:

```
python -m sniffer.bot         диалог и выдача (aiogram, long polling)
python -m sniffer.collector   MTProto-сессия, чтение сообществ
python -m sniffer.agent_app.collector  почасовое пополнение проверенного каталога
python -m sniffer.worker      воронка, очередь jobs, уборка сырья
python -m sniffer.notifier    доставка из outbox
python -m sniffer.dashboard   интерфейс владельца (uvicorn, порт 8005)
```

Общий каркас — `sniffer/runtime/`: настройка лога, обработка сигналов и
холостой цикл. Слоем он не является, бизнес-логики в нём нет; он существует,
чтобы шесть точек входа не описывали одно и то же шестью способами.

Седьмой `__main__` — `python -m sniffer.simulation` — в этом списке не стоит и в
`docker-compose.yml` его нет: это не сервис, а измерительный инструмент.
Отрабатывает и выходит, сети, модели и базы не требует, печатает таблицу
«сценарий → метрики → вердикт» по качеству диалога. Живёт в `src/`, а не в
`scripts/`, ровно потому, что запускать его надо и в CI, и в боевом контейнере:
зелёный прогон на раннере не доказывает, что на сервере то же самое, а тестов
образ не везёт. Что он меряет — [passport.md, «Симуляция диалога»](passport.md#симуляция-диалога--качество-в-цифрах).

**Процесс без обязательной настройки не падает.** Он пишет в лог, чего именно
не хватает — именами из `.env`, — и уходит ждать, перепроверяя окружение раз в
минуту:

```
{"event": "service.not_configured", "service": "bot", "missing": ["BOT_TOKEN"],
 "message": "не настроен: нет BOT_TOKEN, жду конфигурации"}
```

Причина конкретная: контейнер, перезапускающийся каждые пять секунд, выглядит
как сломанный деплой и заваливает healthcheck, хотя на деле просто не заведён
секрет. Ожидание отличает «не настроен» от «сломан» и в логе, и в `docker ps`.
Перепроверка не декоративная: секрет заводят уже после первого запуска, и
процесс подхватывает его сам, без `docker compose restart`.

Пустой токен и неверный токен — разные вещи. Пустой означает ожидание, неверный
означает падение с внятной ошибкой: молча ждать при опечатке в секрете хуже,
чем упасть.

| Процесс | Без чего не работает |
|---|---|
| `bot` | `BOT_TOKEN`; в публичном каталоге также `BROKER_PROJECT_KEY`, а deploy проверяет `CATALOG_MODE` и `AGENT_COLLECTOR_ENABLED` до рестарта |
| `notifier` | `BOT_TOKEN` — доставка идёт тем же Bot API |
| `collector` | `TG_API_ID`, `TG_API_HASH`, `TG_SESSION`; код подтверждения в фоновом контейнере ввести негде, поэтому строка сессии обязательна — её выдаёт `python -m sniffer.collector auth` ([deploy.md, 3.5](deploy.md#35-авторизация-юзербота)) |
| `agent-collector` | `AGENT_COLLECTOR_ENABLED`, `BROKER_PROJECT_KEY`; production deploy проверяет эффективные compose-значения до перезапуска бота |
| `worker` | ничего: без базы он просто не найдёт задач |
| `dashboard` | `BOT_TOKEN` (проверить подпись виджета), `DASHBOARD_SESSION_SECRET` (подписать cookie), `OWNER_CHAT_ID` (кого пускать). Не хватает любого — пускать некого и нечем, а открытая страница хуже закрытой |

**Подкоманда — это `auth` и только `auth`.** Любой другой аргумент —
неизвестное имя, опечатка, лишний позиционный — заканчивается кодом 9 и
подсказкой, а не запуском сервиса. Разбор строгий намеренно:
`python -m sniffer.collector notauth` раньше молча уходил в демона, аргумент
терялся, и владелец ждал диалога авторизации, глядя на обычный старт
коллектора.

**Как мы подписаны в Telegram → Настройки → Устройства — общий контракт трёх
точек входа.** Клиента создают `collector/client.py` (разовый вход за строкой
сессии), `sources/telegram_client.py` (боевое чтение) и
`sources/telegram_discover_client.py` (вступление и беззвучный режим).
Telegram считает устройством пару (auth key, подпись клиента), поэтому одна и
та же сессия с разными `device_model` показывается там ДВУМЯ строками — и
владелец, решая, какой сеанс отозвать, не понимает, откуда второй. Подпись
поэтому лежит в `sniffer/telegram_identity.py` — модуле-листе, который видят
все три точки входа и который не создаёт между ними зависимости; расхождение
ловит `tests/test_telegram_identity.py`.

**SIGTERM останавливает, а не убивает.** `docker compose stop` даёт десять
секунд; бот дослушивает текущий апдейт и закрывает сессию, фоновые процессы
выходят из цикла на ближайшей проверке. Лог структурный: JSON в контейнере,
человекочитаемый рендер в терминале, уровень из `LOG_LEVEL`.

Холостой цикл фоновых процессов молчит: «нечего делать» пишется не чаще раза в
пять минут, иначе `max-size: 10m` из compose открутится за час. Пока работа
находится, цикл не спит вовсе — очередь разгребается пачками, а не по таймеру.

### 3.2 Бот изнутри: ход, слова, выдача

Процесс `bot` тонкий: он связывает, а не решает. Диалог разложен так, чтобы
каждый модуль менялся по одной причине, и правка заголовка выдачи не лежала в
одном файле с порядком шагов поиска:

```
bot/conversation.py   ход: кто за кем идёт, что журналировать, где закончить
bot/wording.py        слова клиенту: «Понял», отказы, заголовок выдачи
bot/presenter.py      выдача: итог поиска → одно сообщение (заголовок, карточки, кнопки)
bot/quota.py          сколько карточек положено показать этому человеку (5.2)
bot/showing.py        выдача через квоту: допуск → отправка → подтверждение (5.2)
bot/wording_plan.py   слова про лимит и подписку: остаток, исчерпание, `/plan`
bot/cards.py          одна карточка, факты из атрибутов, нарезка по 4096 знаков
bot/paging.py         снимок выдачи, порядок без засилья автора, курсор «Ещё»
bot/more_cards.py     «Ещё N» / «Показать все N»: следующая страница по снимку
domain/card_facts.py  строка фактов («Honda Lead · 110 cc · 2008 · автомат») для всех карточек
bot/keyboards.py      разметка кнопок, единственное место с типами Telegram
```

**Показ выдачи — отдельная ответственность.** До 03.10.2026 `Conversation._search`
не только искал, но и решал, что показать: сколько карточек, какой заголовок,
предлагать ли слежение. Эти решения меняются по другим причинам, чем порядок шагов
(сколько карточек положено человеку — правило продукта, а не диалога), поэтому они
переехали в `presenter.present(passport, found, root=…) -> Reply` без смены
поведения: перенос доказан сравнением старого и нового `_search` на 26 280
комбинациях паспорта, числа находок, статуса, признака «жду сбора» и настройки
`MAX_CARDS` (расхождений 0). Число показанных карточек считается в презентере один
раз и идёт и в заголовок, и в срез карточек: прежнее «в двух местах независимо»
позволяло написать «показываю 5» над четырьмя.

**Листание по снимку.** Страница показывает первые `MAX_CARDS` находок (порядок — после
`paging.diversify`, не больше двух карточек одного автора впереди). Остальное лежит в
снимке выдачи: `callback_data` несёт только ключ снимка и смещение (`pg:Ab3xYz9Q:more:5`,
19 байт из 64), сами карточки по проводу не ходят. Снимок живёт в памяти процесса 48 часов
(`MemorySnapshots`, столько же, сколько Telegram держит сообщение доступным для кнопок);
после перезапуска бота кнопка отвечает «выдача устарела». Хранилище в базе спрятано за
`SnapshotStore` и пока не нужно показу. Курсор снимка не даёт показать страницу дважды
(двойное нажатие, старая кнопка), а от двойного списания защищает журнал квоты.
Снимок чужого пользователя неотличим от просроченного.

Одна карточка на все поверхности: факты (марка, модель, объём, год, коробка, пробег,
площадь) строит `domain/card_facts.facts_line`; её зовут чат (`bot/cards`), мониторинг
(`worker/matcher._payload` кладёт строку в очередь) и отложенные ответы
(`agent_app/followup._item`), нотифаер печатает её, экранируя.

`Reply` — одно сообщение клиенту, единица показа — живёт в презентере.
`conversation` его ре-экспортирует: хендлеры, клавиатуры и симулятор импортируют
`Reply` оттуда, и переезд их не ломает.

## 4. Воронка обработки — где решается стоимость

Главная ошибка в таких ботах — отправлять каждое сообщение в LLM. Лестница
«дёшево → дорого», где каждая ступень отсеивает мусор до того, как он дойдёт до
дорогого слоя:

| # | Ступень | Стоимость | Отсев |
|---|---|---|---|
| 0 | Дедуп: `UNIQUE(chat_id, msg_id)` плюс хэш нормализованного текста | 0 | кросспостинг одного байка в пять групп |
| 1 | Regex-гейт: цена (`$`, `k`, `тр`, `VND`, `triệu`) **и** глагол сделки | 0 | ~85–90% |
| 2 | LLM `prefilter`: «объявление? да/нет», **пачками по 20** | free, кэш 10 мин | ~60% остатка |
| 3 | LLM `structured`: карточка по strict `json_schema` | free | — |
| 4 | Эмбеддинг для семантики | опционально, этап P3 | — |

Батчинг — не оптимизация, а условие бесплатности: 700 сообщений по одному это
700 вызовов, пачками по 20 — тридцать пять. Ровно разница между «влезаем в
free-квоту» и «не влезаем».

## 5. Модель данных

У одного клиента может быть несколько независимых цепочек паспортов, и цепочка
— это **ветка** в терминах бота: один поиск человека. Явный активный контекст,
переключение (`/new`, `/requests`), предел на число веток и управление
мониторингами описаны в [`multi-query.md`](multi-query.md). Свежесть версии не
используется как указатель активного запроса.

```
chats            справочник отслеживаемых сообществ (курируется вручную)
raw_messages     сырьё как пришло; хранится 90 дней от ingested_at
listings         нормализованная карточка предложения — то, что ищем
listing_media    отпечаток фото (перцептивный хеш) для дедупа кросспостов
sellers          агрегат по автору: частота постинга, скам-скор
users            клиенты бота
passports        паспорт запроса, версионируемый
passport_events  история диалога и обратной связи
subscriptions    активный паспорт плюс политика уведомлений
payments         платежи Stars: журнал, в который платёж пишется первым делом и целиком
user_consents    согласие с условиями до покупки: версия текста и время
billing_events   события оплаты без своего charge id: подписка, возврат, обращение
notifications    что кому уже отправлено (дедуп)
outbox           очередь доставки, переживает рестарт
jobs             внутренняя очередь воронки
client_requests  запрос клиента как единица наблюдения (показано / удержано лимитом)
quota_periods    периоды квоты аккаунта: якорь + k месяцев по Вьетнаму
offer_views      журнал показов: карточка в периоде, резерв и подтверждение (5.2)
dialog_messages  переписка с ботом — то, что человек увидел
broker_calls     расход на LLM по каждому вызову
telegram_sessions сессия юзербота, строка зашифрована
```

DDL: [`infra/sql/001_init.sql`](../infra/sql/001_init.sql).

Два решения стоит подсветить отдельно:

- **`raw_messages` и `listings` разделены.** Сырьё живёт 90 дней и удаляется,
  карточки живут дольше и компактны. Будь карточка колонкой в сырье, ретеншн
  удалял бы вместе с мусором и полезное.
- **Паспорт версионируется, а не перезаписывается.** Клиент говорит «дорого» —
  создаётся новая версия с изменённым бюджетом, старая остаётся. Без этого
  невозможно ни отладить агента, ни объяснить клиенту, почему выдача изменилась.

### 5.0 Срок хранения сырья — «крон», который живёт в коде

`raw_messages` растёт с каждым проходом коллектора и ничем не ограничен сверху.
Схема с самого начала обещала TTL 30 дней «чистится кроном» — и это было
неправдой: ни крона, ни какой-либо уборки не существовало до 01.09.2026.
Комментарий в DDL при этом читался как описание работающего механизма, что
хуже честного «не сделано»: заметить такое можно только по выросшему диску.

Теперь срок — **90 дней** (решение владельца), а уборку делает воркер, раз в
сутки, пачками по тысяче строк (`worker/retention.py`). Три решения, которые
там приняты, стоят объяснения:

**Не системный `crontab`.** Состояние машины определяется репозиторием: строчка
в crontab не попадёт ни в один диff, не переживёт пересборку машины и не будет
видна тому, кто читает код. Расписание в коде едет тем же деплоем и проверяется
тестами без сервера. Отдельный контейнер ради одного `DELETE` в сутки на общей
машине тоже не оправдан — поэтому уборка живёт в воркере, у которого холостой
цикл уже есть, а уборка воронки и есть работа воронки.

**Считаем от `ingested_at`, а не от `posted_at`.** Срок здесь про диск — «мы
держим скачанное столько-то», — а не про устаревание объявления. По дате
публикации уборка стирала бы догон истории ровно с той скоростью, с какой
коллектор его дочитывает: архив чата уходит на годы назад, и глубокий добор
терял бы смысл целиком.

**Не трогаем сырьё, из которого вышла карточка.** У `listings.raw_message_id`
стоит `ON DELETE CASCADE`: удаление сырья по возрасту унесло бы с собой живую
карточку, показанную клиенту, вместе с текстом, по которому verifier её
сверяет. Поэтому уборка берёт только строки без карточки. Это проверяется
тестом на настоящем Postgres (`test_retention_never_takes_a_listing_down_with_the_raw_message`)
— на подделке каскада нет, и тест был бы зелёным при любой ошибке.

Что этот срок НЕ решает: сырьё, которое воронка не успела разобрать, удалится
вместе с остальным. Пока ступени `extract` нет, всё лежит в `pending`, и через
90 дней самое старое начнёт исчезать необработанным. При работающей воронке
разрыв в 90 дней несоизмерим с её задержкой, но пока её нет — это надо знать.

### 5.0.0 Контур целиком: сырьё → карточка → подписка → доставка

До 01.09.2026 контура не было. Коллектор честно наполнял `raw_messages`, а
дальше всё обрывалось: воркер только убирал старое, `matching/` был пустым
пакетом, `outbox` не наполнял никто, нотифаер возвращал ноль. Накопленная
история групп не превращалась ни в карточки, ни в уведомления.

Теперь звенья такие, и каждое проверено на живом Postgres:

```
raw_messages ──гейт──▶ listings ──подбор──▶ outbox ──доставка──▶ клиент
   collector        worker/archive     worker/matcher      notifier/delivery
                    (+ дедуп по          (по подпискам)     (троттлинг, повтор)
                     отпечатку)
```

Разовый agent-catalog запрос использует тот же последний участок: после задачи
сбора scoped-поиск анализирует новые записи и ставит в `outbox` один полный
ответ (карточки либо честный пустой итог). Это не платный мониторинг: ответ
создаётся ровно один раз для версии запроса, а новые объявления после него не
рассылаются без подписки.

**Гейт и минимальная карточка** (`pipeline/archive.py`). LLM не обязателен для
появления карточки: сообщение, прошедшее бесплатный гейт, уже даёт ссылку,
категорию и явно указанную цену. Полное извлечение позже улучшит карточку, но
не блокирует ни поиск, ни подписки.

Категорию гейт узнаёт **внедрённым детектором**, а не своим списком. Знание
«какими словами, марками и моделями зовётся предмет» одно — в словаре поиска
(`CATEGORY_TERMS` плюс `motorbike_models`), — и воркер отдаёт его гейту функцией
`vocabulary.category_hints`; сама воронка про поиск не знает (`pipeline` не
импортирует `search` — обратное ребро слоёв). Раньше гейт держал свою копию
списка марок и моделей, и она разошлась с рынком: honda и vision в ней были, а
sym, kymco, lead, attila — нет, и терсовое «Sym Attila, 15тр» отсеивалось как
«без категории» ещё до базы — тот же дефект, что был у поиска, только на входе.
В самом гейте дефолтом остались лишь стабильные общие слова предмета (скутер,
квартира) — они не дрейфуют, как список моделей.

**Совпадение предмета — тоже работа кода.** Замер 01.09.2026 на пяти
вьетнамских объявлениях о домах и земле: модель ТРИ РАЗА ИЗ ТРЁХ ответила
«подходит» для запроса про мотоцикл. Правила отказа были перечислены по-русски
(«телефон, ноутбук, часы, колонка»), объявление написано по-вьетнамски
(`Bán nhà`, `căn hộ`, `Bán đất`), и связь между ними она не построила. Дописать
вьетнамские слова в список значило бы ждать следующего языка.

Поэтому вопрос к модели теперь другой: не «подходит ли», а **«что это»** — одним
значением из нашего закрытого списка категорий. Назвать предмет она умеет на
любом языке; сравнить две строки умеем мы. `unknown` проходит: непонятное
объявление решает человек, а не мы за него.

Это уже третий случай одного и того же правила в одном модуле, и стоит записать
его прямо: **модели задают вопросы восприятия, а не вопросы решения.** Что
написано в объявлении — восприятие. Влезает ли в бюджет, тот ли это предмет —
решение, и оно детерминированное.

**Арифметику у модели забрали.** Сравнение цены с бюджетом сначала было её
работой вместе со смыслом, и второй замер 01.09.2026 показал, почему так
нельзя: на «до 300 USD» (потолок 7.8 млн) она оставила байки за 10–11 млн, а на
«до 400 USD» (потолок 10.4 млн) отбраковала ВСЁ. Один промпт, соседние запросы,
противоположная строгость — это разброс, а не ошибка формулировки.

Теперь у модели два вопроса: тот ли это предмет и какой фрагмент текста
содержит цену. Числа сравнивает код, с тем же запасом в 30%, что и
ранжирование: чуть дороже клиент вправе увидеть и решить сам, вдесятеро дороже
— нет. Правило шире одного охранника: **если задачу можно свести к сравнению
двух чисел, модели её отдавать незачем** — она даст разброс там, где нужен
детерминизм, и за это ещё придётся заплатить.

**Охранник настраивается замером, а не догадкой.** Первая боевая пачка
01.09.2026 отбраковала десять карточек из двенадцати, и обе причины оказались
дефектами промпта, а не модели: «Цена в тексте отсутствует» (половина
объявлений Нячанга цену не пишет вовсе) и «Это скутер, а клиент ищет
motorbike» — модель читала значение перечисления как требование, потому что
человек так не пишет. Теперь правила отказа перечислены явным списком из двух
пунктов, отсутствие цены названо НЕ причиной, а предмет и город приходят
русскими словами из словаря рынка.

Тем же замером вскрылась вторая ошибка, тяжелее первой. Непроверенный хвост
возвращался следом за проверенным — и когда охранник вычистил голову, наверх
всплыло то, куда ранжирование сложило заведомо худшее: на «мотоцикл до 300 USD»
клиент увидел ноутбуки ThinkPad. Не потому что охранник их пропустил, а потому
что до них не дошёл. Теперь возвращается только проверенное: показываем пять,
проверяем двенадцать, и три проверенные карточки честнее, чем три проверенные и
две неизвестно какие — для клиента они выглядят одинаково.

**Одно объявление не смеет останавливать пачку.** Первая версия воронки
обрабатывала все пятьдесят сообщений одной транзакцией, и 01.09.2026 это стоило
всей обработки: продавец написал «Цена: 21.500.000 млн VND», парсер честно
умножил на миллион, получил 21.5 триллиона донгов, вставка упала на
`NUMERIC(14,2)` — и воркер ушёл в цикл перезапуска. Одно кривое объявление
остановило обработку остальных навсегда. Теперь каждое сообщение идёт своей
транзакцией, а любое падение помечает его `rejected` с причиной и не трогает
соседей.

Лечение двойное, и вторая половина важнее. `domain/prices.py` больше не отдаёт
неправдоподобных цен: потолок — 10 млрд донгов, ровно там же, где кончается
колонка. **Обрезать до потолка было бы хуже, чем отказаться от цены**:
обрезанное число выглядит как настоящее и попадёт в фильтр по бюджету, то есть
соврёт клиенту тише и опаснее, чем честное «цены не знаю».

**Подбор идёт по подпискам, а не по карточкам** (`worker/matcher.py`). Подписок
единицы, карточек будут тысячи; обход по карточкам требовал бы запроса на
каждую строку («а кому это надо»), обход по подпискам — одного запроса на
подписку. `since_listing_id` фиксирует начало, а `scan_listing_id` — докуда
реально дошёл отбор, включая неподходящие строки. `notifications` отдельно
хранит дедуп постановки в очередь: факт отправки не является курсором просмотра.
Как проход защищён от собственных сбоев — обход по кругу, карантин сбойной
подписки, курс доллара, часы — описано в разделе 7.1.

Правила подбора живут в `matching/rules.py` и SQL не содержат — запрос строит
`db/repositories/listings.py::match`. Спецификация отбора (`MatchFilter`) лежит
в `domain/`, и это не мелочь: положи её в `matching`, и репозиторий начнёт
импортировать слой, который сам его вызывает. Первая версия так и была
написана; поймал это `tests/test_layers.py`, добавленный тем же коммитом.

**Оценка подписки строже, чем ранжирование поиска.** В поиске клиент сам решил
посмотреть и вправе увидеть «дороговато, но близко»; подписка будит его сама,
поэтому дороже бюджета отбрасывается совсем, свежесть весит больше, а ниже
`MATCH_MIN_SCORE`-порога карточка не уходит вовсе.

**Суточный лимит считается запросом, а не колонкой.** `subscriptions.sent_today`
в схеме остался, но источником правды не служит: счётчик требует не забыть
обнулить его в полночь. Граница суток передаётся вызывающим явно — первая
версия сравнивала `date(sent_at)` с датой, а `date()` от `timestamptz` считается
в часовом поясе СЕССИИ базы, то есть лимит клиента сбрасывался бы в полночь того
пояса, в котором подняли Postgres.

**Доставка не теряет сообщений и понимает, что ей ответил Telegram.** Время
постановки в очередь задаётся явно, а не `DEFAULT now()`: иначе проход не может ни
отложить доставку до вечера (дайджест), ни быть проверен на заданном времени.
Статусов строки `outbox` четыре: `pending`, `sent`, `failed` (Telegram отказал
или кончились попытки) и `cancelled` (мы решили не слать); причина — в
`outbox.last_error`, без неё `failed` и `cancelled` не различить, глядя в базу.

**Транзакция — на одно сообщение, а не на пачку.** Проход читает очередь без
блокировок (`take_pending`), а перед каждой отправкой запирает ровно её строки
(`lock_pending`, `FOR UPDATE SKIP LOCKED`), шлёт, ставит отметку «отправлено» и
коммитит — и только потом берётся за следующее. Раньше коммит стоял в конце
прохода из двадцати сообщений с паузой в секунду между ними, а `docker compose
stop` даёт десять секунд до SIGKILL: убитый процесс забывал всю пачку, и клиент
получал её второй раз. Теперь повтор возможен не больше чем для ОДНОГО сообщения
(в окне между ответом Telegram и коммитом; Bot API нашего ключа идемпотентности
не принимает, поэтому exactly once обещать нельзя). Отметка `sent_at` — момент
подтверждения Telegram, а не начало прохода, у которого за двадцать сообщений
набегают десятки секунд: по ней считается и задержка доставки, и суточная
статистика. Паузу между отправками нотифаер берёт только после настоящего
обращения к Bot API: строка, которую успела забрать другая копия, к Telegram не
ходила, и ждать после неё незачем.

**Что значит ответ Bot API.** Раньше любая ошибка была одинаковой: «подожди
пятнадцать минут, попробуй ещё дважды, третья неудача — клиент заблокировал
бота». Telegram говорит о разном, и разное требует разного. Исход решает
`notifier/outcome.classify`, а не класс исключения (всё неузнанное — временный
сбой), решение по исходу — чистая `notifier/policy.decide`:

| Ответ Bot API | Исход | Что делает очередь |
|---|---|---|
| 403 (бот заблокирован, аккаунт удалён, диалог не начат), 400 «chat not found» | `blocked` | `users.bot_blocked_at` = момент отказа; все ждущие строки клиента → `cancelled`; слежение приостановлено, пока метка стоит (ниже) |
| 429 | `rate_limited` | нотифаер молчит ровно `retry_after` секунд — для ВСЕХ клиентов: Telegram просит подождать бота, а не одного получателя. Строка не тронута, попытка не засчитана |
| 400: «message is too long», «thread not found», «can't parse entities», любой другой | `rejected` | `failed` сразу, причина в `last_error`: повтор дал бы тот же отказ |
| 401, 404 | `system` | сломан токен: нотифаер молчит пять минут, строки не тронуты, пока человек не починит |
| сеть, 5xx, всё остальное | `transient` | `scheduled_at` отодвигается на 1, 2, 4, 8, 16 минут (потолок час), попытка засчитана; после шестой — `failed` |

Шаг отправки (сборка текста и вызов Bot API) стоит под одной охраной до корня
иерархии, `except BaseException`: что бы ни вылетело, итог — документированный
исход, а Ctrl+C и отмена задачи пробрасываются и ничего не оставляют после себя в
базе. Различает их одна функция, `outcome.must_propagate`; полноту держат тесты
`tests/test_notifier_guard.py` — чужой `Exception`, все виды прерывания и отказ
базы на каждом шаге. Токен бота из текста ошибки вырезается до записи в лог и в
`last_error`.

**Клиент заблокировал бота.** Пока метка `users.bot_blocked_at` стоит,
`active_subscriptions` клиента пропускает — матчер не ставит ему в очередь, — а
каждый проход нотифаера первым делом отменяет ждущие строки всех, у кого метка
есть: очередь наполняют и матчер, и сборщик отложенных ответов, и ни один не
обязан помнить про блокировку. Пауза слежения выведена запросом, а не записана в
подписку: подписка, срок и курсор целы, ручная пауза (`is_active`) не
затрагивается, а метку снять — значит слежение возобновилось, ничего больше
делать не надо. Метку ставит нотифаер (по 403) и бот (по апдейту `my_chat_member`
со статусом `kicked`, чтобы не узнавать о блокировке отправкой), снимает апдейт
`member`. Второй путь снятия — любое сообщение или нажатие клиента
(`bot/reachability.MarkReachable`): заблокировавший бота написать ему не может,
значит метка устарела. Он нужен, потому что апдейт может потеряться (бот лежал
дольше суток, а Telegram хранит неполученное ровно столько) или обработаться не
в том порядке (блокировку и снятие одной пачкой разбирают разные задачи), а
клиент, заплативший за слежение, молчал бы навсегда. Middleware не вешается на
`my_chat_member` — апдейт о блокировке тоже «от клиента» — и пишет в строку, только
когда метка стоит. Подписка при блокировке не отменяется и звёзды не
возвращаются: это решение владельца, и оно ещё не принято.

**У очереди есть срок годности.** Простоя нотифаера хватает на сутки (деплой,
упавший контейнер, долгий 429), и раньше «мгновенные» уведомления вчерашней
давности уходили как новые — о лоте, который уже продан. Теперь первым делом
каждый проход отменяет (`cancelled`, причина в `last_error`) строки старше срока:
сутки для всех (`expired`, `OUTBOX_TTL_H`). Шесть часов после окончания подписки —
другое правило, его применяет матчер (`MONITOR_LAPSE_GRACE_HOURS`, раздел 7.1):
правило «шесть часов» живёт в одном месте. Возраст считается от времени, на которое строка
назначена (`scheduled_at`), а не от постановки: подборка на 18:00, поставленная
утром, вечером ещё свежая. Повтор после сбоя сдвигает `scheduled_at` вперёд, но
застрявшую строку останавливает потолок попыток, а не срок. У отложенного ответа
после сбора подписки нет, и ждёт он общие сутки.

**Подборка режется по границе карточки.** Bot API принимает до 4096 знаков и
на длинном тексте отвечает 400 «message is too long»: подборка из девяти
карточек (≈ 460 знаков каждая) раньше пропадала целиком — все карточки разом.
`notifier/digest.split` режет подборку клиента на сообщения жадно и по порядку:
карточка не разрывается, сообщение не длиннее 4096 знаков (меряется по HTML-строке,
то есть с запасом — Telegram считает уже разобранную разметку) и не больше восьми
карточек, даже если текст влезает. Подборка из нескольких сообщений нумеруется
(«1 из 3»), и каждая часть — отдельная транзакция: сбой отправки одной части не
трогает остальные. Карточка, одна длиннее лимита, получает сообщение целиком для
себя, а её соседи не страдают; заголовок карточки обрезается до 200 знаков ДО
экранирования, чтобы `&amp;` не оказался разрезан. Весь чужой текст проходит
через `html.escape`, а `render` не бросает на чужих данных — его вызывают при
планировании, и бросок уронил бы проход, а не одну отправку.

Чего в контуре ещё нет: полного LLM-извлечения и продавца. Явные атрибуты
извлекаются детерминированно; digest, тихие часы и раздельные времена постановки
и фактической отправки реализованы. Полный контракт и конкурентные гарантии —
в [universal-search.md](universal-search.md).

### 5.0.1 Дедуп кросспостов — отпечаток, а не побайтовый хеш

`raw_messages.text_hash` схема с первого дня описывала как «sha256
нормализованного текста: ловит кросспостинг одного объявления в пять групп, где
меняются только эмодзи и пробелы». Считался он от сырого текста, то есть ловил
лишь побайтовый повтор: другой смайлик или лишний перевод строки — и одно
объявление становилось двумя карточками. Комментарий описывал замысел, код — нет.

Теперь отпечаток считает `domain/fingerprint.py`: регистр вниз, любые
несловесные символы схлопываются в пробел, **и ничего больше**. Цифры и буквы
не трогаются — «Honda 125» и «Honda 150» обязаны разойтись, — а `\W+` берётся
по Unicode, а не списком разрешённых алфавитов: рынок трёхъязычный, и
перечисление алфавитов означает однажды забыть чужой (`xe máy` не смеет стать
`xe m y`).

Решение о дубле принимает воронка: она находит активную карточку ДРУГОГО
сообщения с тем же отпечатком. Уникальность `(chat_tg_id, msg_id)` здесь
бесполезна: при кросспосте сообщения разные, объявление одно. Более свежий
репост освежает ссылку и дату канонической карточки. Если новый разбор исправил
направление сделки, категорию или город, старая карточка выключается, а
исправленная получает новый cursor id и становится видна существующим
подпискам. Только неизменившаяся старая копия получает стадию `duplicate`.

В объявлении прошедшем offer-гейт намерение `rent` означает предложение аренды,
то есть карточку `rent_out`. Это покрывает не только «сдам», но и обычные
заголовки прокатов вроде «АРЕНДА БАЙКОВ»; они не могут молча стать продажей.

Строки, принятые старым коллектором, несут хеш старой схемы и с новыми не
сойдутся. Отдельного прохода пересчёта нет и не нужно: воронка читает каждую
строку ровно один раз и в этот момент держит текст в руках, поэтому освежает
отпечаток тем же запросом, что меняет стадию.

### 5.0.2 Чтение цены из текста объявления

Цена нужна и живому поиску по Telegram, и обработке архива, поэтому знание одно и
лежит в `domain/`: ни один из модулей ниже не знает про базу.

| Модуль | Что делает |
|---|---|
| `text_clean.py` | возвращает цифрам вид цифр: «жирные» `𝟙𝟚 𝟝𝟘𝟘`, кейкапы `1️⃣5️⃣🔣000`, кириллическая «О» вместо нуля, скобки вокруг цены |
| `price_vocab.py` | как здесь пишут цену: единицы (`млн`, `tr`, `🍋`, `кк`), валюты, метки, чужие суммы, сроки |
| `price_numbers.py` | запись числа и перевод в донги: `9 000 000`, `9tr5`, `19.5 vnd`; вилка или «номер — цена»; потолок и пол правдоподобия |
| `price_facts.py` | какая сумма в тексте похожа на цену предмета и чем это подтверждено |
| `price_bounds.py` | границы здравого смысла по категории и стороне сделки |
| `prices.py` | выбор одной цены из найденных; `fits_budget` — влезает ли она в колонку «донги за месяц»; `price_hint` для живого поиска |
| `pipeline/listing_price.py` | что из цены идёт в колонки `price_*`, а что — в атрибуты |
| `sources/telegram_mapping.py` | `price_context`: категория и сторона предложений из плана поиска — для живого разбора |

**Почему прежний разбор терял цену.** Он брал число только после слов
«цена / price / giá». Замер 03.10.2026 по 18 868 активным карточкам архива: у
56% жилья в аренду (7355 из 13 177) цены в базе не было, а в 90% их текстов сумма
стояла — после «Арендная плата:», «Стоимость аренды», в строке «💵 14M VND/month»
или в итоговой строке бота-агрегатора «💰 9 000 000 ₫/мес #booking». Живой случай:
пост «Oceanus» с «Арендная плата: 12.5 млн VND / месяц» уходил карточкой «цена не
указана».

**Что делает новый разбор.** Метка перестала быть обязательной, но каждая сумма
получает контекст, и берётся только арендная плата или цена предмета:

- **чужие суммы отбрасываются** — залог и депозит, вода и электричество
  (`/кВт`, `/чел`), управление, интернет, парковка, уборка, регистрация, резерв,
  надбавка за питомца (`+500 000`, «— интернет», «/мес за питомца»). Слово «за что
  платят» называет сумму, только если стоит **вплотную** (не дальше двух слов) и
  целиком, а не основой: «электр» читало «электроскутер» как электричество, а
  «без комиссии 12 млн» и «с парковкой 15 млн» теряли цену. После «без», «с»,
  «включая» слово описывает предмет, а не сумму;
- **у суммы есть сила подтверждения**: `label` — метка в начале фразы или после
  двоеточия («Цена:», «Аренда», «DT: 48m2 - Giá: 4,5tỷ», в том числе метка строкой
  выше над списком цен) — сильнее `weak` (метка и слова без двоеточия: «цена
  ремонта 2 млн»), `inline` (метка посреди фразы без знака: «Прошёл ТО стоимостью
  4,2 млн») и `money` (значок денег перед суммой); те сильнее суммы без пометки.
  «Арендатор» — человек, а не метка, «оплата клининг» — сбор, «Стоимость покупки»
  в объявлении об аренде — цена другой сделки. **Итоговая строка бота-агрегатора
  не читается вовсе**: на 5051 такой строке архива она в 94% повторяет цену текста,
  а где расходится — выдумывает («АРЕНДА ДО 10 МЛН» принято за цену, площадь «72 м²»
  за 72 200 000 ₫). Хэштеги тоже ярлыки, а не суммы: «#от10до15млн» — корзина
  фильтра агрегатора;

- **продавцы пишут цену по-разному**: `15.000. 000`, `19.5 vnd`, `12M`, `20🍋`,
  `195кк`, `9tr5`, `Giá 3.7tr`, «от 4 до 15 млн», «3–10 млн». Число перед тире —
  номер, а не начало вилки, если это хвост слова («35 м2 — 12 млн»), если сумма за
  тире на порядки больше («№402 — 9 500 000»), если тире с пробелами и сумма
  втрое больше («2 — 13 млн») или если вилка идёт вниз («Yamaha NVX 155 — 25 млн»
  — это 25 млн, а не 155). Цену прячут цифрами-эмодзи и «жирными» цифрами, и
  `text_clean.py` их читает;
- **число без единицы и валюты** («Цена 19.500», «Цена 8.5») — сокращённые тысячи
  или миллионы; масштаб выбирают границы категории, а без категории такое число
  не угадывается. Верим ему только после слова «цена» вплотную либо после значка
  денег и заголовка списка цен — и тогда за числом не может стоять слово («2 с
  ванной», «2 качественных шлема» под заголовком «Аренда в районе…:» — не два
  миллиона), а заголовок «В стоимость включено:» списком цен не считается. Год,
  пробег, `125cc`, телефон, «этаж 4», «2, 3 этаж», «договор 3-6 месяцев»,
  «2-month deposit» ценой не становятся;
- **границы категории** (`price_bounds.py`) страхуют от остального: квартира в
  аренду не стоит 150 тысяч в месяц, а скутер — 30 миллиардов. Выход за границу —
  «это не цена», и честнее остаться без цены, чем показать сбор вместо аренды;
- **срок**: аренде нужна помесячная цена, продаже — цена без срока. Цена «6 млн/мес»
  в объявлении о продаже дома — доход соседнего, а не цена дома, а «аренда 200к/сутки»
  рядом с продажей байка — не цена байка. Единицы срока — целые слова: «мес» —
  начало слова «место», и «ЦЕНА 9 млн. Место осмотра» теряла цену; срок бывает
  и перед меткой («посуточная аренда: 2.2 млн»).

**Что идёт в колонки.** `price_amount` — донги, `price_period` — `month` или
`once`: именно так их читают отбор по бюджету, ранжирование и карточка. Суточная и
понедельная цена, сумма в долларах и верх вилки в этот договор не влезают
(`prices.fits_budget`) и лежат в атрибутах (`rate_amount`, `rate_currency`,
`rate_per`, `rate_up_to`, `price_up_to`): 250 тысяч в сутки в колонке
`price_amount` прошли бы любой месячный бюджет. Бюджетный фильтр считает такую цену
неизвестной, как и раньше. **Эти атрибуты пока никто не читает**: ни карточка, ни
фильтр; показ суточной цены — задача карточек, а не разбора.

**Живой поиск.** Он видит только текст, поэтому `price_hint` отдаёт `price_vnd`
осторожно. План поиска знает категорию и намерение клиента и через
`telegram_mapping.price_context` передаёт их разбору: ищущему аренду видят тех, кто
сдаёт, и границы категории отсеивают сборы («700 000 донгов в месяц» у квартиры за
17 млн), а срок читается по стороне. Без стороны сделки суточная, недельная и
годовая цена не называется вовсе, а если в тексте есть и разовая, и месячная
(«Bán căn hộ 4,39 tỷ, có HĐ thuê 13 triệu/tháng»), по тексту не угадать, какая из
них цена, — честнее ничего не назвать. Падение разбора на одном сообщении не
уносит остальные находки запроса: `TelegramGroupsSource._items` ловит его, пишет
`telegram.item_failed` и идёт дальше.

**Цена самого разбора ограничена.** Окно контекста слева 200 знаков, справа 60,
не больше 60 сумм на строку и 6000 знаков на текст; число длиннее 18 цифр — не
цена; запись `9tr5` ищется только с начала серии цифр. Прогон 4-килобайтных
враждебных текстов (03.10.2026) нашёл два дефекта: строка из тысячи чисел считалась
по четыре секунды, а число из четырёх тысяч девяток давало `OverflowError` и
останавливало воронку на одном сообщении. Ревью нашло третий: таб, U+1680 или U+001F
внутри числа («1.<таб>000.000») давали `ValueError`, потому что регулярка числа
пускала любой пробельный знак, а чистка знала только пробел, и четвёртый —
квадратичную `9tr5` на серии из шести тысяч цифр. Пределы и случайный перебор
(`tests/test_price_safety.py`) закрепляют это свойством «любой текст — цена или
`None`», а не списком ожидаемых ошибок.

**Результат** (прогон по всем 18 868 активным карточкам архива, ошибок нет): цена
найдена у 98,7% квартир в аренду (13 006 из 13 177, было 5 822), у 98,8% домов
(3 198 из 3 236), у 94,9% байков на продажу (1 947 из 2 051, было 968), у 57% аренды
байков (60 из 105, было 3: у остальных цены в тексте нет). Из прежних значений 72
изменились или пропали; просмотр показал, что это в основном ошибки старого разбора
(`5500` и `40000` вместо «5,5 млн» и «40 млн», «1,4 млн» у квартиры в центре,
«2 tỷ» вместо «2 tỷ 300 triệu»), а часть — выбор наименьшей цены каталога вместо
первой. Итоговая строка агрегатора раньше давала цену 34 карточкам; теперь её
нет, и это сознательная потеря: у 10 из этих 34 цен ревью нашло выдуманное
значение. Точность ревью проверило выборкой: 179 из 180 новых цен верны (прежняя
версия разбора).

**Проверка тестами.** `tests/test_prices.py` — реальные шаблоны из чатов;
`test_price_regressions.py` — находки ревью, каждая отдельным случаем (44 из 65
краснеют на прежнем коде); `test_price_vocabulary.py` — по примеру на каждое слово
словаря письма, парами «настоящая цена — соперник поменьше»: один факт на текст
выигрывает при любой метке и слово не проверяет; `test_price_safety.py` — свойство
«любой текст — цена или `None`» на случайных строках из цифр, единиц, меток и редких
пробелов. Мутационная проверка ревью (115 мутаций словаря и логики) в первой
версии оставляла живыми 49: слово можно было вычеркнуть, и тесты молчали. Теперь
прогон по 209 мутациям оставляет живыми ноль. Одна мутация (точечная защита
в `OTHER_AFTER_RE`) эквивалентна: её нельзя убить, и защита удалена как мёртвый код.

**Чего этот разбор не делает.**

- Каталог из нескольких товаров в одном посте даёт одну цену — наименьшую («от»),
  остальные уходят в `price_up_to`.
- Продажа дороже 10 млрд донгов (вилла «27 tỷ») не читается: потолок
  `MAX_PLAUSIBLE_VND` закреплён тестом после падения воронки 01.09.2026, и
  пересматривать его — отдельное решение.
- После вердикта модели, меняющего сторону или категорию, цена в живом потоке не
  перечитывается: 1 054 карточки из 18 888 (5,6%) сменили то и другое после чтения,
  у 92 из них цена из-за этого другая (74 потеряны, 11 неверных, 7 лишних, у 17
  пропали `rate_*`). Исправляет это проход догона по тексту (пакет «enrich»).
- Цена в долларах рядом с ценой в донгах уступает ей, даже когда слабее по
  пометке: «Цена 180 дол.» рядом с «около 100 донгов» даёт 100 млн.
- Показанный текст цены (`raw`, он же `RawItem.price_raw`) — читаемая запись после
  очистки: `9tr5` показывается как `9.5 tr`, «жирные» цифры — обычными. У 3,7%
  подсказок живого поиска он не подстрока оригинала.
- Слова, которых в словаре нет: «мл» (миллионы) — в русской речи это миллилитры.

### 5.0.3 Чтение фактов из текста объявления

Карточки архива жили с пустыми полями: район, площадь, этаж, балкон, лифт — 0%;
заголовок — первая строка поста («AN-HOME» — 1437 карточек из 18 868, «#нячанг
#аренда #сдам» — 486); язык у всего Telegram не стоял. Диалог не мог сузить выдачу
по району, а карточка выглядела голой. Читает всё это `pipeline/listing_facts.fact_columns`,
вызываемый из `listing_from`; сами чтения — чистые функции `domain/`, без ввода-вывода.

| Модуль | Что делает |
|---|---|
| `facts_text.py` | текст для чтения: `lines`, `low` и `folded` (без вьетнамской диакритики: «tặng» ≠ «tầng»); вырезаны ссылки, хэштеги, меню; пределы 6000 знаков на текст и 600 на строку |
| `facts_vocab.py` | словарь удобств, отрицаний («без», «нет», «no»), «рядом» (`NEARBY_RE`), питомцы, кухня |
| `facts_amenities.py` | балкон, лифт, бассейн, зал, стиральная машина, кондиционер, питомцы, кухня: `True`/`False`/нет записи |
| `facts_area.py`, `facts_floor.py`, `facts_terms.py`, `facts_sea.py` | площадь, этаж, залог и срок в месяцах, расстояние до моря |
| `facts_housing.py`, `facts_bikes.py` | набор чтений по категории: жильё и байки |
| `districts.py` + `districts_nha_trang.py` + `districts_da_nang.py` | справочник мест как ДАННЫЕ (89 мест): `(slug, имя, зона, вид, синонимы)` |
| `facts_place.py` | район, зона и город по тексту |
| `listing_title.py`, `text_lang.py` | заголовок и язык |

**Правила чтения.** Отрицание вплотную к слову даёт `False`, не «нет записи»:
«без балкона» — это ответ. Нейтральные обороты не считаются утверждением («без
использования лифта»), частичные («нет кондиционера в гостиной») — тоже. «Рядом
с…» вырезается до конца предложения: «рядом бассейн соседнего комплекса» не даёт
`pool`. Противоречие внутри поста — `None`, а не угадывание. Числа читаются только
в пределах одной строки: «контракт от 12 мес ⏎ депозит 2 мес» когда-то давал залог 12.

- **Жильё:** `area_m2` (границы 8–1000; полезная площадь важнее общей, участок,
  размеры и «часть» не площадь; диапазон — меньшая граница), `floor` (порядковый
  этаж квартиры; у дома — этажность `floors_total`; разные этажи — `None`; этаж
  удобства «бассейн на 31 этаже» не считается; вьетнамское `lầu N` = N+1),
  `balcony`, `elevator`, `pool`, `gym`, `washing_machine`, `air_conditioner`,
  `pets_allowed`, `kitchen`, `deposit_months`, `deposit_amount`, `min_term_months` (только аренда),
  `sea_distance_min` или `sea_distance_m` («на байке» не читается). Комнаты, мебель
  и вид на море приходят от `parse_query`: слой `domain` не импортирует `search`,
  а второй список слов разъехался бы с первым.
- **Байки:** `year` (метка или единица; голый год — только в первых двух строках и не
  после названия месяца), `mileage_km` (только после «пробег»; «км/ч» — скорость),
  `papers` (`blue_card` | `none`; слова внутри отрицания не считаются), `no_license_claimed`,
  `bargain` (`negotiable` | `fixed`). У проката — только `papers` и `no_license_claimed`.
- **Район и зона.** Название места — данные, а не ветвление: каноническое имя
  идёт в `Listing.district`, зона (`north`/`center`/`south`/`west`) — в атрибут `zone`.
  Места трёх видов: район < комплекс < улица; зона проставлена только там, где на
  корпусе набралось ≥10 совпадений и ≥80% согласия. Читается тремя кругами — строки-
  метки («Район: …»), первые три строки, весь текст без меню; место из подвала,
  противоречащее зоне заголовка, отбрасывается. Ссылки на соседей («до Mango Garden
  5 минут», «from Vinpearl») место объявления не определяют. Город голосуют различные
  места; явное «Da Nang» — два голоса; улицы не голосуют.
- **Заголовок:** первая содержательная строка из шести первых, ≤80 знаков, обрезка
  по слову (`…`). Пропускаются хэштеги, ссылки, телефоны, эмодзи, бренд-одиночки,
  ценовые строки, рамка («Квартира в аренду»), служебные фразы («Свободна с…») и
  «ключ: значение». Если содержательной строки нет — из фактов («Студия · 35 м² ·
  Север Нячанга»), иначе «Объявление».
- **Язык:** `ru` при ≥12 русских буквах и их доле ≥0,25 (двуязычный русско-английский
  пост читается по-русски; вьетнамский пост с короткой русской строкой агрегатора
  остаётся `vi`), иначе вьетнамская диакритика ≥5% латиницы и вьетнамских слов не
  меньше английских — `vi`, иначе по частотным словам; нет букв — `None`.

**Слияние.** Явное непустое значение из `parse_query` главнее прочитанного
(`{**факты, **известное}`): факты дополняют, а не перечитывают. Для города вне
справочника место не читается: «в центре города» в ханойском объявлении не станет
зоной Нячанга.

**Контакты не читаются и не хранятся.** Телефон, @username и Zalo в карточку не
попадают; в ней стоит ссылка на оригинал. Телефон в заголовке вырезается.

**Города.** Город называет сам пост (решение владельца 04.10.2026): `read_place` отдаёт
`PlaceFact.city`, `listing_from` кладёт его в `Listing.city` раньше города чата и
умолчания `parse_query`, и дананговский лот в нячангской группе становится карточкой
Дананга. Голосуют различные места, явное «Da Nang» — два голоса, улицы не голосуют; город
читается только у Нячанга и Дананга (у остальных нет справочника мест), поэтому ханойский
пост городом справочника не становится. На архиве 1345 из 16 600 жилых текстов называют
место Дананга; существующие карточки правит перечитывание, а не эта правка.

**Залог суммой.** «Депозит 18 млн» читает `facts_terms.read_deposit_amount` в донгах
(`deposit_amount`, только карточка: паспорт спрашивает месяцы). Диапазон 100 тыс.–200 млн;
голое число без единицы — месяцы, не сумма; доллары не читаются. При известной месячной
аренде в донгах воронка пересчитывает сумму в `deposit_months` с точностью до полумесяца
(0,5–6 месяцев, иначе не пересчитывает); месяцы, названные в самом посте, главнее.

**Смена категории вердиктом модели** (`worker/screening.py`) перечитывает факты под новую
категорию тем же `fact_columns`, а не оставляет только разбор запроса: площадь, залог,
срок, год и пробег больше не пропадают вместе с коробкой передач.

**Сравнение чисел паспорта и карточки** (`matching/attribute_match.py`) — по смыслу:
площадь ±15%, месяцы залога и срока ±0,5, объём двигателя — полоса `ENGINE_CC_BAND` с
направлением «от/до», прочие числа точно, но «2» и «2.0» равны; нечисловое — строкой без
регистра. И отсечение (`_known_attribute_conflicts`), и доля совпавших (`_attribute_fit`)
спрашивают один и тот же допуск.

**Результат** (замер 04.10.2026 на 18 868 активных карточках, 45 секунд; до пакета
район, зона и все факты были пусты):

| Категория / сделка | район | зона | площадь | этаж | балкон | лифт | бассейн | залог | срок |
|---|---|---|---|---|---|---|---|---|---|
| квартира / аренда (13 177) | 72,4 | 74,6 | 52,8 | 19,2 | 35,8 | 17,1 | 13,9 | 61,8 | 51,9 |
| дом / аренда (3 236) | 64,2 | 69,7 | 66,6 | 36,4 (этажность) | 7,4 | 7,8 | 10,0 | 68,7 | 58,5 |

У байков на продажу (2 051): год 66,5%, пробег 23,0%, документы 52,7%, «права не
нужны» 23,8%, торг 23,4%. Мусорные заголовки (короче 8 знаков, хэштеги, без букв):
19,2% → 0,1% у квартир, 21,3% → 0,2% у домов. Меньше ориентира R3 только этаж (19%
против 23%): дома считаются отдельно, а разные этажи в одном посте дают `None`.
Залог суммой («депозит 18 млн») не читается.

**Предел чтения ограничен:** текст 6000 знаков, строка 600; прогон 4-килобайтных
враждебных текстов укладывается в 1,5 с (`tests/test_facts_hostile.py`).
Покрыто: `tests/test_facts_*.py`, `test_districts.py`, `test_listing_title.py`,
`test_text_lang.py`, `test_listing_facts.py`; нижние границы долей на корпусе
(`test_facts_corpus.py`) ловят деградацию словаря в CI. Каждое правило проверено
мутацией: без него хотя бы один тест краснеет.

### 5.0.4 Проход догона: накопленные карточки, пересчитанные из исходного текста

Разбор цены из 5.0.2 работает для новых сообщений, а в базе лежат 18 868
активных карточек архива, посчитанных прежним разбором: у 56% жилья в аренду
цены нет, хотя в тексте она есть, у части стоят неверные значения (`5500` и
`40000` вместо «5,5 млн» и «40 млн»). Воронка читает каждое сообщение один раз
(поэтому отпечаток из 5.0.1 она освежает на лету) и накопленное не
перечитывает: без отдельного прохода эти карточки остались бы такими навсегда.
Нужен один безопасный проход «пересчитать из исходного текста», пригодный и для
следующих выводов (район, площадь, этаж, заголовок, язык), а не только для цены.

**Реестр выводов** (`pipeline/enrich.py`). Вывод из текста — класс с `name` и
`derive(listing, text)`: он получает карточку и исходный текст, а возвращает
патч (`domain/listing_patch.py`) — что в карточке стоит изменить, — и ничего не
пишет. Выводы перечислены в одном месте, `DERIVATIONS`; `derive()` прогоняет их
и сливает патчи. Добавить вывод — дописать одну строку в этот кортеж: воронка,
воркер, репозиторий и отчёт не меняются, потому что исходы называются по
выводу (`price.filled`, `district.filled`) и попадают в отчёт сами. Договор
вывода держит тест, который берёт реестр, а не собственный список: исход есть
всегда и назван по выводу; патч — только разница, поэтому повторный проход по
результату пуст; два вывода не могут претендовать на одну колонку или один ключ
атрибутов — это ошибка, а не очерёдность.

**Что проход вправе менять, записано списком.** Цена, район, заголовок, язык
(`PATCHABLE_COLUMNS`) и атрибуты — слиянием и точечным удалением ключей, одним
UPDATE: `(attributes - удаляемые) || патч`. `is_active`, `screened_at`,
`posted_at`, `deal_type`, `category` и `city` — жизнь и личность карточки: их
решают воронка и проверка модели, и пересчёт по тексту перезаписал бы чужое
решение. Патч с такой колонкой не создаётся вовсе — это ошибка построения, а не
записи, и тест перебирает все поля записи, а не список из кода.

**Цена читается под ИТОГОВОЙ стороной и категорией карточки.** Вердикт модели
(`worker/screening.py`) приходит после извлечения и может сменить сторону сделки
и категорию, а границы правдоподобия у аренды и продажи различаются на два
порядка: «аренда квартиры» выбрасывает 1,36 млрд, которые для продажи — цена.
Замер ревью 03.10.2026 на 18 888 карточках: у 1 054 (5,6%) пара «категория,
сторона» после вердикта не та, под которой читалась цена, и у 92 цена из-за
этого неверна — 74 карточки остались без цены (при извлечении её выбросили
границы аренды), у 11 сумма аренды лежит как цена продажи (13 000 000 разово
вместо 4 390 000 000), у 7 сумма вне границ итоговой стороны, а в тексте цены
нет (15 000 000 разово у дома на продажу); ещё у 17 при смене категории
`parse_query` пересобрал атрибуты, и `rate_*` и `price_up_to` потерялись.
Поэтому и разбор, и границы берут `category` и `deal_type` СТРОКИ такими, какие
они сейчас; проход их не пересчитывает и не пишет, и тест закрепляет это на
смене `rent_out` → `sell`.

**Политика замены цены** (`pipeline/enrich_price.py`, функция `judge`; по тесту
на каждую строку). Один исход на карточку:

| было в базе | нашли по тексту | исход | пишем |
|---|---|---|---|
| цены нет | сумма в донгах | `price.filled` | колонки цены |
| цены нет | суточная или в валюте | `price.rate_only` | атрибуты `rate_*` |
| цены нет | ничего | `price.absent` | — |
| есть | то же | `price.same` | — |
| вне границ итоговой стороны | сумма внутри границ | `price.replaced` | колонки цены |
| вне границ | ничего или только ставка | `price.erased` | колонки цены → пусто, старое значение — в `attributes.price_erased` |
| в границах | иная сумма | `price.disagreed` | — |
| в границах | ничего или только ставка | `price.lost` | — |

- **Вне границ — заведомая ошибка, и стирать её можно.** 5 млрд за аренду дома,
  суточная ставка в месячной колонке, «13 000 000 разово» у квартиры, которую
  купили бы за 4,39 млрд: это не цена, и честная замена ей — найденная цена или
  пустое место. Заменяет любая правдоподобная новая сумма, какой бы строкой
  текста она ни подтверждалась: старое значение хуже любого правдоподобного.
  Если новая сумма тоже вне границ (разбор такого не отдаёт, но политика на это
  не полагается), замены нет.
- **В границах не стираем и не правим.** «Потеряно» значит «в тексте цены не
  нашли, а в базе правдоподобная есть»: ошибиться мог и прежний разбор, и новый,
  поэтому значение остаётся и считается в отчёте. Две правдоподобные цены
  разошлись — чаще всего это наименьшая цена каталога вместо первой, и выбор мог
  быть осознанным: тоже остаётся и считается. Для пары без границ «вне границ»
  не определено — такое значение не заменяется и не стирается.
- **Суточная цена и доллары — в атрибуты** (`rate_amount`, `rate_currency`,
  `rate_per`, `rate_up_to`); колонка `price_amount` их не принимает: 250 тысяч в
  сутки в месячной колонке прошли бы любой бюджет.
- **Атрибуты цены пересобираются из нового факта целиком.** Семья
  `PRICE_ATTRIBUTES` (`price_up_to`, `rate_*`): что новый разбор выдал, то
  пишется, а что не выдал, то убирается — иначе от прежней стороны сделки
  оставались бы чужие `rate_*`. Остальные атрибуты карточки (марка, комнаты, всё,
  что извлечено иначе) не трогаются. Одно исключение — `price_up_to`: верх вилки
  принадлежит колонке. Рядом с оставленной старой ценой (`disagreed`, `lost`)
  верх вилки новой дал бы «7 млн — до 11 млн» из двух разных цен, а уже
  стоящий — от старой цены, которую мы оставили, — не стирается. Ставки `rate_*`
  от колонки не зависят и пересобираются всегда. Список ключей сверен с тем,
  что `price_columns` способна записать: новый ключ там без записи здесь
  краснит тест.
- **В патч попадает только разница**, поэтому повторный проход пуст и в базу не
  ходит: идемпотентность держится на этом, а не на счастливом совпадении.

**Сверка на выгрузке** (03.10.2026, все 18 868 активных карточек архива, версия
разбора из этой ветки; после уточнений ветки цены числа чуть сдвинутся, а тесты
политики от них не зависят — разбор и границы правдоподобия в них подменены
заглушками, а провод на живые — один модуль, `tests/test_enrich_wiring.py`). Цена найдена у
тех же 98,8% квартир в аренду (13 017 из 13 177), 98,9% домов (3 199 из
3 236), 95,1% байков на продажу (1 950 из 2 051) и 57,1% аренды байков (60 из
105): совпадает с 5.0.2 до единицы. Из 8 606 карточек, у которых цена уже была,
8 530 совпали, 21 заменена (старое вне границ), 34 стёрты (вне границ, и
заменить нечем: 26 раз текст молчит, 8 раз в нём лишь суточная ставка), 19
расхождений в границах, 2 потеряно. Из 10 262 карточек без цены 9 852 получают
её, 49 получают суточную цену или доллары в атрибуты, у 361 цены в тексте нет.
Патч непуст у 9 995 карточек (9 907 с колонками цены, остальные только
атрибуты); повторный проход по результату — 0 записей. Доля карточек с ценой
в колонке: 45,6% → 97,6%.

Сколько из этого объясняется сменой стороны или категории, отчёт прохода
показывает отдельной пометкой `after_verdict.*`. Критерий — воспроизводимость,
а не просто различие пар: правка объясняется сменой, если чтение текста под
прежней парой (как её присвоила бы воронка, `worker/enrich_origin.py`) даёт ровно
то, что лежит в карточке, а под итоговой — иное. Пары различаются у 6% карточек,
но почти везде цену нашёл бы и прежний разбор: «5500» вместо «5,5 млн» от стороны
не зависит. На выгрузке объяснено сменой 51 заполнение и 1 стирание (пары
различались у 568 заполнений, 2 замен и 3 стираний). Ревью насчитало на живых
карточках больше (74 заполнения, 11 замен, 7 стираний): расхождение ожидаемо —
база свежее, а пометка здесь консервативна, она называет только то, что чтением
под прежней парой воспроизводится, — и сверять эти числа стоит по id из отчёта,
а не по итогам.

**Сам проход** (`worker/enrich.py`; запуск, коды выхода и порядок действий на
сервере — [deploy.md, 7.3](deploy.md)). Это разовая операция, а не задача цикла
воркера: перед ней нужна копия таблицы и чтение сухого прогона человеком. Она
живёт подкомандой образа воркера (`python -m sniffer.worker enrich`), потому что
ей нужны тот же код разбора и те же версии зависимостей, что у воронки, — иначе
пересчёт и новые карточки считали бы цену по-разному.

- **Курсор по `listings.id`, пачки по 200.** Страницу читает короткая
  транзакция, патчи считаются в памяти, пачку пишет другая транзакция. Читаются
  активные карточки архива вместе с исходным текстом из `raw_messages`
  (`db/repositories/listing_enrichment.py`); погашенные (81% таблицы, их никто не
  видит) и карточки Chotot (цена приходит структурой) не трогаются. Карточка без
  сырья не исчезает, а попадает в отчёт строкой `skip.no_text`. Строки,
  появившиеся во время прохода, лежат правее курсора и подхватываются в конце.
- **Одна кривая не рушит пачку.** Запись каждой карточки идёт в своём SAVEPOINT:
  число, не влезшее в `NUMERIC(14,2)` (так 01.09.2026 встала воронка), стоит
  одной строки, а остальные записываются. Вывод, не справившийся с карточкой,
  пропускает её и называет себя (`skip.derive_error.price`). В отчёт и в лог
  сбой попадает именем класса, без текста: в тексте ошибки базы лежат параметры
  SQL — заголовки и атрибуты объявлений с телефонами.
- **Рядом с живым воркером.** Пока проход считает патч, воронка может освежить
  карточку кросспостом, а проверка модели — сменить категорию и сторону сделки.
  Запись по устаревшей строке перетёрла бы чужое решение, поэтому строка
  обновляется, **только если осталась такой, какой её прочитали**: `UPDATE …
  WHERE id = :id AND <колонки, которые патч пишет и которые вывод читает> IS NOT
  DISTINCT FROM <прочитанное>`. Выбрано сравнение значений, а не версия и не
  блокировка: колонки версии у `listings` нет, и заводить её значило бы менять
  схему и каждого писателя ради одного прохода, а `SELECT … FOR UPDATE` держал бы
  строку, пока работает Python, и заставлял бы воркер ждать нас. Условие
  читается в момент записи, а Postgres на `READ COMMITTED` перепроверяет его по
  последней зафиксированной версии, если строку успели изменить. `IS NOT
  DISTINCT FROM`, а не `=`: у половины колонок бывает NULL, и `NULL = NULL` — не
  истина, карточка с пустым районом не обновилась бы никогда. Цена ошибки — не
  запись и строка `skip.changed_since_read` в отчёте; повторный проход
  подхватит. Атрибуты пишутся на стороне базы одним выражением,
  `(attributes - удаляемые) || патч`: чужие ключи не теряются, а ключи семьи
  цены, которых новый разбор не выдал, убираются тем же UPDATE.
- **Сухой прогон не пишет вообще:** запись не вызывается, а транзакция чтения не
  коммитится, так что даже ошибка в коде оставила бы базу прежней.
- **Идемпотентен.** В патче только разница, поэтому повторный проход пуст и в
  базу не ходит. На всех 18 868 карточках выгрузки проверено в памяти (патчи
  применены, выводы посчитаны заново — пусто), на живом Postgres — в
  `tests/test_db_enrichment.py`.
- **Не трогает** `is_active`, `screened_at`, `posted_at`, `deal_type`,
  `category`: колонки патча — закрытый список, и запись проверена на уровне SQL
  (в `SET` попадают только они).
- **Отчёт:** сколько просмотрено, записано (в сухом прогоне — «записали бы»),
  исходов `price.*`, пометок `after_verdict.*` и пропусков по причинам — всё в
  разрезе (категория, сторона сделки), плюс по нескольку id редких исходов,
  чтобы открыть их глазами. Исход считается только у записанной карточки (в
  сухом прогоне — у той, что записали бы): у пропущенной он ложь. Уходит событием
  `enrich.report` в лог и таблицей в вывод команды; ни текстов, ни заголовков, ни
  контактов в нём нет. Итог печатается и при сбое, и при Ctrl+C: по `last_id`
  проход продолжают с `--since-id`.

**Что получится на выгрузке** (доля карточек архива с ценой в колонке, до и
после; 03.10.2026):

| категория / сторона | карточек | было | станет |
|---|---|---|---|
| квартира / аренда | 13 177 | 44,2% | 98,7% |
| дом / аренда | 3 236 | 53,7% | 98,2% |
| байк / продажа | 2 051 | 47,2% | 94,3% |
| комната / аренда | 116 | 31,9% | 90,5% |
| байк / аренда | 105 | 2,9% | 48,6% |
| велосипед / продажа | 101 | 31,7% | 85,1% |
| все | 18 868 | 45,6% | 97,6% |

«Станет» ниже, чем доля найденных цен из 5.0.2, на стёртые 34 неправдоподобных
значения. Оставшиеся без цены — те, у кого её нет в тексте (у аренды байков — у
43%) или она суточная и лежит в атрибутах (`rate_*`), а не в колонке бюджета.

**Чего проход не делает.**

- Не стирает правдоподобное: значение в границах категории, которое новый
  разбор «не нашёл», остаётся и считается строкой `price.lost`. Стирается только
  заведомо неправдоподобное (`price.erased`) — и это решение стоит проверить глазами
  по id из сухого прогона до боевого.
- Не теряет стёртое: прежняя цена остаётся в `attributes.price_erased`
  (`{amount, currency, period}`), сухой прогон печатает «id → прежняя сумма» для
  каждой стираемой карточки. Курсор, который не двигается, — ошибка прохода
  (`CursorStalled`, код выхода 1), а не вечный цикл.
- Не удаляет чужие ключи атрибутов: убираются только ключи семьи цены
  (`price_up_to`, `rate_*`), и только те, которых новый разбор не выдал.
- Не пересчитывает `confidence` (0,40 или 0,55 — «есть ли цена»): при отборе его
  никто не читает.
- Не защищён от обратной гонки: проверка модели (`apply_screen`) и пересчёт
  категорий пишут `attributes` целиком из копии, прочитанной до их собственной
  работы, и могут стереть ключи, добавленные проходом. Повторный проход вернёт
  их — он идемпотентен.
- Не считает `price_usd_month`: у всех NULL, и заполнять его — отдельное
  решение.

### 5.1 Слой доступа — `db/`

Единственное место в проекте, где есть SQL. Всё выше по слоям получает отсюда
доменные записи и не знает ни про SQLAlchemy, ни про имена колонок.

```
db/engine.py        async engine + сессия на единицу работы
db/models/          ORM-зеркало 001_init.sql, разбито по разделам DDL
                    (источники, разведка чатов, предложения, клиенты, доставка, очередь)
db/mappers.py       строка таблицы ↔ доменная запись
db/repositories/    по одному классу на агрегат
domain/records.py   что репозиторий отдаёт наружу
```

Четыре решения, из-за которых слой выглядит именно так:

- **Схему создаёт SQL-файл, модели её только отражают.** `metadata.create_all`
  здесь не вызывается никогда: расширения, GIN-индексы и `vector(1024)`
  описываются обычным DDL точнее, а два источника правды про схему — это
  гарантированный дрейф. Чтобы зеркало не разъехалось молча,
  `tests/test_db_models.py` сверяет имена таблиц и колонок прямо с
  `001_init.sql`, и делает это без базы — то есть на любой машине.
- **Наружу уезжают dataclass-ы, а не ORM-сущности.** ORM-объект тащит за собой
  сессию: после закрытия `async with` обращение к незагруженному полю падает
  `DetachedInstanceError` уже в боте, далеко от места, где сессия закрылась.
  Заодно это держит правило слоёв — `domain` не зависит ни от чего.
- **Репозиторий не коммитит.** Он получает открытую сессию и работает в её
  транзакции; границу единицы работы ставит вызывающий. Автокоммит сделал бы
  эту границу невидимой в коде, а «прочитал» — неотличимым от «записал».
- **Дедуп сырья живёт на уникальном индексе, а не в коде.** Батч-вставка идёт
  через `ON CONFLICT (chat_tg_id, msg_id) DO NOTHING … RETURNING id`: коллектор
  после каждого простоя перечитывает историю и приносит уже виденное, а
  проверять существование по одному сообщению значило бы делать SELECT на
  каждое и всё равно проигрывать гонку.

Один нюанс `ON CONFLICT`, который стоил падения на живой базе: **по частичному
уникальному индексу цель конфликта не выводится** без того же предиката. Дедуп
расходов (`broker_calls.broker_request_id`, индекс с `WHERE … IS NOT NULL`)
обязан передавать `index_where`, иначе Postgres отвечает «no unique or exclusion
constraint matching the ON CONFLICT specification». На подделке базы этот запрос
проходил бы — поэтому тесты слоя и требуют настоящий Postgres (ниже).

Очередь `jobs` разбирается через `SELECT … FOR UPDATE SKIP LOCKED`: задача
выбирается, помечается `running` и коммитится сразу, дальше воркер работает уже
без замка. Второй воркер не ждёт освобождения строки, а пропускает её и берёт
следующую — иначе рабочие процессы выстроились бы в очередь за одной задачей.
Возврат в очередь после ошибки идёт через `run_after`; потолок попыток ставит
вызывающий, потому что он один знает, сколько их осмысленно для его `kind`.

**Кто ещё читает этот слой: источники.** Адаптеру `telegram_groups` нужен
реестр чатов, а архивному источнику — `listings`. Зависимость идёт вниз
(`sources → db`) и целиком сведена в `sources/chat_directory.py`: там собраны
реестр, чтение каталога и материализация проверенных live-находок. Сами
адаптеры про SQL и `sniffer.db` не знают — они видят протоколы. Подробности и
цена ошибки исходной проводки —
[spec-v2, 4.4](spec-v2.md#44-telegram-группы--что-стоило-дорого-узнать).

**Второй такой потребитель — разведка чатов.** Она пишет в `chat_candidates`,
`chat_rejects` и `chat_join_events`; ORM-зеркало этих таблиц лежит в
`db/models/discovery.py`. Знание о `db` к ней тоже не протекает: нужное описано
протоколами `ChatRegistry` / `CandidateQueue` / `RejectedLog` / `JoinLedger` в
`sources/telegram_discover_reference.py` и подставляется снаружи.
`collector/discovery.py` связывает их с репозиториями Postgres: короткая
транзакция занимает слот, затем один Telegram-вызов вступает в один чат, а
запись сразу появляется в реестре поиска. Заглушек в памяти намеренно нет:
журнал вступлений в памяти обнулялся бы каждым перезапуском и разрешал бы три
вступления после каждого деплоя — отказ, который замечают по бану аккаунта, а
не по красному тесту. Устройство — [spec-v2, 4.5](spec-v2.md#45-telegram_discover--как-набирается-список-чатов).

**Тесты слоя требуют настоящий Postgres.** Схема Postgres-специфична, на sqlite
не поднимается, а подделка была бы зелёной ровно в тех местах, которые и
ломаются. Поэтому тесты с базой берут адрес из `TEST_DATABASE_URL` и
пропускаются, когда её нет: у разработчика без Docker прогон остаётся зелёным,
в CI поднимается `pgvector/pgvector:pg16`, накатывается `001_init.sql` и они
выполняются. Чистая логика — маппинг и сверка со схемой — покрыта обычными
тестами без базы.

### 5.2 Журнал показов и квота карточек

Правила и числа — [`monetization.md`](monetization.md): бесплатно 10 уникальных
карточек за период на Telegram-аккаунт, по подписке до 300. Здесь — как это
разложено по слоям и почему именно так.

```
domain/plans.py        10 / 300 / 10 ⭐ — единственное место с числами; card_cap(slots)
domain/quota.py        чистые функции: decide() (что допустить), numbered_period();
                       Admission, Claim, Ticket — данные, без ввода-вывода
domain/quota_period.py период «годовщина»: якорь + k месяцев по Вьетнаму (UTC+7)
db/repositories/quota.py  SQL журнала: резерв под блокировкой, confirm, release, чистка
                       зависших, usage, identify (карточка по паре «источник, внешний id»);
                       право предложить подписку — `UserRepository.claim_paywall_offer`:
                       это колонка клиента, а не журнала
bot/quota.py           QuotaService: admit / confirm / release; порты Ledger,
                       Entitlements, Clock; владелец и слежение — без потолка
bot/quota_ledger.py    SqlLedger — единственное место, где бот встречает базу ради
                       квоты (сессия и коммит на каждый вызов)
simulation/ledger.py   MemoryLedger — подделка с теми же правилами для тестов
worker/quota_sweep.py  раз в минуту снимает резервы диалога старше десяти минут
```

Три решения, из-за которых слой выглядит именно так.

- **Решение «сколько пустить» — чистая функция, исполняемая под блокировкой.**
  `decide(запрошено, уже_видено, занято, потолок)` не знает про базу, поэтому каждое
  правило (остаток 4 из 37, виденное бесплатно при нуле, порядок выдачи) проверяется
  обычным тестом; база исполняет ту же функцию, но под `SELECT ... FOR UPDATE` строки
  периода. Параллельные ответы одного клиента встают в очередь, и «осталось 3» не
  видят оба: двадцать одновременных резервов по шесть карточек при остатке десять
  дают ровно десять строк (`tests/test_quota_db.py`).
- **Порт `Ledger` и подделка с контрактными тестами.** `QuotaService` не импортирует
  SQLAlchemy: журнал приходит протоколом. `MemoryLedger` и `SqlLedger` проходят
  одни и те же сценарии (`tests/test_quota_ledger.py`), поэтому подделке верят не на
  слово. Чего подделка не воспроизводит (блокировки, CHECK границ, составные ключи),
  проверяет только живой Postgres.
- **Резерв → отправка → подтверждение или возврат.** Запись коммитится ДО отправки,
  иначе двойное нажатие даст обоим поискам одни и те же карточки. Не дошло —
  `release`; процесс умер между шагами — резерв снимет воркер. Сбой подтверждения
  уходит в лог, а не в клиента: сообщение уже доставлено, откатывать нечего. Сбой
  возврата — тоже в лог: он вызывается из `except`, и брошенная ошибка подменила бы
  настоящую причину.

**Показ через квоту — отдельный модуль, а не ветка в диалоге.** `bot/showing.py`
получает итог поиска и решает, что из него уходит человеку: берёт страницу (первые
`MAX_CARDS` находок), опознаёт карточки журнала (`listing_id` из источника либо пара
«источник, внешний id»), зовёт `QuotaService.admit`, собирает `Gate` (допущенные
карточки и право на предложение) и отдаёт презентеру, который остаётся чистой функцией.
Порядок тот же, что у резерва: допуск → отправка → `confirm` или `release`; возврат
идёт из корня иерархии исключений, потому что отмена задачи по таймауту тоже значит
«не показано». Предложение подписки уходит после выдачи и отдельным сообщением: оно не
задерживает карточки и не отнимает их при своём сбое.

`Conversation` получает квоту необязательной зависимостью (`quota=None` — прежнее
поведение, на нём живут симулятор и большинство тестов диалога) и тратит на неё
несколько строк: кто пишет (`_Turn.client`) и номер запроса для счётчиков. Недоступная
квота — честная реплика «не смог проверить остаток», а не карточки в обход лимита и не
молчание. Находки, которых нет в журнале, показываются, но не считаются, а в лог идёт
`quota.unidentified_cards`: прятать выдачу молча хуже, чем не посчитать.

Отложенные ответы (`agent_app/followup.py`, доля получателя — `followup_quota.py`)
проходят ту же точку `admit` на каждого получателя: анализ каталога один на задачу, а
остаток у каждого свой. Резерв
подтверждается, когда ответ лёг в очередь доставки, и возвращается, если не лёг или
запись упала. Слова про лимит и подписку — `bot/wording_plan.py` (числа из
`domain/plans`, даты по Вьетнаму), а не `wording.py`: меняются они по решению владельца,
а не вместе с ранжированием.

Что не сделано намеренно: `Entitlements` по умолчанию отдаёт ноль слотов — подписки
подключает платёжный пакет; слежение (`channel = 'monitor'`) в журнал пока никто не
пишет, но таблица и правило подсчёта к этому готовы.

## 6. Матчинг и ранжирование

**Жёсткие фильтры (SQL, отсекают наглухо):** город, категория, тип сделки,
deal-breakers, возраст объявления. Пока исторические объявления ещё проходят
воронку, живой поиск применяет ту же детерминированную формулу в Python до
показа карточек: иначе клиент видел бы пять самых свежих ссылок, а не пять
вариантов под свой паспорт.
**Мягкие (влияют на score):** бюджет, атрибуты, репутация продавца.

```
score = 0.35·freshness + 0.30·price_fit + 0.25·attr_match + 0.10·seller_rep

freshness  = exp(-age_hours / 48)     свежесть решает: вчерашний байк уже продан
price_fit  = 1.0 в бюджете, линейно вниз до 0 при +30% сверху
attr_match = доля совпавших must_have; deal_breaker выбрасывает кандидата
seller_rep = 1 - scam_score
```

**Сортировки мало, поэтому у живого поиска есть и отсев.** «Ниже» не значит «не
показан»: карточек показывается пять, и когда лучшего нет, первыми пятью
оказывается мусор — на «honda lead» это были три Airblade и лот 59-дневной
давности (02.09.2026). Перед показом снимаются две вещи: лот другой известной
модели, когда клиент модель назвал, и лот старше 28 дней. Первое не
возвращается никогда — это не «похуже», а не тот предмет; второе возвращается,
если после отсева не осталось ничего, и тогда честность берёт на себя карточка
(«могло быть продано»). Подробности и почему порог здесь по дате, а не по баллу
— [spec-v2, 2.7](spec-v2.md#27-что-доходит-до-клиента--отбор-перед-показом).

Ранжирует **SQL, а не LLM**. Модель подключается на последнем шаге и только
чтобы написать человеческий текст карточек и честно сказать, чем вариант не
идеален («на 50$ выше бюджета, зато 2024 год»). Ранжирование моделью медленно,
недетерминированно и невоспроизводимо при разборе жалобы «почему мне это
показали».

## 7. Подписки

Новая карточка → кандидаты по жёстким фильтрам → score → выбранный клиентом режим доставки:

| режим | Действие |
|---|---|
| `instant` | сразу, кроме тихих часов, максимум 5 в сутки на подписку |
| `digest` | одним сообщением в 18:00 Asia/Ho_Chi_Minh |
| 0.45–0.55 | серая зона: **один** LLM-вызов на проверку соответствия |
| < 0.45 | молчим |

LLM в цикле уведомлений почти не участвует: иначе каждое новое объявление
умножается на число активных подписок и фри-квота кончается за час.

Троттлинг обязателен. Бот, который шлёт сорок сообщений в день, отключается
пользователем в первые сутки — это не гипотеза, а стандартная судьба
алерт-ботов.

### 7.1 Монитор подписок: как проход защищён от собственных сбоев

Матчер (`worker/matcher.py`) — единственное место, где платная услуга становится
сообщениями, поэтому его устройство держится на правиле «одна неудача не
останавливает остальных». Что именно и чем проверено — ниже; тесты называют
дефект, который закрывают (нумерация D1–D15 — из разведки 03.10.2026).

**Часы внедряются, проход живёт одним моментом (D6).** Матчер получает порт
`Clock` и `tick(now=...)`; срок подписки, окно свежести карточек, граница суток,
время постановки и слот суточного лимита считаются от ОДНОГО момента. Раньше
`now` доходил только до оценки карточек, а подписки выбирались по часам
процесса, и проход «на заданном времени» судил подписку по одному «сейчас», а
карточки — по другому. Слот суток — `notifications.created_at` — тоже ставится
явно (`enqueue(now=...)`), а не колонкой `DEFAULT now()`: остаток слотов
проход считает от своей полуночи, и слот с часов базы был бы чужим «сейчас».
`DeliveryRepository.set_active` принимает `now` по той же причине. Тесты живой
базы не зашивают время (`test_db_clock_rule.py`): срок и окна сверяются с тем,
что проход получил аргументом.

**Долларовый бюджет сужает выдачу — или подписка ждёт курса (D2).** Объявления
написаны в донгах, и потолок в долларах без курса не существует. Прежний
`Matcher()` строил отбор без потолка, а `_price_fit` ставил единицу любой
известной цене: дорогое уходило клиенту как «идеально в бюджете» (03.10.2026 у
10 из 14 бюджетных паспортов в базе бюджет в USD, и при 26 000 ₫/$ дороже
бюджета 38–91% карточек). Теперь воркер собирает матчер функцией
`build_matcher()` и даёт ему источник `search.currency.usd_vnd_rate` (кэш на
шесть часов уже внутри). Подписка с долларовым потолком
(`matching.needs_usd_rate`) без курса **ждёт**: ничего не шлёт и не двигает
курсор — вернётся курс, и проход возьмёт всё с того же места. Это решение
владельца («ждать», а не слать без бюджета). Остальные подписки не ждут.

Недоступный источник не опрашивают на каждом проходе: пауза 60 секунд, отказ
пишется в журнал один раз на простой (`fx.usd_rate_unavailable` →
`fx.usd_rate_restored`). Ожидающие подписки видны строкой за проход
(`matcher.waiting_for_rate`) и счётчиком `Matcher.counters.skipped_no_rate`.
Нуль, минус, NaN и бесконечность — не курс: NaN в Postgres больше любого числа,
и потолок «до NaN» вернул бы тот же дефект. Бюджет в EUR и RUB курса не получает
ни в диалоге, ни здесь — это прежнее расхождение, оно остаётся.

**Обход идёт по кругу, размер порции — константа в конфиге (D4).** Проход берёт
`MONITOR_BATCH` подписок (по умолчанию 50) и идёт «кого не смотрели дольше всех —
первым»: `ORDER BY last_scanned_at ASC NULLS FIRST, id`. Свежая оплаченная
подписка (`last_scanned_at IS NULL`) стоит в начале. Прежний `ORDER BY id LIMIT 50`
без смещения не обслуживал 51-ю и дальнейшие подписки никогда, пока не истечёт одна
из первых пятидесяти. `last_scanned_at` — ключ ротации, а не «когда последний раз
всё удалось»: обойдённой считается любая подписка, которую взяли в работу, — и та,
что ничего не нашла, и та, что упёрлась в суточный потолок, и та, что ждёт курса
(её курсор при этом не двигается). Иначе те, кому нечего отдать, стояли бы в начале
порции вечно и морили остальных. Строки берутся `FOR UPDATE SKIP LOCKED`: две
копии воркера не делят подписку и не ждут друг друга.

**Одна больная подписка не роняет проход (D5).** Каждая подписка работает в своём
SAVEPOINT: сбой откатывает только её записи (даже уже поставленную в очередь
карточку), и она уходит в **карантин** — `failed_streak` (сколько проходов подряд
падала), `last_error` (чем) и `quarantined_until` (до какого времени её не трогать).
Пауза растёт вдвое — 5, 10, 20 минут … — и упирается в 6 часов
(`worker/quarantine.py`); по истечении подписка возвращается в обход сама, а
первый же удачный проход обнуляет все три колонки. Прежний проход шёл одной
транзакцией без охраны: незнакомое значение перечисления в паспорте (оно остаётся в
базе после `git revert` кода, добавившего значение) падало при разборе пачки,
Docker перезапускал воркер, цикл повторялся — вставала вся воронка, а не один
мониторинг. Строку, которую не удалось даже прочитать, `claim_due` возвращает
отдельно с причиной, и она уходит в тот же карантин.

Охраняется `Exception`, а не `BaseException`: остановка процесса (`CancelledError`
при SIGTERM, `KeyboardInterrupt`) — не сбой подписки и в карантин за неё не
отправляет. Типы ожидаемых ошибок не перечисляются: список ожиданий и есть дефект.
Падение самой выборки (база недоступна) не прячется — изолировать там нечего.
Компромисс записан честно: системная ошибка в самом матчере теперь уведёт в
карантин ВСЕ подписки, и проход переживёт её, но будет молчать; это видно по
`matcher.quarantined` на уровне `error` (с причиной) и по счётчику
`Matcher.counters.quarantined`, а прежний вариант — падение процесса — молчал бы
так же, только с перезапусками.

**Право проверяется не только при выборе подписок (D7).** Раньше срок смотрел
только выбор, а постановка в очередь и отправка ему не доверяли ничего:
подписка, истёкшая или поставленная на паузу между выбором и вставкой, всё равно
получила бы карточку, а уже стоящее в `outbox` уходило без оглядки на срок, хоть
через сутки. Теперь:

* ОДИН предикат права `entitled(now)` (`db/repositories/delivery.py`: подписка
  включена, а `expires_at` пуст или позже `now`) спрашивают и выбор подписок, и `enqueue` —
  прямо в самой вставке `INSERT … SELECT … WHERE EXISTS`, без зазора между
  «проверил» и «вставил». `False` из `enqueue` значит «не поставлено» (уже было
  или права нет), и ни одной строки в базе. Когда право начнёт считаться от числа
  живых подписок Stars, менять предикат надо в одном месте;
* найденное в оплаченный период доходит до клиента ещё **6 часов после срока**
  (`MONITOR_LAPSE_GRACE_HOURS`) — он платил за находки, а не за момент, когда
  нотифаер до них добрался. Дальше строка очереди становится
  `outbox.status = 'cancelled'`: отменена, а не потеряна, запись в `notifications`
  остаётся, и карточка повторно не ставится. Отмену делает проход матчера первым
  шагом (`MonitorRepository.cancel_lapsed`), ровно в границу льготы сообщение ещё
  доходит. Продление срока внутри льготы возвращает очередь в силу. Строки без
  подписки (ответы сбора каталога) и бессрочные подписки отмена не касается.
  Отмена идёт `SKIP LOCKED`: строку, которую нотифаер уже взял в отправку, она не
  ждёт — проход матчера стоит на пути всего воркера, а судьба такой строки всё равно
  решена (отменять отправляемое поздно).

Что здесь осознанно НЕ сделано. `expires_at IS NULL` по-прежнему читается как
«бессрочно» (так заведены подписки без платежа): платёж срок ставит всегда, и
переворот условия в «нет срока — нет права» ломал бы подписки владельца; это
решение принадлежит пакету биллинга вместе с заменой предиката. Отмена идёт в
процессе воркера, а не нотифаера: при остановленном воркере просроченное доставляется
дальше, пока он не вернётся. Проверка «при отправке» внутри нотифаера — часть его
пакета (`MonitorRepository.cancel_lapsed` ей служит готовым методом).

### Почему не managed-БД на free-тире

Neon Free даёт 100 CU-hours в месяц — по их же документации это 0.25 CU в
течение 400 часов, то есть ~13 часов в сутки при 720 часах в месяце.
Приложение, держащее пул соединений круглосуточно, выедает месячную квоту
примерно за две недели, после чего компьют встаёт до следующего цикла.
Managed-БД на бесплатном тарифе и всегда-живой сервис плохо совместимы.

Раз VM всё равно нужна под Telethon, Postgres на ней же означает ноль сетевых
хопов, ноль внешних квот и ноль лишних аккаунтов. Устойчивость к потере машины
закрывается `pg_dump` по крону в R2 — одна строка в crontab.

### Почему не полный serverless

Соблазнительный вариант: коллектор как задача по расписанию (подключился,
догнал историю по `last_msg_id`, отключился), бот на webhook, БД в Neon. При
интервальном доступе квоты сходятся, и платить не нужно вообще ни за что.

Ломает его не экономика, а **плавающий IP**: при каждом холодном старте
контейнер получает новый адрес датацентра, а юзербот, логинящийся с постоянно
меняющихся IP, — ровно тот паттерн, на который Telegram отвечает блокировкой.
Аккаунт один, и переподписываться с нового номера на 30 групп после каждой
блокировки — это не работающий продукт. Фиксированный IP маленькой VM здесь
функциональное требование, а не привычка.

Второй, меньший минус: задержка уведомлений становится равна интервалу
запуска (10–15 минут) вместо мгновенной.

Почему **не Cloudflare D1**: `rows written` считает и записи в индексы,
`rows read` считает просканированные строки, так что поисковая нагрузка выедает
5 млн в день; доступ снаружи Workers требует прокси-Worker, а collector на
Telethon внутри Workers жить не может в принципе.

## 9. Экономика — почему это бесплатно

Расчёт на 20 чатов по 300 сообщений, то есть 6000 в день:

```
regex-гейт      6000 → ~700          0 вызовов
prefilter        700 → батчи по 20   35 вызовов
structured       250 → батчи по 10   25 вызовов
диалог           100 запросов × 2    200 вызовов
выдача           100 запросов × 1    100 вызовов
подписки         серая зона          ~20 вызовов
                                    ─────────────
                                    ~380 вызовов в день
```

Free-лимитов брокера хватает с запасом. Критично держать три вещи: regex-гейт
перед LLM, батчинг и **отдельный project-key с низким дневным cap**, чтобы бот
физически не мог выесть чужую квоту.

## 10. Риски

| Риск | Что делаем |
|---|---|
| Бан юзербота | отдельный номер, только чтение, 20–30 групп вручную с паузами в дни, лимит запросов, `FloodWaitError` с экспоненциальной паузой |
| `FloodWait` на поиске | максимум 10 чатов на запрос, семафор, кэш результатов 5–10 минут |
| Мультиязычность | чаты Нячанга русско-англо-вьетнамские; **regex-гейт сразу мультиязычный**, иначе первая ступень выкосит половину настоящих объявлений |
| Кросспостинг | дедуп по нормализованному тексту и телефону, иначе выдача из пяти копий одного байка |
| Скам и риелторы-спамеры | `sellers.scam_score`: частота постинга, повторяющийся текст, жалобы клиентов |
| Простой сбора (выключенный ноутбук, деплой, падение коллектора) | `chats.last_msg_id`: каждые 15 минут дочитываем до 200 последних сообщений каждого из первых десяти активных чатов после курсора и вставляем их с дедупликацией. Telegram очередь для нас не держит — без догона объявления за время простоя пропадают молча |
| Потеря сессии | `StringSession` в БД или секрете, не файлом — на эфемерной ФС она умрёт |
| Качество выдачи | кнопки обратной связи на каждой карточке уточняют паспорт |

## 11. Этапы

**P0 — проверка идеи (вечер).** Пять чатов, только живой поиск, без ингеста:
диалог → паспорт → `messages.search` → пять карточек. Цель — увидеть, полезна
ли выдача вообще. Если карточки мусорные, остальная инфраструктура
бессмысленна, и это выясняется за часы, а не за неделю.

**P1 — база.** Ингест, воронка, Postgres, полнотекстовый поиск (`pg_trgm` и
`tsvector`), карточки из базы вместо живого поиска.

**P2 — подписки.** Матчинг, outbox, троттлинг, дайджесты.

**P3 — качество.** pgvector и семантика, скам-скоринг, репутация продавцов,
второй город.

Между P0 и P1 стоит явная точка принятия решения. Она не техническая — код к
тому моменту работает; вопрос в том, попадает ли выдача.
