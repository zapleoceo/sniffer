# SnifferBot — архитектура

> Агент в Telegram, который выясняет у клиента, что ему нужно, формирует
> **паспорт запроса**, показывает актуальные предложения из телеграм-сообществ
> и присылает новые по мере появления.

> **Дополнено [spec-v2.md](spec-v2.md).** Там источники перестали быть
> курируемым списком чатов и превратились в реестр адаптеров с планировщиком,
> добавился обязательный verifier и задел под публичный доступ. Где документы
> расходятся, верен spec-v2.

## 1. Что делаем и чего не делаем

**Делаем:** диалог → структурированный паспорт запроса → подбор из уже
собранных объявлений + живой поиск по чатам → подписка на новые совпадения.

**Не делаем (сознательно):**

| Не делаем | Почему |
|---|---|
| Не перепечатываем объявления | отдаём ссылку на оригинал; снимает вопрос ответственности за чужой контент и контакты. Форма ссылки зависит от чата: у публичной группы `t.me/<username>/<msg>` (открывается у кого угодно), у закрытой — `t.me/c/<chat>/<msg>` (только для участников), в форуме между ними встаёт номер темы — [spec-v2, 4.4](spec-v2.md#44-telegram-группы--что-стоило-дорого-узнать) |
| Не пишем от имени юзербота | любое исходящее действие с userbot-аккаунта кратно повышает риск бана; аккаунт только читает |
| Не сводим людей и не берём комиссию | это поисковый помощник, а не маркетплейс — нет эскроу, нет модерации сделок, нет ответственности за них |
| Не держим базу контактов продавцов | контакт живёт внутри исходного сообщения, мы храним ссылку |

Первый рынок — **Нячанг**: байки, апартаменты и комнаты. Категории и город
задаются данными, а не кодом: добавить «Дананг + скутеры» — это строки в
таблицах, а не релиз.

## 2. Ключевое решение — паспорт запроса

Разница между поисковой строкой и агентом ровно одна: **агент хранит намерение
клиента как объект и переиспользует его**. Паспорт — центральная сущность, из
неё растёт всё остальное:

```
паспорт → запрос к базе (что есть сейчас)
паспорт → ключевые слова для живого поиска по чатам
паспорт → фильтр подписки (что присылать потом)
паспорт → критерии ранжирования (почему это в топе)
паспорт ← обратная связь «дорого» / «не то» уточняет паспорт
```

Один и тот же объект обслуживает и разовый подбор, и подписку. Поэтому
подписка — не отдельная фича, а **статус паспорта** (`active`).

Полная схема полей: [passport.md](passport.md).

**Правило диалога: задаём только те вопросы, которые реально сужают выдачу.**
Для байка в Нячанге бюджет и «автомат или механика» режут выборку вдвое, а цвет
не режет почти никак. Агент оценивает, сколько кандидатов отсекает каждое
незаполненное поле, и спрашивает максимум два-три самых информативных. Допрос
из десяти вопросов убивает конверсию сильнее, чем неточная выдача.

## 3. Компоненты

```
                    ┌──────────────────────────────────────┐
   клиент  ────────►│  bot (aiogram 3)                     │
   в Telegram       │  диалог, паспорт, выдача, подписки   │
                    └───────┬──────────────────────▲───────┘
                            │                      │ уведомления
                            ▼                      │
                    ┌──────────────────────────────┴───────┐
                    │  Postgres                            │
                    │  chats · raw_messages · listings     │
                    │  passports · subscriptions · outbox  │
                    └───▲──────────────▲───────────────▲───┘
                        │              │               │
       ингест ──────────┘              │               └──── матчинг и рассылка
                        │              │                          │
        ┌───────────────┴───────┐  ┌───┴──────────────┐  ┌────────┴─────────┐
        │ collector (Telethon)  │  │ worker           │  │ notifier         │
        │ live-подписка на чаты │  │ воронка обработки│  │ дедуп, троттлинг │
        │ messages.search       │  │ извлечение карточ│  │ digest / instant │
        └───────────┬───────────┘  └───────┬──────────┘  └──────────────────┘
                    │                      │
                    │              ┌───────▼──────────────────────────┐
                    │              │ AIbroker  aib.zapleo.com         │
                    │              │ prefilter · structured · fast    │
                    │              └──────────────────────────────────┘
                    ▼
            ┌───────────────┐
            │ Telegram      │   фото не храним: из них берём только
            │ MTProto       │   перцептивный хеш для дедупа кросспостов
            └───────────────┘   (roadmap.md, волна 5)
```

Четыре процесса на одной машине, общаются **только через Postgres** — брокер
сообщений не нужен, очередь делается на `SELECT … FOR UPDATE SKIP LOCKED`. Это
осознанный отказ от Redis и RabbitMQ: на таком объёме они добавляют
операционную сложность и не решают ни одной реальной проблемы.

| Процесс | Ответственность | Почему отдельный |
|---|---|---|
| `bot` | диалог, показ карточек, управление подписками | падение ингеста не должно ронять общение с клиентом |
| `collector` | единственный держатель MTProto-сессии | сессия одна на аккаунт; два процесса с одной сессией дают `AuthKeyDuplicated` |
| `worker` | воронка: гейт → извлечение → нормализация → матчинг | тяжёлый и перезапускаемый, его можно убить без потерь |
| `notifier` | доставка с троттлингом | доставка обязана переживать рестарт воркера, отсюда таблица `outbox` |

### 3.1 Точки входа

У каждого процесса свой `__main__.py`, ровно те четыре команды, что стоят в
`docker-compose.yml`:

```
python -m sniffer.bot         диалог и выдача (aiogram, long polling)
python -m sniffer.collector   MTProto-сессия, чтение сообществ
python -m sniffer.worker      воронка, очередь jobs
python -m sniffer.notifier    доставка из outbox
```

Общий каркас — `sniffer/runtime/`: настройка лога, обработка сигналов и
холостой цикл. Слоем он не является, бизнес-логики в нём нет; он существует,
чтобы четыре точки входа не описывали одно и то же четырьмя способами.

**Процесс без обязательной настройки не падает.** Он пишет в лог, чего именно
не хватает — именами из `.env`, — и уходит ждать, перепроверяя окружение раз в
минуту:

```
{"event": "service.not_configured", "service": "bot", "missing": ["BOT_TOKEN"],
 "message": "не настроен: нет BOT_TOKEN, жду конфигурации"}
```

Причина конкретная: контейнер, перезапускающийся каждые пять секунд, выглядит
как сломанный деплой и заваливает healthcheck, хотя на деле просто не заведён
секрет. Ожидание отличает «не настроен» от «сломан» и в логе, и в `docker ps`.
Перепроверка не декоративная: секрет заводят уже после первого запуска, и
процесс подхватывает его сам, без `docker compose restart`.

Пустой токен и неверный токен — разные вещи. Пустой означает ожидание, неверный
означает падение с внятной ошибкой: молча ждать при опечатке в секрете хуже,
чем упасть.

| Процесс | Без чего не работает |
|---|---|
| `bot` | `BOT_TOKEN` |
| `notifier` | `BOT_TOKEN` — доставка идёт тем же Bot API |
| `collector` | `TG_API_ID`, `TG_API_HASH`, `TG_SESSION`; код подтверждения в фоновом контейнере ввести негде, поэтому строка сессии обязательна — её выдаёт `python -m sniffer.collector auth` ([deploy.md, 3.5](deploy.md#35-авторизация-юзербота)) |
| `worker` | ничего: без базы он просто не найдёт задач |

**Подкоманда — это `auth` и только `auth`.** Любой другой аргумент —
неизвестное имя, опечатка, лишний позиционный — заканчивается кодом 9 и
подсказкой, а не запуском сервиса. Разбор строгий намеренно:
`python -m sniffer.collector notauth` раньше молча уходил в демона, аргумент
терялся, и владелец ждал диалога авторизации, глядя на обычный старт
коллектора.

**Как мы подписаны в Telegram → Настройки → Устройства — общий контракт двух
слоёв.** Клиента создают `collector/client.py` (разовый вход за строкой сессии)
и `sources/telegram_client.py` (боевое чтение по этой строке). Telegram считает
устройством пару (auth key, подпись клиента), поэтому одна и та же сессия с
разными `device_model` показывается там ДВУМЯ строками — и владелец, решая,
какой сеанс отозвать, не понимает, откуда второй. Подпись поэтому лежит в
`sniffer/telegram_identity.py` — модуле-листе, который видят оба слоя и который
не создаёт между ними зависимости; расхождение ловит
`tests/test_telegram_identity.py`.

**SIGTERM останавливает, а не убивает.** `docker compose stop` даёт десять
секунд; бот дослушивает текущий апдейт и закрывает сессию, фоновые процессы
выходят из цикла на ближайшей проверке. Лог структурный: JSON в контейнере,
человекочитаемый рендер в терминале, уровень из `LOG_LEVEL`.

Холостой цикл фоновых процессов молчит: «нечего делать» пишется не чаще раза в
пять минут, иначе `max-size: 10m` из compose открутится за час. Пока работа
находится, цикл не спит вовсе — очередь разгребается пачками, а не по таймеру.

## 4. Воронка обработки — где решается стоимость

Главная ошибка в таких ботах — отправлять каждое сообщение в LLM. Лестница
«дёшево → дорого», где каждая ступень отсеивает мусор до того, как он дойдёт до
дорогого слоя:

| # | Ступень | Стоимость | Отсев |
|---|---|---|---|
| 0 | Дедуп: `UNIQUE(chat_id, msg_id)` плюс хэш нормализованного текста | 0 | кросспостинг одного байка в пять групп |
| 1 | Regex-гейт: цена (`$`, `k`, `тр`, `VND`, `triệu`) **и** глагол сделки | 0 | ~85–90% |
| 2 | LLM `prefilter`: «объявление? да/нет», **пачками по 20** | free, кэш 10 мин | ~60% остатка |
| 3 | LLM `structured`: карточка по strict `json_schema` | free | — |
| 4 | Эмбеддинг для семантики | опционально, этап P3 | — |

Батчинг — не оптимизация, а условие бесплатности: 700 сообщений по одному это
700 вызовов, пачками по 20 — тридцать пять. Ровно разница между «влезаем в
free-квоту» и «не влезаем».

## 5. Модель данных

```
chats            справочник отслеживаемых сообществ (курируется вручную)
raw_messages     сырьё как пришло; TTL 30 дней
listings         нормализованная карточка предложения — то, что ищем
listing_media    отпечаток фото (перцептивный хеш) для дедупа кросспостов
sellers          агрегат по автору: частота постинга, скам-скор
users            клиенты бота
passports        паспорт запроса, версионируемый
passport_events  история диалога и обратной связи
subscriptions    активный паспорт плюс политика уведомлений
notifications    что кому уже отправлено (дедуп)
outbox           очередь доставки, переживает рестарт
jobs             внутренняя очередь воронки
```

DDL: [`infra/sql/001_init.sql`](../infra/sql/001_init.sql).

Два решения стоит подсветить отдельно:

- **`raw_messages` и `listings` разделены.** Сырьё живёт 30 дней и удаляется,
  карточки живут дольше и компактны. Будь карточка колонкой в сырье, ретеншн
  удалял бы вместе с мусором и полезное.
- **Паспорт версионируется, а не перезаписывается.** Клиент говорит «дорого» —
  создаётся новая версия с изменённым бюджетом, старая остаётся. Без этого
  невозможно ни отладить агента, ни объяснить клиенту, почему выдача изменилась.

### 5.1 Слой доступа — `db/`

Единственное место в проекте, где есть SQL. Всё выше по слоям получает отсюда
доменные записи и не знает ни про SQLAlchemy, ни про имена колонок.

```
db/engine.py        async engine + сессия на единицу работы
db/models/          ORM-зеркало 001_init.sql, разбито по разделам DDL
db/mappers.py       строка таблицы ↔ доменная запись
db/repositories/    по одному классу на агрегат
domain/records.py   что репозиторий отдаёт наружу
```

Четыре решения, из-за которых слой выглядит именно так:

- **Схему создаёт SQL-файл, модели её только отражают.** `metadata.create_all`
  здесь не вызывается никогда: расширения, GIN-индексы и `vector(1024)`
  описываются обычным DDL точнее, а два источника правды про схему — это
  гарантированный дрейф. Чтобы зеркало не разъехалось молча,
  `tests/test_db_models.py` сверяет имена таблиц и колонок прямо с
  `001_init.sql`, и делает это без базы — то есть на любой машине.
- **Наружу уезжают dataclass-ы, а не ORM-сущности.** ORM-объект тащит за собой
  сессию: после закрытия `async with` обращение к незагруженному полю падает
  `DetachedInstanceError` уже в боте, далеко от места, где сессия закрылась.
  Заодно это держит правило слоёв — `domain` не зависит ни от чего.
- **Репозиторий не коммитит.** Он получает открытую сессию и работает в её
  транзакции; границу единицы работы ставит вызывающий. Автокоммит сделал бы
  эту границу невидимой в коде, а «прочитал» — неотличимым от «записал».
- **Дедуп сырья живёт на уникальном индексе, а не в коде.** Батч-вставка идёт
  через `ON CONFLICT (chat_tg_id, msg_id) DO NOTHING … RETURNING id`: коллектор
  после каждого простоя перечитывает историю и приносит уже виденное, а
  проверять существование по одному сообщению значило бы делать SELECT на
  каждое и всё равно проигрывать гонку.

Очередь `jobs` разбирается через `SELECT … FOR UPDATE SKIP LOCKED`: задача
выбирается, помечается `running` и коммитится сразу, дальше воркер работает уже
без замка. Второй воркер не ждёт освобождения строки, а пропускает её и берёт
следующую — иначе четыре процесса выстроились бы в очередь за одной задачей.
Возврат в очередь после ошибки идёт через `run_after`; потолок попыток ставит
вызывающий, потому что он один знает, сколько их осмысленно для его `kind`.

**Кто ещё читает этот слой: источники.** Адаптеру `telegram_groups` нужен
реестр чатов, а он живёт в таблице `chats`. Зависимость идёт вниз (`sources →
db`) и сведена в одну функцию `new_directory()` в
`sources/chat_directory.py`: она собирает `RepositoryChatDirectory(session_scope,
ChatRepository)` и стоит у адаптера значением по умолчанию, чтобы боевой путь
получал базу, а не заглушку. Сам адаптер про SQL и про `sniffer.db` не знает —
он видит протокол `ChatDirectory`. Подробности и цена ошибки —
[spec-v2, 4.4](spec-v2.md#44-telegram-группы--что-стоило-дорого-узнать).

**Тесты слоя требуют настоящий Postgres.** Схема Postgres-специфична, на sqlite
не поднимается, а подделка была бы зелёной ровно в тех местах, которые и
ломаются. Поэтому тесты с базой берут адрес из `TEST_DATABASE_URL` и
пропускаются, когда её нет: у разработчика без Docker прогон остаётся зелёным,
в CI поднимается `pgvector/pgvector:pg16`, накатывается `001_init.sql` и они
выполняются. Чистая логика — маппинг и сверка со схемой — покрыта обычными
тестами без базы.

## 6. Матчинг и ранжирование

**Жёсткие фильтры (SQL, отсекают наглухо):** город, категория, тип сделки,
deal-breakers, возраст объявления.
**Мягкие (влияют на score):** бюджет, атрибуты, репутация продавца.

```
score = 0.35·freshness + 0.30·price_fit + 0.25·attr_match + 0.10·seller_rep

freshness  = exp(-age_hours / 48)     свежесть решает: вчерашний байк уже продан
price_fit  = 1.0 в бюджете, линейно вниз до 0 при +30% сверху
attr_match = доля совпавших must_have; deal_breaker выбрасывает кандидата
seller_rep = 1 - scam_score
```

Ранжирует **SQL, а не LLM**. Модель подключается на последнем шаге и только
чтобы написать человеческий текст карточек и честно сказать, чем вариант не
идеален («на 50$ выше бюджета, зато 2024 год»). Ранжирование моделью медленно,
недетерминированно и невоспроизводимо при разборе жалобы «почему мне это
показали».

## 7. Подписки

Новая карточка → кандидаты по жёстким фильтрам → score → политика доставки:

| score | Действие |
|---|---|
| > 0.80 | мгновенно, максимум 5 в сутки на подписку |
| 0.55–0.80 | в дайджест один-два раза в день |
| 0.45–0.55 | серая зона: **один** LLM-вызов на проверку соответствия |
| < 0.45 | молчим |

LLM в цикле уведомлений почти не участвует: иначе каждое новое объявление
умножается на число активных подписок и фри-квота кончается за час.

Троттлинг обязателен. Бот, который шлёт сорок сообщений в день, отключается
пользователем в первые сутки — это не гипотеза, а стандартная судьба
алерт-ботов.

## 8. Что используем

| Слой | Решение | Статус | Почему это |
|---|---|---|---|
| Чтение Telegram | **Telethon**, юзербот на отдельном номере | нужен номер | Bot API не видит чужие группы и не умеет искать по истории |
| Интерфейс | **aiogram 3** (Bot API) | нужен токен BotFather | обычный бот, аккаунт отдельный от юзербота |
| LLM | **AIbroker** `aib.zapleo.com` | нужен project-key | free-first цепочки, ротация ключей, свой дневной cap |
| БД | **Postgres 16 + pgvector** на той же VM | нужен аккаунт хоста | реляционка, полнотекст и векторы в одном месте, без внешних квот |
| Медиа | **не храним** | — | фото не складываем: по ссылке на оригинал они и так видны, а хранить чужие снимки — это перепечатка. Из фото берём только перцептивный хеш для дедупа, 16 байт |
| Хост | **Hetzner `195.201.31.49`** — общая машина с Верой, Степаном и AIbroker | готово | 4 vCPU / 7.6 ГБ / 75 ГБ после апгрейда 2026-08-31; предельная стоимость нового проекта — ноль |
| Оркестрация | Docker Compose | готово | postgres плюс четыре процесса, одинаково локально и в проде |

### Почему не managed-БД на free-тире

Neon Free даёт 100 CU-hours в месяц — по их же документации это 0.25 CU в
течение 400 часов, то есть ~13 часов в сутки при 720 часах в месяце.
Приложение, держащее пул соединений круглосуточно, выедает месячную квоту
примерно за две недели, после чего компьют встаёт до следующего цикла.
Managed-БД на бесплатном тарифе и всегда-живой сервис плохо совместимы.

Раз VM всё равно нужна под Telethon, Postgres на ней же означает ноль сетевых
хопов, ноль внешних квот и ноль лишних аккаунтов. Устойчивость к потере машины
закрывается `pg_dump` по крону в R2 — одна строка в crontab.

### Почему не полный serverless

Соблазнительный вариант: коллектор как задача по расписанию (подключился,
догнал историю по `last_msg_id`, отключился), бот на webhook, БД в Neon. При
интервальном доступе квоты сходятся, и платить не нужно вообще ни за что.

Ломает его не экономика, а **плавающий IP**: при каждом холодном старте
контейнер получает новый адрес датацентра, а юзербот, логинящийся с постоянно
меняющихся IP, — ровно тот паттерн, на который Telegram отвечает блокировкой.
Аккаунт один, и переподписываться с нового номера на 30 групп после каждой
блокировки — это не работающий продукт. Фиксированный IP маленькой VM здесь
функциональное требование, а не привычка.

Второй, меньший минус: задержка уведомлений становится равна интервалу
запуска (10–15 минут) вместо мгновенной.

Почему **не Cloudflare D1**: `rows written` считает и записи в индексы,
`rows read` считает просканированные строки, так что поисковая нагрузка выедает
5 млн в день; доступ снаружи Workers требует прокси-Worker, а collector на
Telethon внутри Workers жить не может в принципе.

## 9. Экономика — почему это бесплатно

Расчёт на 20 чатов по 300 сообщений, то есть 6000 в день:

```
regex-гейт      6000 → ~700          0 вызовов
prefilter        700 → батчи по 20   35 вызовов
structured       250 → батчи по 10   25 вызовов
диалог           100 запросов × 2    200 вызовов
выдача           100 запросов × 1    100 вызовов
подписки         серая зона          ~20 вызовов
                                    ─────────────
                                    ~380 вызовов в день
```

Free-лимитов брокера хватает с запасом. Критично держать три вещи: regex-гейт
перед LLM, батчинг и **отдельный project-key с низким дневным cap**, чтобы бот
физически не мог выесть чужую квоту.

## 10. Риски

| Риск | Что делаем |
|---|---|
| Бан юзербота | отдельный номер, только чтение, 20–30 групп вручную с паузами в дни, лимит запросов, `FloodWaitError` с экспоненциальной паузой |
| `FloodWait` на поиске | максимум 10 чатов на запрос, семафор, кэш результатов 5–10 минут |
| Мультиязычность | чаты Нячанга русско-англо-вьетнамские; **regex-гейт сразу мультиязычный**, иначе первая ступень выкосит половину настоящих объявлений |
| Кросспостинг | дедуп по нормализованному тексту и телефону, иначе выдача из пяти копий одного байка |
| Скам и риелторы-спамеры | `sellers.scam_score`: частота постинга, повторяющийся текст, жалобы клиентов |
| Простой сбора (выключенный ноутбук, деплой, падение коллектора) | `chats.last_msg_id`: при старте догоняем историю каждого чата с последнего прочитанного сообщения. Telegram очередь для нас не держит — без догона объявления за время простоя пропадают молча |
| Потеря сессии | `StringSession` в БД или секрете, не файлом — на эфемерной ФС она умрёт |
| Качество выдачи | кнопки обратной связи на каждой карточке уточняют паспорт |

## 11. Этапы

**P0 — проверка идеи (вечер).** Пять чатов, только живой поиск, без ингеста:
диалог → паспорт → `messages.search` → пять карточек. Цель — увидеть, полезна
ли выдача вообще. Если карточки мусорные, остальная инфраструктура
бессмысленна, и это выясняется за часы, а не за неделю.

**P1 — база.** Ингест, воронка, Postgres, полнотекстовый поиск (`pg_trgm` и
`tsvector`), карточки из базы вместо живого поиска.

**P2 — подписки.** Матчинг, outbox, троттлинг, дайджесты.

**P3 — качество.** pgvector и семантика, скам-скоринг, репутация продавцов,
второй город.

Между P0 и P1 стоит явная точка принятия решения. Она не техническая — код к
тому моменту работает; вопрос в том, попадает ли выдача.
