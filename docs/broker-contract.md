# Граница ответа AIbroker

Все вызовы моделей остаются через AIbroker: submit `/v1/jobs`, затем polling.
`BrokerClient.structured()` отправляет `json_schema` со `strict: true`, но не
считает это гарантией: провайдер может обрезать ответ или отказаться отвечать.

Перед платным вызовом проверяется корректность самой JSON Schema. После ответа
клиент принимает только JSON-объект, соответствующий схеме (тип, enum, required,
additionalProperties и вложенные ограничения — через `jsonschema`). Повторяющиеся
ключи, NaN/Infinity, переполнение чисел, Markdown-обёртки и хвост после JSON
отклоняются. Никакого автоматического «ремонта» JSON или повторной покупки ответа.

Если брокер передал `refusal`, ответ отклоняется. Если передал `finish_reason`,
принимаются только `stop` (без учёта регистра), `end_turn`, `completed`;
обрезание, фильтрация и неизвестные причины считаются незавершённым ответом.
Старый брокер без этого поля поддерживается, но в таком случае отличить
синтаксически завершённое обрезание от полного ответа невозможно.

Отказ представлен `BrokerOutputError`, наследником `BrokerError`: существующие
fallback-ветки продолжают работать. Диагностика содержит reason, provider,
request_id, job_id и доступный finish_reason, но не текст модели, промпт,
объяснение отказа или значения полей из ошибки валидатора. Учёт уже оплаченного
вызова происходит до проверки, поэтому отклонённый ответ не исчезает из расходов.

Это исключает принятие повреждённых данных приложением, **не обещает отсутствия
ошибок генерации у провайдера**. Доступ к данным/действиям разрешается только
после этой границы и отдельной доменной проверки полномочий.

Проверка: `tests/test_broker_output.py` проводит ответы через реальный HTTP-клиент
с MockTransport, проверяет схему, причины завершения, приватность диагностики
и отсутствие скрытых повторов. Сеть и живая модель в этих тестах не используются.
